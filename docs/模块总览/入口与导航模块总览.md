# 入口与导航模块总览

## 模块职责

负责应用进程与界面的启动骨架：`App` 提供全局数据层单例并在启动时拉起后台续跑与旧模型清理，`MainActivity` 挂载 Compose，`AppNav` 注册并路由 5 个页面、并在顶层挂载应用自更新的弹窗与启动静默检查，`Theme.kt` 决定配色，`AndroidManifest.xml` 声明权限（含自更新所需的 `REQUEST_INSTALL_PACKAGES`）、TTS 引擎可见性、前台服务与 FileProvider。

## 运作流程

**从哪来**：系统按 `AndroidManifest.xml:21` 的 `android:name=".App"` 实例化 `App`，`App.onCreate`（`App.kt:18-25`）在把自己写进 `companion` 的 `instance`（`:20`）之后做两件 v1.5.0 新增的启动事务：

1. `NoteProcessor.resumeStuck()`（`App.kt:22`）——查 Room 里所有 `TRANSCRIBING`/`GENERATING` 状态的半路笔记并逐条拉起（实现见笔记处理宿主模块总览；`pipeline/NoteProcessor.kt:89-104`）。这条协程会触发 `App.database` 的 `by lazy` 初始化（`App.kt:10`），即**启动瞬间就有一次数据库创建与查询**（旧版「启动瞬间不发生任何磁盘 IO」的说法自 v1.5.0 起不再成立；`App.settings`（`:11`）仍是首次使用才建）。
2. 裸线程 `Thread { ModelManager.cleanupLegacyTts(this) }.start()`（`App.kt:24`）——后台删掉已被 kokoro 替代的旧 vits-melo 朗读模型目录 `filesDir/tts/melo-zh-en`（`transcribe/ModelManager.kt:534-536`；「约 190MB」出自 `App.kt:23` 的注释声明，`ModelManager` 侧注释未写数字；该体积未入库无法实测，见模型下载模块总览）。刻意不起协程而用裸线程：它必须不依赖任何协程基础设施、与进程共存亡。

LAUNCHER 意图（`AndroidManifest.xml:34-37`）拉起 `MainActivity`（`AndroidManifest.xml:29`）。

**怎么处理**：`MainActivity.kt:13` 先 `enableEdgeToEdge()`，再 `setContent { TingsiweiTheme { AppNav() } }`（`MainActivity.kt:14-18`）。`TingsiweiTheme`（`Theme.kt:14-25`）按 `Build.VERSION.SDK_INT >= S` 选动态取色或内置明暗方案（`Theme.kt:19-23`），最后交给 `MaterialTheme`（`Theme.kt:24`）。`AppNav`（`AppNav.kt:19-59`）建一个 `rememberNavController()`（`AppNav.kt:20`），顶层持有应用自更新的 `UpdateViewModel`（`AppNav.kt:23`）并在 `LaunchedEffect(Unit)` 里静默检查一次（`AppNav.kt:24`），以 `Routes.HOME` 为起点声明 `NavHost`（`AppNav.kt:25`），5 个 `composable` 分支把跳转闭包作为参数注入页面（`AppNav.kt:26-56`，`SETTINGS` 额外注入 `updateVm`：`AppNav.kt:55`）——页面本身不认识 NavController，全部靠回调。`detail/{noteId}` 的参数从字符串解析，失败退化成 `0L`（`AppNav.kt:51`）。`NavHost` 之外再挂 `UpdateDialog(vm = updateVm)`（`AppNav.kt:58`），更新弹窗因此能盖在任何页面上。

**产出什么**：产出「路由字符串 → 页面 composable」的映射表和两个进程级单例（`App.database`、`App.settings`），不产出任何持久化数据；启动期的两张工单（续跑半路任务、清理旧朗读模型）分别派给笔记处理宿主与模型下载模块执行。

**影响谁**：所有页面与 ViewModel 都通过 `App.get()` 拿数据层（现行 28 处调用，分布见「对外接口」表），一旦 `App` 没注册或没跑到 `onCreate`，`App.kt:15` 的 `instance!!` 直接 NPE，ViewModel 构造即崩（与索引 README「坑」清单第 2 条一致）。反向引用也有：`RecordService` 的通知点击意图指向 `MainActivity`（`RecordService.kt:14`、`RecordService.kt:50-53`），录音通知的「完成」按钮指向 `.record.RecordService`（`AndroidManifest.xml:38-41`、`RecordService.kt:54-58`）。

## 依赖的上游模块

本模块是最顶层，没有业务上游依赖；它依赖的是**下游**：

- 数据层：`App.kt:4-5` 直接 import `data.db.AppDatabase` 与 `data.SettingsRepository`。
- 任务宿主与模型下载：`App.kt:6-7` import `pipeline.NoteProcessor`（启动续跑，`:22`）与 `transcribe.ModelManager`（启动清理，`:24`）。
- UI 五个页面：`AppNav.kt:27,35,43,52,55` 分别调 `HomeScreen`、`RecordScreen`、`TextInputScreen`、`DetailScreen`、`SettingsScreen`；顶层另有应用自更新的 `UpdateViewModel`（`:23`）与 `UpdateDialog`（`:58`）。
- 资源：`androidx.compose.material3`、`androidx.navigation:navigation-compose:2.8.5`、`androidx.activity:activity-compose:1.9.3`（`app/build.gradle.kts:70-71`）。
- 其他组件由 Manifest 侧挂：`RecordService`（录音）、`FileProvider`（导出）。

## 关键数据结构

- `object Routes`（`AppNav.kt:10-17`）：`HOME="home"`、`RECORD="record"`、`TEXT_INPUT="textinput"`、`SETTINGS="settings"`、`DETAIL="detail/{noteId}"`（模板）+ `detail(noteId: Long)` 构造器（`AppNav.kt:16`）。模板与实际参数都用字符串，`noteId` 类型是 `Long`，出参时再 `toLongOrNull()`（`AppNav.kt:51`）。
- `App.companion.instance`（`App.kt:14`，可空私有）＋ `get()`（`App.kt:15`，`!!` 断言）：进程内手工单例，没有 DI 框架。

## 已知坑与约束

1. `App.get()` 是 `instance!!`（`App.kt:15`），删掉 Manifest 的 `android:name=".App"`（`AndroidManifest.xml:21`）会在任何 ViewModel 构造时抛 NPE，与索引 README「坑」清单一致。
2. **启动顺序耦合**：`resumeStuck()` 在 `App.onCreate` 主线程同步发起（协程体在 `Dispatchers.Default` 上跑），首帧绘制可能与数据库初始化、半路任务查询并发；`App.database` 是 `by lazy`，首个访问者就是 `resumeStuck` 的协程（`App.kt:10`、`:22`；`pipeline/NoteProcessor.kt:91`）——若首屏 ViewModel 更早访问 `App.get().database`，建库就发生在 ViewModel 线程。Room 自身线程安全，风险仅是首帧多一次磁盘 IO（静态推断，未实测）。
3. 双主题轨道：Compose 用 `TingsiweiTheme`，窗口层用 `res/values/themes.xml` 里 parent 为 `android:Theme.Material.Light.NoActionBar` 的 `Theme.Tingsiwei`（`AndroidManifest.xml:27`）——它是**固定 Light**，深色模式下冷启动瞬间仍是浅色底。
4. `Theme.kt` 只有 `TingsiweiTheme` 一个文件（`ui/theme/` 目录下无 Color/Type/Shape 定义），`Theme.kt:19-23` 在非 Android 12+ 设备上直接用 Material3 默认 `darkColorScheme()`/`lightColorScheme()`，项目没有自定义色板；minSdk=26（`app/build.gradle.kts:17`）意味着 8.0~11 一律走默认色。
5. `noteId` 解析失败静默降级为 `0L`（`AppNav.kt:51`），`DetailViewModel` 对 `noteId <= 0L` 返回 `flowOf(null)`/`flowOf(emptyList())`（`DetailScreen.kt:454-457`）：页面不崩但呈现空白，没有兜底回首页。
6. `MainActivity` 用 `configChanges` 吞掉旋转/键盘/尺寸变化（`AndroidManifest.xml:33`）以避免重建，窗口输入靠 `windowSoftInputMode="adjustResize"`（`AndroidManifest.xml:32`）；副作用是 Activity 级状态长期存活。
7. 导航里 `popUpTo(Routes.HOME)` 只用在录音/文字保存后的跳详情（`AppNav.kt:37,45`），`RECORD`/`TEXT_INPUT` 自身没有 `launchSingleTop`，重复点击入口理论上可叠栈。
8. `allowBackup="true"`（`AndroidManifest.xml:22`）且未提供 `fullBackupContent`/`dataExtractionRules`（`app/src/main/res/xml/` 下只有 `file_paths.xml`），意味着 DataStore 里的设置项（含 `llm_key` 与 2026-10-05 新增的 `github_token`，见数据层模块总览）会被系统自动备份带走。本文档只描述这一事实，不涉及任何取值。
9. `usesCleartextTraffic="true"`（`AndroidManifest.xml:26`）是**应用级**放开明文，不只作用于 LLM 地址，WebView 与模型下载同样受影响（模型下载实际走 https，`app/src/main/java/com/tingsiwei/app/transcribe/ModelManager.kt:19-22`）。
10. `POST_NOTIFICATIONS` 只在点录音按钮时才申请（`RecordScreen.kt:127-128`），没有启动时申请；Android 13+ 用户若不授权，前台服务能起但通知不可见。
11. `FileProvider` 的 authority 在两侧手工拼：Manifest 用 `${applicationId}`（`AndroidManifest.xml:47`），代码用 `context.packageName`（`Exporter.kt:73`）或写死字面量 `"com.tingsiwei.app.fileprovider"`（`data/update/UpdateInstaller.kt:19`）。当前 `namespace` 与 `applicationId` 同为 `com.tingsiwei.app`（`app/build.gradle.kts:21,25`）所以一致；一旦加 `applicationIdSuffix`（如 debug）就会两边不一致导致分享/安装崩溃。
12. **`cleanupLegacyTts` 每次启动都跑**（`App.kt:24`；`ModelManager.kt:534-536`）：没有"已清理过"的标记，裸线程每次冷启动都 `deleteRecursively` 一次不存在的目录——幂等无害，但意味着这条清理逻辑永远删不掉（删掉后用户重装旧版本会重新产生目录，也能被再次清掉）。
13. **签名凭据外置的边界（2026-10-05 更新）**：本机钥匙仍是 `tingsiwei-release.jks` + `keystore.properties`（都 gitignore）。`keystore.properties` 缺失时 `storePassword`/`keyPassword` 取空串、`keyAlias` 兜底 `"tingsiwei"`（`app/build.gradle.kts:47-49`）；release 必挂这把签名（`:55`），**debug 仅在 `hasKeystore`（jks 存在且口令非空，`:41-42`）时挂同一把（`:58-61`），否则回落默认 debug 钥匙**——空口令的 release 配置不会被 debug 引用，全新克隆也能 build debug。CI 不读仓库文件：由 workflow 从 Actions Secrets 还原这两个文件后构建（见应用自更新总览坑 2：钥匙丢失=无法给已装用户发可覆盖的更新包）。
14. **索引 README 与本模块的现状**：README「入口与导航」行（现行 README 第 11 行）已列全 `App.kt`、`MainActivity.kt`、`ui/AppNav.kt`、`ui/theme/Theme.kt` 与 Manifest，5 个路由描述与 `AppNav.kt:8-15` 一致（2026-09-20 旧坑「缺 App.kt/Theme.kt」已解决）；README「录音服务」行（第 25 行）也已列全 3 个 record 文件。旧差异「README 构建说明仍指 `E:\engine\tingsiwei` 与 Gradle 8.9、单测数字未更新」**已于 2026-10-04 修正**：README 现文写真实位置 `C:\AIWorkSpace\tingsiwei-src`、Gradle wrapper 8.9（`distributionUrl` 走腾讯云镜像）、单测 167 例/15 文件/16 类——本坑销案，留此记录防止再漂。
