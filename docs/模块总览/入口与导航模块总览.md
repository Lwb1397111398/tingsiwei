# 入口与导航模块总览

## 模块职责

负责应用进程与界面的启动骨架：`App` 提供全局数据层单例并在启动时拉起后台续跑与旧模型清理，`MainActivity` 挂载 Compose，`AppNav` 注册并路由 5 个页面，`Theme.kt` 决定配色，`AndroidManifest.xml` 声明权限、TTS 引擎可见性、前台服务与 FileProvider。

## 运作流程

**从哪来**：系统按 `AndroidManifest.xml:19` 的 `android:name=".App"` 实例化 `App`，`App.onCreate`（`App.kt:18-25`）在把自己写进 `companion` 的 `instance`（`:20`）之后做两件 v1.5.0 新增的启动事务：

1. `NoteProcessor.resumeStuck()`（`App.kt:22`）——查 Room 里所有 `TRANSCRIBING`/`GENERATING` 状态的半路笔记并逐条拉起（实现见笔记处理宿主模块总览；`pipeline/NoteProcessor.kt:89-104`）。这条协程会触发 `App.database` 的 `by lazy` 初始化（`App.kt:10`），即**启动瞬间就有一次数据库创建与查询**（旧版「启动瞬间不发生任何磁盘 IO」的说法自 v1.5.0 起不再成立；`App.settings`（`:11`）仍是首次使用才建）。
2. 裸线程 `Thread { ModelManager.cleanupLegacyTts(this) }.start()`（`App.kt:24`）——后台删掉已被 kokoro 替代的旧 vits-melo 朗读模型目录 `filesDir/tts/melo-zh-en`（`transcribe/ModelManager.kt:534-536`；「约 190MB」出自 `App.kt:23` 的注释声明，`ModelManager` 侧注释未写数字；该体积未入库无法实测，见模型下载模块总览）。刻意不起协程而用裸线程：它必须不依赖任何协程基础设施、与进程共存亡。

LAUNCHER 意图（`AndroidManifest.xml:32-35`）拉起 `MainActivity`（`AndroidManifest.xml:27`）。

**怎么处理**：`MainActivity.kt:13` 先 `enableEdgeToEdge()`，再 `setContent { TingsiweiTheme { AppNav() } }`（`MainActivity.kt:14-18`）。`TingsiweiTheme`（`Theme.kt:14-25`）按 `Build.VERSION.SDK_INT >= S` 选动态取色或内置明暗方案（`Theme.kt:19-23`），最后交给 `MaterialTheme`（`Theme.kt:24`）。`AppNav`（`AppNav.kt:18-53`）建一个 `rememberNavController()`（`AppNav.kt:19`），以 `Routes.HOME` 为起点声明 `NavHost`（`AppNav.kt:20`），5 个 `composable` 分支把跳转闭包作为参数注入页面（`AppNav.kt:21-51`）——页面本身不认识 NavController，全部靠回调。`detail/{noteId}` 的参数从字符串解析，失败退化成 `0L`（`AppNav.kt:46`）。

**产出什么**：产出「路由字符串 → 页面 composable」的映射表和两个进程级单例（`App.database`、`App.settings`），不产出任何持久化数据；启动期的两张工单（续跑半路任务、清理旧朗读模型）分别派给笔记处理宿主与模型下载模块执行。

**影响谁**：所有页面与 ViewModel 都通过 `App.get()` 拿数据层（现行 28 处调用，分布见「对外接口」表），一旦 `App` 没注册或没跑到 `onCreate`，`App.kt:15` 的 `instance!!` 直接 NPE，ViewModel 构造即崩（与索引 README「坑」清单第 2 条一致）。反向引用也有：`RecordService` 的通知点击意图指向 `MainActivity`（`RecordService.kt:14`、`RecordService.kt:50-53`），录音通知的「完成」按钮指向 `.record.RecordService`（`AndroidManifest.xml:38-41`、`RecordService.kt:54-58`）。

### Manifest 四件事逐条

- **权限**（`AndroidManifest.xml:4-8`）：`INTERNET`（LLM 接口与模型下载）、`RECORD_AUDIO`、`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_MICROPHONE`、`POST_NOTIFICATIONS`。运行时只主动申请两个：录音按钮里申请 `RECORD_AUDIO`，Android 13+ 追加 `POST_NOTIFICATIONS`（`app/src/main/java/com/tingsiwei/app/ui/RecordScreen.kt:120-131`）。另有 `android:usesCleartextTraffic="true"`（`AndroidManifest.xml:24`）放开明文 HTTP，供自建/内网 LLM 地址使用。
- **TTS 引擎可见性（v1.5.0 新增）**（`AndroidManifest.xml:10-16`）：`<queries>` 声明一个 `android.intent.action.TTS_SERVICE` intent——Android 11+ 包可见性过滤下，没有这段 `packageManager.queryIntentServices` 查不到系统 TTS 引擎，TtsPlayer 的「系统引擎预检」会永远判"没有引擎"（消费方见 TTS朗读模块总览的 `hasSystemEngine()`）。
- **前台服务**（`AndroidManifest.xml:38-41`）：`.record.RecordService`，`exported="false"`，`foregroundServiceType="microphone"`。`RecordService.kt:35-47` 在 `onStartCommand` 里 `startForeground`，Android 11+ 显式传 `FOREGROUND_SERVICE_TYPE_MICROPHONE`（`RecordService.kt:37-41`），返回 `START_NOT_STICKY`（`RecordService.kt:46`）；启动/停止由 `RecordService.start/stop` 封装（`RecordService.kt:77-83`），调用点在 `RecordSession.kt:76` 与 `RecordSession.kt:169`。
- **FileProvider**（`AndroidManifest.xml:43-51`）：用 androidx 内置 `FileProvider`，authority 为 `${applicationId}.fileprovider`，`exported="false"` + `grantUriPermissions="true"`，路径表 `@xml/file_paths` 只开放 `cache/shared/`（`file_paths.xml:3`）与 `files/exports/`（`file_paths.xml:4`）。唯一使用方是导出模块：`Exporter.kt:73` 以 `"${context.packageName}.fileprovider"` 拼出同一个 authority 分享 Markdown/PNG。

## 依赖的上游模块

本模块是最顶层，没有业务上游依赖；它依赖的是**下游**：

- 数据层：`App.kt:4-5` 直接 import `data.db.AppDatabase` 与 `data.SettingsRepository`。
- 任务宿主与模型下载：`App.kt:6-7` import `pipeline.NoteProcessor`（启动续跑，`:22`）与 `transcribe.ModelManager`（启动清理，`:24`）。
- UI 五个页面：`AppNav.kt:22,30,38,47,50` 分别调 `HomeScreen`、`RecordScreen`、`TextInputScreen`、`DetailScreen`、`SettingsScreen`。
- 资源：`androidx.compose.material3`、`androidx.navigation:navigation-compose:2.8.5`、`androidx.activity:activity-compose:1.9.3`（`app/build.gradle.kts:70-71`）。
- 其他组件由 Manifest 侧挂：`RecordService`（录音）、`FileProvider`（导出）。

## 关键数据结构

- `object Routes`（`AppNav.kt:8-15`）：`HOME="home"`、`RECORD="record"`、`TEXT_INPUT="textinput"`、`SETTINGS="settings"`、`DETAIL="detail/{noteId}"`（模板）+ `detail(noteId: Long)` 构造器（`AppNav.kt:14`）。模板与实际参数都用字符串，`noteId` 类型是 `Long`，出参时再 `toLongOrNull()`（`AppNav.kt:46`）。
- `App.companion.instance`（`App.kt:14`，可空私有）＋ `get()`（`App.kt:15`，`!!` 断言）：进程内手工单例，没有 DI 框架。
- `TingsiweiTheme(darkTheme, content)`（`Theme.kt:14-17`）：`darkTheme` 默认取 `isSystemInDarkTheme()`。
- 除此之外无独立数据结构——导航状态全部封装在 `rememberNavController()`（`AppNav.kt:19`）内部。

## 已知坑与约束

1. `App.get()` 是 `instance!!`（`App.kt:15`），删掉 Manifest 的 `android:name=".App"`（`AndroidManifest.xml:19`）会在任何 ViewModel 构造时抛 NPE，与索引 README「坑」清单一致。
2. **启动顺序耦合**：`resumeStuck()` 在 `App.onCreate` 主线程同步发起（协程体在 `Dispatchers.Default` 上跑），首帧绘制可能与数据库初始化、半路任务查询并发；`App.database` 是 `by lazy`，首个访问者就是 `resumeStuck` 的协程（`App.kt:10`、`:22`；`pipeline/NoteProcessor.kt:91`）——若首屏 ViewModel 更早访问 `App.get().database`，建库就发生在 ViewModel 线程。Room 自身线程安全，风险仅是首帧多一次磁盘 IO（静态推断，未实测）。
3. 双主题轨道：Compose 用 `TingsiweiTheme`，窗口层用 `res/values/themes.xml` 里 parent 为 `android:Theme.Material.Light.NoActionBar` 的 `Theme.Tingsiwei`（`AndroidManifest.xml:25`）——它是**固定 Light**，深色模式下冷启动瞬间仍是浅色底。
4. `Theme.kt` 只有 `TingsiweiTheme` 一个文件（`ui/theme/` 目录下无 Color/Type/Shape 定义），`Theme.kt:19-23` 在非 Android 12+ 设备上直接用 Material3 默认 `darkColorScheme()`/`lightColorScheme()`，项目没有自定义色板；minSdk=26（`app/build.gradle.kts:17`）意味着 8.0~11 一律走默认色。
5. `noteId` 解析失败静默降级为 `0L`（`AppNav.kt:46`），`DetailViewModel` 对 `noteId <= 0L` 返回 `flowOf(null)`/`flowOf(emptyList())`（`DetailScreen.kt:454-457`）：页面不崩但呈现空白，没有兜底回首页。
6. `MainActivity` 用 `configChanges` 吞掉旋转/键盘/尺寸变化（`AndroidManifest.xml:31`）以避免重建，窗口输入靠 `windowSoftInputMode="adjustResize"`（`AndroidManifest.xml:30`）；副作用是 Activity 级状态长期存活。
7. 导航里 `popUpTo(Routes.HOME)` 只用在录音/文字保存后的跳详情（`AppNav.kt:32,40`），`RECORD`/`TEXT_INPUT` 自身没有 `launchSingleTop`，重复点击入口理论上可叠栈。
8. `allowBackup="true"`（`AndroidManifest.xml:20`）且未提供 `fullBackupContent`/`dataExtractionRules`（`app/src/main/res/xml/` 下只有 `file_paths.xml`），意味着 DataStore 里的设置项（含 `llm_key`，见数据层模块总览）会被系统自动备份带走。本文档只描述这一事实，不涉及任何取值。
9. `usesCleartextTraffic="true"`（`AndroidManifest.xml:24`）是**应用级**放开明文，不只作用于 LLM 地址，WebView 与模型下载同样受影响（模型下载实际走 https，`app/src/main/java/com/tingsiwei/app/transcribe/ModelManager.kt:19-22`）。
10. `POST_NOTIFICATIONS` 只在点录音按钮时才申请（`RecordScreen.kt:127-128`），没有启动时申请；Android 13+ 用户若不授权，前台服务能起但通知不可见。
11. `FileProvider` 的 authority 在两侧手工拼：Manifest 用 `${applicationId}`（`AndroidManifest.xml:45`），代码用 `context.packageName`（`Exporter.kt:73`）。当前 `namespace` 与 `applicationId` 同为 `com.tingsiwei.app`（`app/build.gradle.kts:12,16`）所以一致；一旦加 `applicationIdSuffix`（如 debug）就会两边不一致导致分享崩溃。
12. **`cleanupLegacyTts` 每次启动都跑**（`App.kt:24`；`ModelManager.kt:534-536`）：没有"已清理过"的标记，裸线程每次冷启动都 `deleteRecursively` 一次不存在的目录——幂等无害，但意味着这条清理逻辑永远删不掉（删掉后用户重装旧版本会重新产生目录，也能被再次清掉）。
13. **签名凭据外置的边界**：`keystore.properties` 缺失时 `storePassword`/`keyPassword` 取空字符串、`keyAlias` 兜底为 `"tingsiwei"`（`app/build.gradle.kts:35-37`），debug 构建不受影响（debug 用默认 debug key），release 打包会因空密码失败——只在发版机上需要该文件；`tingsiwei-release.jks` 不入库，换机器构建 release 必须先补这两个文件。
14. **索引 README 与本模块的现状**：README「入口与导航」行（现行 README 第 11 行）已列全 `App.kt`、`MainActivity.kt`、`ui/AppNav.kt`、`ui/theme/Theme.kt` 与 Manifest，5 个路由描述与 `AppNav.kt:8-15` 一致（2026-09-20 旧坑「缺 App.kt/Theme.kt」已解决）；README「录音服务」行（第 25 行）也已列全 3 个 record 文件。旧差异「README 构建说明仍指 `E:\engine\tingsiwei` 与 Gradle 8.9、单测数字未更新」**已于 2026-10-04 修正**：README 现文写真实位置 `C:\AIWorkSpace\tingsiwei-src`、Gradle wrapper 8.9（`distributionUrl` 走腾讯云镜像）、单测 167 例/15 文件/16 类——本坑销案，留此记录防止再漂。
