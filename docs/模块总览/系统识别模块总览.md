# 系统识别模块总览

## 模块职责

用安卓自带的 `SpeechRecognizer` 在录音**进行中**做实时识别（边录边转），识别会话被系统中断时自动重建续接，把最终文本一段段累积回调给录音会话。

## 运作流程

**从哪来（数据源是重点）**：音频**不来自 `Recorder`**。`SystemSpeechRecognizer.startOnce()` 里 `SpeechRecognizer.createSpeechRecognizer(context)`（`transcribe/SystemSpeechRecognizer.kt:47`）+ `r.startListening(intent)`（`:94`）会**自行打开麦克风**采集，`MediaRecorder` 与它并行工作（`record/RecordSession.kt:67-68` 先起录音，`:76` 再起识别）。也就是说：本模块拿到的是系统识别服务自己的那一路音频，中间没有 PCM 交接，也没有音频文件参与。

**怎么处理**：
1. `RecordSession.start()` 里，只有当转写方式为 `SYSTEM` 时才调用 `startRecognition()`（`record/RecordSession.kt:76`）；`startRecognition()` 会先 `sysRecognizer?.stop()` 再 `SystemSpeechRecognizer(App.get()).start(recognizerCallback)`（`record/RecordSession.kt:153-158`）。
2. `start()` 先 `stop()` 自清，再 `SpeechRecognizer.isRecognitionAvailable(context)` 检查设备有无识别服务，没有就直接回调错误"这台手机没有可用的语音识别服务，请到设置里改用离线识别"（`transcribe/SystemSpeechRecognizer.kt:33-43`）。
3. `startOnce()` 组装意图：`ACTION_RECOGNIZE_SPEECH` + `LANGUAGE_MODEL_FREE_FORM` + `Locale.CHINA` + `EXTRA_PARTIAL_RESULTS = true` + `EXTRA_MAX_RESULTS = 1`（`transcribe/SystemSpeechRecognizer.kt:49-54`），挂上 `RecognitionListener`（`:55-93`）。
4. 回调上行：`onPartialResults` → `cb.onPartial(text)`（`:85-90`）；`onResults` → 取 `RESULTS_RECOGNITION` 首条非空 → `cb.onSegment(text)`（`:75-83`）；`onError` → 走重启或放弃（`:62-73`）。`RecordSession` 的实现是：`onSegment` 把文本追加到 `finalText`（`finalText + text + "\n"` 后 `trim()`）并清空 `partialText`，`onPartial` 只覆盖 `partialText`，`onError` 写 `error`（`record/RecordSession.kt:44-57`）。
5. **会话中断自动重启续接**：`onResults` 尾部 `r.destroy(); if (running) startOnce()`（`transcribe/SystemSpeechRecognizer.kt:81-82`）；`onError` 同样 `errorCount++` → `r.destroy()` → `startOnce()`（`:65-72`）。只有成功出一段结果才把 `errorCount` 归零（`:77`）；累计超过 30 次就 `running = false` 并回调"语音识别多次失败，请改用离线识别"（`:66-70`）。`running` 标志是重启的总闸，`stop()` 置 false 后所有回调直接 return（`:63`、`:76`、`:86`、`:97-105`）。
6. 生命周期收尾：`pause()` 时 `sysRecognizer?.stop()`（`record/RecordSession.kt:96`），`resume()` 时重新启动一次全新识别（`:103`），`stopAndSave()` 与 `cancelIfAny()` 里先 `stop()` 再置空（`:110-111`、`:147-148`）。

**产出什么**：两类文本流——实时 `partialText`（正在说）与累积 `finalText`（已定稿的句子拼接）。停止录音时，若 `finalText` 非空，它被**直接当作笔记正文**写入 `NoteEntity.content`，状态记 `DRAFT`（`record/RecordSession.kt:121-135`），从而跳过离线转写；为空则状态 `TRANSCRIBING`，交给详情页的离线链路兜底。

**影响谁**：录音页显示识别方式与实时字幕（`ui/RecordScreen.kt:102`、`:165-176`）；Room 笔记正文与状态（`record/RecordSession.kt:125-131`）；因此影响 LLM 生成入口（详情页 `DRAFT → generateInternal()`，`ui/DetailScreen.kt:481-482`）；错误文案影响用户去设置页切换模式。

**与离线模式的互斥关系（结论：不互斥，是"优先 + 回落"）**：
- 分流只发生在录音侧：`record/RecordSession.kt:76`（开录时是否启动系统识别）、`:103`（恢复时重启）、`:125`（保存时用不用系统文本）。
- 离线侧完全没有模式分支：`transcribe/Transcriber.kt` 只有 `transcribeOffline` 一条路（`transcribe/Transcriber.kt:16-52`）。
- 回落在详情页：系统文本为空 → `status = TRANSCRIBING` → `ui/DetailScreen.kt:479` 自动跑离线转写；反过来离线失败/无内容时错误提示会建议"到设置里改用「手机自带识别」重新录一次"（`ui/DetailScreen.kt:522`）。两条链路共用同一条笔记、同一个 m4a 文件，互不覆盖对方的产物。

## 对外接口 / 被谁调用

- `SystemSpeechRecognizer(context)`（`transcribe/SystemSpeechRecognizer.kt:16`）：`start(cb: Callback)`（`:33`）、`stop()`（`:97`）、`isRunning`（`:31`）。
- `interface Callback { onSegment(text); onPartial(text); onError(message) }`（`transcribe/SystemSpeechRecognizer.kt:18-24`）——唯一实现是 `RecordSession` 里的匿名对象（`record/RecordSession.kt:44-57`）。
- 生产调用方**只有 `RecordSession`** 一个：`record/RecordSession.kt:8`（import）、`:41`（持有）、`:96`/`:110`/`:147`（stop）、`:153-158`（创建并 start）。`Transcriber`/`AudioDecode`/详情页都不碰这个类。
- 不被 `App`、Room、DataStore 直接依赖；`Context` 由 `App.get()` 传入（`record/RecordSession.kt:155`）。

## 依赖的上游模块

- 平台框架：`android.speech.SpeechRecognizer` / `RecognitionListener` / `RecognizerIntent`、`android.content.Intent`、`android.os.Bundle`、`java.util.Locale`（`transcribe/SystemSpeechRecognizer.kt:3-9`）。
- **设备侧外部依赖**：手机必须装有可用的语音识别服务，`SpeechRecognizer.isRecognitionAvailable()` 判定（`:35-38`）；识别是否联网、是否上传音频由厂商实现决定，本模块不控制。
- `record/RecordSession.kt`（宿主：状态流、生命周期编排、模式判断）→ 依赖 `App`（Context）、`data/SettingsRepository.kt` 的 `TranscribeMode`（`record/RecordSession.kt:4`、`:76`）。
- `data/db`：识别文本经宿主写入 `NoteEntity.content`（`record/RecordSession.kt:126-136`）。
- 与 `record/Recorder.kt` 是**并行占麦**关系，不是上下游数据关系（`record/RecordSession.kt:67-76`）。

## 关键数据结构

- `Callback` 三方法语义（`transcribe/SystemSpeechRecognizer.kt:18-24`）：`onSegment` = 一段话的最终结果（可持久化），`onPartial` = 正在说的临时结果（只上屏），`onError` = 面向用户的中文提示。
- 内部状态四件套：`recognizer`（当前实例，重启即换）、`callback`、`running`（总闸）、`errorCount`（连续失败计数）（`transcribe/SystemSpeechRecognizer.kt:26-29`）。
- 识别意图参数（`transcribe/SystemSpeechRecognizer.kt:49-54`）：`FREE_FORM`（自由说，不约束语法）、语言 `zh-CN`（`Locale.CHINA.toString()`）、`EXTRA_PARTIAL_RESULTS = true`、`EXTRA_MAX_RESULTS = 1`（只取第一条候选）。
- 文本累积结构：`finalText: MutableStateFlow<String>`，追加规则 `(finalText.value + text + "\n").trim()`（`record/RecordSession.kt:32`、`:46`）——**段间固定插换行**，`partialText` 是独立的单值流（`:31`、`:51`），页面显示时再拼成 `finalText + "\n" + partialText`（`ui/RecordScreen.kt:167`）。
- 失败上限常量：`errorCount > 30`（`transcribe/SystemSpeechRecognizer.kt:66`，硬编码在方法内，无 companion 常量）。
- 错误码语义按注释"无语音输入(6/7)、超时(1)等都直接重启续录"（`transcribe/SystemSpeechRecognizer.kt:64`）——代码不对错误码分支，一律走重启。

## 已知坑与约束

- **README 只写了功能、没写代价**：索引 README 第 21 行"边录边转，会话中断自动重启续接"与代码一致，但没提三件实际影响体验的事——① 每段结束/每次出错都 `destroy()` + 重新 `createSpeechRecognizer()`（`transcribe/SystemSpeechRecognizer.kt:71-72`、`:81-82`、`:47`），重启有几数百毫秒空窗，跨界的那句话会整段丢；② 连续失败 30 次直接停用本次边录边转（`:66-70`）；③ 块/段之间没有重叠兜底。
- **与 `MediaRecorder` 并发占麦（未验证）**：`record/RecordSession.kt:67-68` 起录音、`:76` 起识别，二者同时打开麦克风；Android 10+ 通常会把第二路录音静音（只有特权场景才允许并发采集），因此"边录边转"能否真拿到音频高度依赖厂商实现。工程侧没有针对这一项的自动化用例（`docs/迭代计划/用户实测清单-v1.md` 也未见对应条目）→ **本条为疑点，需真机验证**。
- **创建线程不一致（未验证风险）**：`startRecognition()` 有两条来路——`RecordSession.start()` 里在 `scope.launch { … }` 即 `Dispatchers.Default` 线程执行（`record/RecordSession.kt:61`、`:76`、`:153-157`），`resume()` 里则是调用方线程（UI 主线程，`record/RecordSession.kt:100-105`）。`SpeechRecognizer` 历史上要求在有 Looper 的线程创建、回调也分发到该线程，代码没有显式 `withContext(Dispatchers.Main)`；实测是否崩/是否丢回调未在仓库内得到验证 → **列为待确认**。
- **停止时尾句丢失**：`stopAndSave()` 顺序是先 `sysRecognizer?.stop()` 再 `rec.stop()`（`record/RecordSession.kt:110-113`），`stop()` 里 `stopListening()` + `destroy()`（`transcribe/SystemSpeechRecognizer.kt:97-105`）之后正在出结果的最后一句 `onResults` 可能永远不来 → 笔记正文少最后一句。
- **`partialText` 会滞留**：`partialText` 只在 `onSegment` 时清空（`record/RecordSession.kt:46-47`）；`pause()` 只 `stop()` 识别（`:96`）不清文本，暂停后屏幕上仍挂着最后一次 partial 文本，直到下一段定稿才被替换。
- **暂停=丢弃识别上下文**：`pause()` 停识别、`resume()` 全新 `startRecognition()`（`record/RecordSession.kt:96`、`:103`），不会恢复被打断的那句；若机型不支持 `MediaRecorder.pause()`，`Recorder` 静默不暂停而 UI 已显示暂停（`record/Recorder.kt:65-70` 与 `record/RecordSession.kt:95-98`），识别却是真的停了。
- **长静音会烧掉重试预算**：安静环境下 `onError` 会连续累计（超时/无语音输入都算，`transcribe/SystemSpeechRecognizer.kt:62-70`），30 次后本条录音的边录边转彻底停用，只留一条 `error` 文案，且**同一会话内不会再自愈**（`running = false` 后 `startOnce` 不再被调）。
- **语言与结果数不可配**：只 `Locale.CHINA`（`:51`）、只取第一条候选（`:78-80`、`:87-89`），不读置信度、不做候选择优；设置页无开关。
- **权限要求同录音**：需要 `RECORD_AUDIO`（`AndroidManifest.xml:5`），本模块自身不做运行时申请，依赖录音页已申请（`ui/RecordScreen.kt:120-131`）；不额外需要前台服务权限，但录音期间由 `RecordService` 保活间接受益。
- **无单测**：依赖 Android framework 与厂商服务，`app/src/test` 下无对应测试文件（只有 6 个纯 JVM 测试），行为只能真机冒烟。
- **归属未在索引里点明**：README 第 21 行把这条链路只写成 `transcribe/SystemSpeechRecognizer.kt` 一个文件，实际的回调落地、模式分流与生命周期都在 `record/RecordSession.kt`（`:44-57`、`:76`、`:96`、`:103`、`:110-111`、`:125`、`:153-158`），看代码时容易漏。
