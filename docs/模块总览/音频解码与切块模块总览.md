# 音频解码与切块模块总览

## 模块职责

把任意音频文件（m4a/mp3/wav…）用 `MediaCodec` 流式解码成 **16kHz 单声道 float PCM**，并按"静音中点"切成 15~30 秒的块逐块交出，保证内存峰值与音频总时长无关。

## 运作流程

**从哪来**：唯一生产调用方是离线识别门面 `Transcriber.transcribeOffline()`（`transcribe/Transcriber.kt:32-46`），它把 `NoteEntity.audioPath`（录音或导入的文件路径）传给 `AudioDecode.forEachChunk`。

**怎么处理**（`transcribe/AudioDecode.kt:17-112`）：
1. `MediaExtractor.setDataSource(path)`，遍历轨道取第一条 MIME 以 `audio/` 开头的轨道，没有就 `require` 抛错（`:27-41`）；读出源采样率（缺省按 44100）、声道数（缺省 1）、时长（缺省 0，`:44-46`）。
2. 换算出**源采样率口径**的判定阈值：`target = srcRate * 15`、`max = (srcRate * 30).coerceAtLeast(target + 1)`、`minSilence = srcRate * 220 / 1000`、`thresh = 600`，并 `PcmBuffer(srcRate, max + srcRate)` + `SpeechScanner(target, max, minSilence, thresh)`（`:48-51`）。
3. `MediaCodec.createDecoderByType(mime)` → `configure` → `start`，跑同步输入/输出循环：`extractor.readSampleData` 喂入、`dequeueOutputBuffer` 取 PCM（`s16le`，`ByteOrder.LITTLE_ENDIAN` + `asShortBuffer`）（`:53-85`）。
4. 每取到一个输出缓冲就 `buffer.append(shortBuf, remaining / channels, channels)` 累积（多声道在缓冲内部按均值下混为单声道，`transcribe/PcmBuffer.kt:28-47`），并按 `presentationTimeUs / durationUs` 回调进度（`transcribe/AudioDecode.kt:87-89`）。
5. **切块决策**：`scanner.pickCut(buffer.samples(), buffer.size)`（`transcribe/AudioDecode.kt:90`）——只在"当前已累积的缓冲区"里找**足够长静音的中点**：帧平均绝对能量 `< thresh` 记为静音帧，连续静音长度 `>= minSilence` 且中点 `>= searchFrom` 才返回中点；否则继续攒；攒到硬上限 `max` 时退而求其次在更早的静音（不早于 `min = target/2`）切，找不到静音就返回 `max` 硬切（`transcribe/SpeechCut.kt:32-66`）。返回 0 表示"还不出块"。
6. 命中切点就 `onChunk(buffer.takeResampled(cut))`：取走前 cut 个源样本、重采样成 16k `FloatArray` 交出，剩余样本 `arraycopy` 前移继续攒（`transcribe/AudioDecode.kt:91`、`transcribe/PcmBuffer.kt:50-58`）；`SpeechScanner` 内部同时 `reset()`（`transcribe/SpeechCut.kt:56`）。
7. 解码结束（EOS 或被取消）后，缓冲区若有剩余样本再出**最后一块**（`transcribe/AudioDecode.kt:95`）。

**产出什么**：一串 `FloatArray`（16k 单声道、幅值归一化到 ±1），外加 0..1 的进度浮点；不写盘、不落库。

**影响谁**：块直接喂 `SherpaTranscriber.recognizeChunk`，块文本由上层拼接成整篇转写（`transcribe/Transcriber.kt:39-46`）；进度百分比又回灌到详情页"已完成 N%，已识别 M 字"的文案（`transcribe/Transcriber.kt:35-38`）。切得不好（把句子劈开）会直接体现为识别丢字，因此本模块是长录音质量的第一道闸门。

**可测接缝**（纯 JVM，不需要设备、不需要模型）：
- `SpeechScanner.pickCut(mono: ShortArray, len: Int): Int` —— 入参是普通数组和长度，`SpeechCutTest` 直接构造它（`app/src/test/java/com/tingsiwei/app/SpeechCutTest.kt:3`、`:23-24`）。
- `PcmBuffer.append/takeResampled/takeAllResampled/highWater` —— 只用 `java.nio.ShortBuffer`，`PcmBufferTest` 灌 60 秒数据断言峰值有界（`app/src/test/java/com/tingsiwei/app/PcmBufferTest.kt:70-84`）。
- `AudioDecode` 本身依赖 `MediaExtractor`/`MediaCodec`，无单测（见已知坑）。

- `AudioDecode.forEachChunk(path, targetSeconds = 15, maxSeconds = 30, silenceMs = 220, silenceThresh = 600, isCancelled = { false }, onProgress = {}, onChunk)`（`transcribe/AudioDecode.kt:17-26`）——模块唯一公开函数（`object` 单例）。被 `transcribe/Transcriber.kt:32` 调用，调用处**只传 path + isCancelled + onProgress + onChunk，其余参数全用默认值**。
- `SpeechScanner(target, max, minSilence, thresh, min = maxOf(1, target / 2))`（`transcribe/SpeechCut.kt:13-20`）：`pickCut(mono, len): Int`（`:32`）、`reset()`（`:26`）、`companion object { const val FrameSamples = 160 }`（`:68-71`）。生产调用点只有 `transcribe/AudioDecode.kt:51`、`:90`；测试调用点 `app/src/test/java/com/tingsiwei/app/SpeechCutTest.kt`（全文）。
- `PcmBuffer(srcRate, initialCapacity)`（`transcribe/PcmBuffer.kt:9-25`）：`samples()`、`size`、`highWater`、`ensureRoom()`、`append(ShortBuffer, frameCount, channels)`、`takeResampled(count): FloatArray`、`takeAllResampled(): FloatArray`、`companion object { const val TargetRate = 16000 }`（`:83-85`）。生产调用点只有 `transcribe/AudioDecode.kt:50`、`:84`、`:90-91`、`:95`；测试 `app/src/test/java/com/tingsiwei/app/PcmBufferTest.kt`。
- 本模块不反向依赖任何业务模块，可整体替换（例如换成 MediaCodec 异步模式或外部解码库）而不影响 `record/`、`llm/`。

## 关键数据结构

索引 README 第 18 行的三个数值在代码里都能对上，但**常量名与归属类**不同：

| 语义 | README 说法 | 代码实际值 / 常量名 | 证据 |
| --- | --- | --- | --- |
| 目标块长 | 15s | `targetSeconds: Int = 15` → `val target = srcRate * targetSeconds` | `transcribe/AudioDecode.kt:19`、`:48` |
| 硬上限 | 30s | `maxSeconds: Int = 30` → `val max = (srcRate * maxSeconds).coerceAtLeast(target + 1)` | `transcribe/AudioDecode.kt:20`、`:49` |
| 静音判据 | 220ms | `silenceMs: Int = 220` → 构造 `SpeechScanner` 的 `minSilence = srcRate * silenceMs / 1000` | `transcribe/AudioDecode.kt:21`、`:51`；字段 `transcribe/SpeechCut.kt:16` |
| 静音能量阈值 | （README 未给数值） | `silenceThresh: Int = 600` → `SpeechScanner.thresh`，判据 `sum / FrameSamples < thresh` | `transcribe/AudioDecode.kt:22`、`:51`；`transcribe/SpeechCut.kt:17`、`:52` |
| 碎块下限 | （README 未提） | `min = maxOf(1, target / 2)`（默认 7.5s，仅硬上限触发后启用） | `transcribe/SpeechCut.kt:19`、`:44` |
| 判定帧长 | （README 未提） | `const val FrameSamples = 160`（16k 下 10ms/帧） | `transcribe/SpeechCut.kt:68-71` |
| 目标采样率 | 16k 单声道 PCM | `const val TargetRate = 16000`（`PcmBuffer`） | `transcribe/PcmBuffer.kt:83-85` |

- 缓冲区容量：`PcmBuffer(srcRate, max + srcRate)` ≈ **31 秒源样本**，元素是 `Short`（2 字节）→ 16k 时约 1MB、44.1k 时约 2.7MB，且**不随音频时长增长**（`transcribe/AudioDecode.kt:50`；峰值断言 `transcribe/PcmBuffer.kt:16`、测试 `app/src/test/java/com/tingsiwei/app/PcmBufferTest.kt:70-84`）。
- `SpeechScanner` 的三个内部状态：`scannedFrames`（已扫到第几帧，增量扫描的依据）、`runStart`（当前静音段起始样本下标，-1 表示非静音）、`wasForced`（上一轮是否处于硬上限口径）（`transcribe/SpeechCut.kt:22-24`）。
- `pickCut` 返回值语义：`0` = 继续攒；`>0` = 在源样本下标处出块（内部已 `reset()`，调用方前移缓冲区即可继续）（`transcribe/SpeechCut.kt:11`、`:32-66`）。
- `PcmBuffer` 对外只暴露源样本（`samples()`，`ShortArray`，长度 ≥ `size`，有效区是 `[0, size)`）；出块时才对外的类型变成 `FloatArray`（`takeResampled`，`transcribe/PcmBuffer.kt:50-58`）。
- 重采样：`srcRate == 16000` 时等长直通；否则按 `step = srcRate / 16000` 线性插值，`outLen = count * 16000 / srcRate`，归一化 `/ 32768f`（`transcribe/PcmBuffer.kt:62-81`）。
- 下混：多声道按各声道 `Short` 整数均值（`transcribe/PcmBuffer.kt:34-43`）。

## 已知坑与约束

- **README 说"纯函数"，实际是有状态类**：索引 README 第 18 行写「出块点由 `SpeechCut.pickCut`（**纯函数**）在静音中点选择」。实际代码里 `SpeechCut.kt` 文件内的类型是 `class SpeechScanner`（`transcribe/SpeechCut.kt:13`），`pickCut` 是它的成员方法且依赖 `scannedFrames`/`runStart`/`wasForced` 三个可变字段（`:22-24`），出块后靠内部 `reset()` 复位（`:26-30`、`:56`）。之所以不能写成纯函数，正是为了"每次只扫新到的帧"这个线性复杂度目标（`:38-43`、`:64`）。"纯"仅在"无 Android 依赖、可 JVM 直测"这个意义上成立。
- **README 未记的两个参数**：静音能量阈值实际是 `silenceThresh = 600`（帧内 `|sample|` 均值，量纲是 Short 满量程，`transcribe/AudioDecode.kt:22`）；另有硬上限下允许更早切的碎块下限 `min = target/2`（`transcribe/SpeechCut.kt:19`）。调这两个值就能整体改变出块风格，但都没有从上层暴露（`transcribe/Transcriber.kt:32` 未传参）。
- **判据是"平均绝对值"不是 RMS**：`sum / FrameSamples < thresh`（`transcribe/SpeechCut.kt:50-52`），与 `docs/迭代计划/00-迭代总计划-v3.md` 第 21 行"按 `thresh`（RMS 门限）+ `minSilenceSamples`"的措辞不一致（同文档第 15 行还写的是 `pickCut(buffer: FloatArray, …)`，实际签名是 `ShortArray` + 源采样率口径）。
- **判定用源采样率，出块才转 16k**：`target`/`max`/`minSilence` 全按 `srcRate` 折算（`transcribe/AudioDecode.kt:48-51`），而 `FrameSamples` 固定 160（`transcribe/SpeechCut.kt:70`）→ 44.1kHz 下一帧只有约 3.6ms，静音检测粒度比 16k 更细；同一段音频用不同源采样率解出来的切点不会完全一致（代码注释自己也承认这点，`transcribe/SpeechCut.kt:69-70`）。
- **一轮输出只切一块**：`if (cut > 0) onChunk(...)` 没有 `while`（`transcribe/AudioDecode.kt:90-91`）。正常情况下单个解码输出不会攒够两块，但若某次输出样本数远超 `max`，第二块要等下一轮才出。
- **进度可能全程不回调**：`onProgress` 只在 `durationUs > 0 && info.presentationTimeUs > 0` 时触发（`transcribe/AudioDecode.kt:87-89`），而 `KEY_DURATION` 缺失时按 0 处理（`:46`）→ 上层"已完成 N%"会一直显示 0%，但识别本身照常进行（进度显示与真实进度解耦）。
- **取消粒度是一个块**：`isCancelled()` 只在解码主循环条件和收尾判断里检查（`transcribe/AudioDecode.kt:61`、`:95`），块内不检查；取消时缓冲区里"还没出块"的样本被整体丢弃（`:95` 的 `!isCancelled()` 守卫），尾音不会被识别。取消由上层传入（`transcribe/Transcriber.kt:30`、`:34`）。
- **最后一块可以很短**：收尾 `takeAllResampled()` 出的是不足 `target` 的尾巴（`transcribe/AudioDecode.kt:95`、`transcribe/PcmBuffer.kt:60`），实测里也验证"剩下的不足一块"（`app/src/test/java/com/tingsiwei/app/SpeechCutTest.kt:116-138`）。
- **硬上限处可能把一句话切成两半**：找不到静音时返回 `limit` 硬切（`transcribe/SpeechCut.kt:65`），块与块之间**没有重叠兜底**，跨块的词由上层拼接时承担。
- **不支持的容器/编码直接抛**：`require(trackIndex >= 0)`（`transcribe/AudioDecode.kt:40`）、`MediaCodec.createDecoderByType`（`:53`）、`codec.configure`（`:55`）都不套 try，只有 `finally` 释放 codec 与 extractor（`:96-111`）→ 异常上抛给 `DetailViewModel` 置笔记 ERROR。
- **`append` 的隐含契约**：多声道分支用绝对索引 `src.get(idx + ch)` 读，靠调用方传对 `frameCount = remaining / channels`（`transcribe/AudioDecode.kt:84`、`transcribe/PcmBuffer.kt:36-43`）；`remaining` 不是 `channels` 整数倍时末尾残样被截断。
- **重采样是线性插值、无抗混叠滤波**（`transcribe/PcmBuffer.kt:62-81`）：44.1k→16k 属于降采样，理论上会有混叠；对识别精度影响未做量化验证。
- **扩容是全量拷贝**：`ensureRoom` 每次 `data.copyOf((size + extra) * 2)`（`transcribe/PcmBuffer.kt:21-25`），取块后 `System.arraycopy` 前移（`:55`）；因为容量有 `max + srcRate` 起步（约 31 秒）且会被排空，实际不会反复扩容，但这是 O(缓冲长度) 操作。
- **本模块没有集成测试**：`SpeechCutTest`（13 例）与 `PcmBufferTest`（9 例）与索引 README 第 41 行的数字一致，但 `AudioDecode.forEachChunk` 依赖 `MediaCodec`，纯 JVM 跑不了，仓库里没有对应的仪器化测试目录（`app/src/` 下只有 `main` 与 `test` 两个 source set），所以"解码→累积→出块"的整链路只能靠真机冒烟。
- **内存上限是硬编码在参数里的**：改 `maxSeconds` 会同时改变块长和缓冲峰值（二者由同一个 `max` 派生，`transcribe/AudioDecode.kt:49-51`），无法只调其一。
