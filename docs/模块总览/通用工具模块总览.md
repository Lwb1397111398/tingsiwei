# 通用工具模块总览

## 模块职责

`util/Formatters.kt` 是唯一的通用工具文件，提供三个纯函数式格式化器：时长（毫秒 → `mm:ss`/`h:mm:ss`）、日期时间（毫秒时间戳 → `yyyy-MM-dd HH:mm`）、文件大小（字节 → KB/MB/GB 可读串）。

## 运作流程

**从哪来**：调用方全部是 UI 层页面，输入是数据层的原始数值——`NoteEntity.createdAt`/`updatedAt`（`app/src/main/java/com/tingsiwei/app/data/db/Entities.kt:28-29`）、`durationMs`（`Entities.kt:33`）与模型下载得到的字节数（ASR 来自 `transcribe/ModelManager.kt:428-433` 的 `downloadedBytes` 与 `:593-594` 的 `totalBytes`，TTS 来自 `:545-555` 的 `ttsDownloadedBytes`）。

**怎么处理**：无状态、无 IO、无协程。`duration` 整除拆时/分/秒后按是否有小时选格式（`app/src/main/java/com/tingsiwei/app/util/Formatters.kt:9-15`）；`dateTime` 每次新建一个 `SimpleDateFormat` 再格式化（`Formatters.kt:17-18`）；`fileSize` 用 `when` 按 1024 进制阈值自高到低匹配（`Formatters.kt:20-25`）。

**产出什么**：只产出给用户看的字符串，不回写任何数据、不触发任何状态变化。

**影响谁**：首页列表（时间、时长）、录音页计时、详情页音频进度与版本时间、设置页两张模型卡片的体积文案（ASR 与 TTS）。它是显示层叶子，谁都能依赖，它不依赖任何人。

## 依赖的上游模块

无。`Formatters.kt` 的全部 import 只有 `java.text.SimpleDateFormat`、`java.util.Date`、`java.util.Locale`（`Formatters.kt:3-5`），不引用项目内任何包（`Formatters.kt:1-5`），因此可被任意模块使用，也天然适合纯 JVM 单测。

## 关键数据结构

无独立数据结构，复用调用方传入的 `Long` 原值与返回的 `String`：时长与时间戳都是 `NoteEntity` 里的 `Long` 毫秒（`data/db/Entities.kt:28-33`），字节数来自 `File.length()` 聚合（ASR `transcribe/ModelManager.kt:593-594`、TTS `:545-555`）。模块本体只是一个无字段 `object`（`Formatters.kt:7`）。

## 已知坑与约束

1. `duration` 不做负数与超 24 小时保护（`Formatters.kt:10-14`）：`ms < 0` 时整除结果为 0 或负，会输出 `-1:-1` 之类的串；小时只按 `h > 0` 分支展开（`Formatters.kt:14`），没有「天」。当前所有输入来自录音时长/播放位置（非负），实际不触发，但导入音频的时长是靠 `MediaMetadataRetriever` 元数据取的，取不到时给 0（`ui/HomeScreen.kt:310`、`:312-315`）。
2. `duration` 采用整除截断（`Formatters.kt:10`），不做四舍五入：59.9 s 显示 `00:59`，录音页与详情页的秒数可能比实际少 1 秒。
3. `dateTime` 固定 `Locale.CHINA` 与 `yyyy-MM-dd HH:mm`（`Formatters.kt:18`），不带秒、不带时区；同一分钟内的两条记录文案完全相同（版本列表相邻快照可能撞时间串），且非中文系统也强制走该格式。
4. `dateTime` 每次调用都 `new SimpleDateFormat`（`Formatters.kt:18`）：好处是天然线程安全、无共享状态；代价是列表滚动时每个可见项一次对象分配（`HomeScreen.kt:219`、`DetailScreen.kt:421` 在组合里直接调用，无 `remember`）。
5. `fileSize` 阈值是 1024 进制但单位写作 GB/MB/KB（`Formatters.kt:21-24`），与厂商十进制口径差约 7%。同一模型文件多口径并存：ASR 侧 `fileSize(237_115_547)` → `226.1 MB`，`transcribe/ModelManager.kt:25` 定义的 `MODEL_BYTES = 237_115_547L`，界面文案硬编码「约 230MB」（`ui/SettingsScreen.kt:195`、`:614`），`transcribe/SherpaTranscriber.kt:13` 注释写「约 226MB」；TTS 侧（v1.5.0 新增同类差）`fileSize(215_308_902)` → `205.3 MB`，而界面文案与 `ModelManager.kt:412` 注释都写「约 215MB」（十进制口径）。数字都指各自同一份文件，只是进制/取整口径不同，容易被误读成两个模型。
6. `fileSize` 的分支顺序不可调换（`Formatters.kt:21-24`）：阈值是「从高到低」的 `when`，写反会让 GB 区间永久不可达；`bytes` 为 0 时落到 `else` 输出 `0 B`（`Formatters.kt:24`），负数同样落 `else` 输出 `-1 B`。
7. 阈值常量 `1 shl 30`/`1 shl 20`/`1 shl 10` 是 `Int`（`Formatters.kt:21-23`），与 `Long` 比较时靠隐式提升，当前 `1 shl 30 = 1073741824` 未溢出；若将来加 TB 档写成 `1 shl 40` 会静默溢出为负，所有大文件都会掉进 TB 分支。
8. 时间格式化存在 3 处**未走本模块**的重复实现，格式各异：`record/Recorder.kt:35`（`yyyyMMdd_HHmmss`，录音文件名）、`record/RecordSession.kt:129`（`MM-dd HH:mm`，笔记标题）、`ui/HomeScreen.kt:298`（`yyyyMMdd_HHmmss`，导入文件名）。它们各自 `import java.text.SimpleDateFormat`（`Recorder.kt:8`、`RecordSession.kt:18`、`HomeScreen.kt:72`），`Formatters` 没有对应函数，改动统一格式时容易漏。
9. 该模块没有单元测试：`app/src/test/java/com/tingsiwei/app/` 下现有 15 个测试文件（v1.5.0 新增了 `ModelManagerTtsTest`、`TtsSplitTest` 等），仍没有 `FormattersTest`——虽然它是最容易测的纯函数模块。
10. **索引 README 一致性（2026-10-04 复核）**：README「模块索引」表的第 33 行已有「通用工具」行（位置 `util/Formatters.kt`，职责「时长/体积/时间等格式化，被各页面共用」），与代码现状相符；2026-09-20 版总览里「README 没有本模块行」的差异已随 README 同日重写消失。
