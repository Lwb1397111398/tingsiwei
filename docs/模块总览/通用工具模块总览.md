# 通用工具模块总览

## 模块职责

`util/Formatters.kt` 是唯一的通用工具文件，提供三个纯函数式格式化器：时长（毫秒 → `mm:ss`/`h:mm:ss`）、日期时间（毫秒时间戳 → `yyyy-MM-dd HH:mm`）、文件大小（字节 → KB/MB/GB 可读串）。

## 运作流程

**从哪来**：调用方全部是 UI 层页面，输入是数据层的原始数值——`NoteEntity.durationMs`/`updatedAt`/`createdAt`（`app/src/main/java/com/tingsiwei/app/data/db/Entities.kt:28-33`）与模型下载得到的字节数（`app/src/main/java/com/tingsiwei/app/transcribe/ModelManager.kt:36-41`、`ModelManager.kt:130-131`）。

**怎么处理**：无状态、无 IO、无协程。`duration` 整除拆时/分/秒后按是否有小时选格式（`app/src/main/java/com/tingsiwei/app/util/Formatters.kt:9-15`）；`dateTime` 每次新建一个 `SimpleDateFormat` 再格式化（`Formatters.kt:17-18`）；`fileSize` 用 `when` 按 1024 进制阈值自高到低匹配（`Formatters.kt:20-25`）。

**产出什么**：只产出给用户看的字符串，不回写任何数据、不触发任何状态变化。

**影响谁**：首页列表（时间、时长）、录音页计时、详情页音频进度与版本时间、设置页模型体积。它是显示层叶子，谁都能依赖，它不依赖任何人。

## 依赖的上游模块

无。`Formatters.kt` 的全部 import 只有 `java.text.SimpleDateFormat`、`java.util.Date`、`java.util.Locale`（`Formatters.kt:3-5`），不引用项目内任何包（`Formatters.kt:1-5`），因此可被任意模块使用，也天然适合纯 JVM 单测。

## 关键数据结构

无独立数据结构，复用调用方传入的 `Long` 原值与返回的 `String`：时长与时间戳都是 `NoteEntity` 里的 `Long` 毫秒（`data/db/Entities.kt:28-33`），字节数来自 `File.length()` 聚合（`transcribe/ModelManager.kt:130-131`）。模块本体只是一个无字段 `object`（`Formatters.kt:7`）。

## 已知坑与约束

1. `duration` 不做负数与超 24 小时保护（`Formatters.kt:10-14`）：`ms < 0` 时整除结果为 0 或负，会输出 `-1:-1` 之类的串；小时只按 `h > 0` 分支展开（`Formatters.kt:14`），没有「天」。当前所有输入来自录音时长/播放位置（非负），实际不触发，但导入音频的时长是靠 `MediaMetadataRetriever` 元数据取的，取不到时给 0（`ui/HomeScreen.kt:296-303`）。
2. `duration` 采用整除截断（`Formatters.kt:10`），不做四舍五入：59.9 s 显示 `00:59`，录音页与详情页的秒数可能比实际少 1 秒。
3. `dateTime` 固定 `Locale.CHINA` 与 `yyyy-MM-dd HH:mm`（`Formatters.kt:18`），不带秒、不带时区；同一分钟内的两条记录文案完全相同（版本列表相邻快照可能撞时间串），且非中文系统也强制走该格式。
4. `dateTime` 每次调用都 `new SimpleDateFormat`（`Formatters.kt:18`）：好处是天然线程安全、无共享状态；代价是列表滚动时每个可见项一次对象分配（`HomeScreen.kt:216`、`DetailScreen.kt:409` 在组合里直接调用，无 `remember`）。
5. `fileSize` 阈值是 1024 进制但单位写作 GB/MB/KB（`Formatters.kt:21-24`），与厂商十进制口径差约 7%。同一模型文件在三个地方口径不同：`fileSize(237_115_547)` → `226.1 MB`；`transcribe/ModelManager.kt:23` 定义的 `MODEL_BYTES = 237_115_547L`；界面文案硬编码「约 230MB」（`ui/SettingsScreen.kt:184`、`SettingsScreen.kt:429`）；`transcribe/SherpaTranscriber.kt:13` 注释写「约 226MB」；索引 README 第 20 行也写「~226MB」。数字都指同一文件，只是进制/取整口径不同，容易被误读成两个模型。
6. `fileSize` 的分支顺序不可调换（`Formatters.kt:21-24`）：阈值是「从高到低」的 `when`，写反会让 GB 区间永久不可达；`bytes` 为 0 时落到 `else` 输出 `0 B`（`Formatters.kt:24`），负数同样落 `else` 输出 `-1 B`。
7. 阈值常量 `1 shl 30`/`1 shl 20`/`1 shl 10` 是 `Int`（`Formatters.kt:21-23`），与 `Long` 比较时靠隐式提升，当前 `1 shl 30 = 1073741824` 未溢出；若将来加 TB 档写成 `1 shl 40` 会静默溢出为负，所有大文件都会掉进 TB 分支。
8. 时间格式化存在 3 处**未走本模块**的重复实现，格式各异：`record/Recorder.kt:35`（`yyyyMMdd_HHmmss`，文件名）、`record/RecordSession.kt:128`（`MM-dd HH:mm`，笔记标题）、`ui/HomeScreen.kt:284`（`yyyyMMdd_HHmmss`，导入文件名）。它们各自 `import java.text.SimpleDateFormat`（`Recorder.kt:8`、`RecordSession.kt:17`、`HomeScreen.kt:71`），`Formatters` 没有对应函数，改动统一格式时容易漏。
9. 该模块没有单元测试：`app/src/test/java/com/tingsiwei/app/` 下只有 `LlmPolicyTest.kt`、`LongTextPipelineTest.kt`、`PcmBufferTest.kt`、`SpeechCutTest.kt`、`TextChunkerTest.kt`、`TreeTextTest.kt` 六个测试文件，没有 `FormattersTest`——虽然它是最容易测的纯函数模块。
10. **索引 README 与本模块的差异**：`docs/模块总览/README.md` 的「模块索引」表（第 7-24 行）里**没有「通用工具」这一行**，`util/Formatters.kt` 未被收录，按索引查模块会整个漏掉；README 中「位置」列出现的文件路径也没有一处指向 `util/`。（同表第 20 行的「~226MB」与第 22 行的「语速 0.5~2.0x」描述的行为与代码相符：`ui/SettingsScreen.kt:272` 的 `valueRange = 0.5f..2.0f`。）
