# 详情页与生成编排模块总览

## 模块职责

详情页是单条笔记的唯一工作台（导图 / 原文 / 思路三页 + 版本回退 + 播放 + 朗读 + 分享 + AI 修改），而同文件里的 `DetailViewModel` 是全工程唯一一处「由界面层发起并兜底整条业务流水线」的地方——转写、生成、重试、断点续跑、状态机纠偏都在这 240 行里编排。

## 运作流程

**从哪来**：路由 `detail/{noteId}`（`AppNav.kt:45-48`），`noteId` 从字符串解析，失败给 `0L`（`AppNav.kt:46`）。首页卡片点击（`HomeScreen.kt:166`）、录音保存（`AppNav.kt:31-33`）、文字录入保存（`AppNav.kt:39-41`）、音频导入后用户手点（`HomeScreen.kt:316`）四条路都汇到这里。

**怎么装配**：`viewModel(key = "note$noteId", factory = detailVmFactory(noteId))`（`DetailScreen.kt:89`）——`key` 保证同一回退栈条目下每条笔记一个实例，factory 是为了把 `noteId` 灌进构造函数（`DetailScreen.kt:432-435`）。状态源是 Room 的两条 Flow：`noteDao().observeById(noteId)`（`DetailScreen.kt:442-443`；`AppDatabase.kt:23-24`）与 `versionDao().observeForNote(noteId)`（`DetailScreen.kt:444-445`；`AppDatabase.kt:41-42`），`noteId <= 0L` 时直接给 `flowOf(null)` / `flowOf(emptyList())` 短路。

**怎么处理**：组合阶段 `LaunchedEffect(note?.id, note?.status) { vm.maybeRunPipeline() }`（`DetailScreen.kt:98`）把「状态一变就检查有没有该跑的活」做成常驻钩子；渲染上先一条状态条（`DetailScreen.kt:124-179`）、再 `TabRow`（`DetailScreen.kt:181-185`）、再一个叠放 Box（`DetailScreen.kt:189-203`，注释解释得很明确：导图 WebView 常驻组合不销毁，另两页用不透明背景盖上去），最后底部 AI 建议输入（`DetailScreen.kt:205-238`）。版本抽屉 `VersionsSheet` 挂在 Scaffold 之外（`DetailScreen.kt:242-251`）。

**产出什么**：全部落在 `notes` 行（状态、content、mapJson、thinking、virtualRoot、errorMsg、updatedAt）与 `versions` 快照上，外加 `cache/shared/*.md` 一个导出临时文件（`DetailScreen.kt:588`；`Exporter.kt:60-64`）。`DetailViewModel` 不持有跨页状态。

**影响谁**：写库后 `observeById` 再发一格 → 画布刷新（`MindMapPanel.kt:144-153`）、首页列表顺序变化（`HomeScreen.kt:257`，按 `updatedAt DESC`）。

| `startPipeline(block)` | `DetailScreen.kt:467-470` | 唯一的任务闸门：`if (pipelineJob?.isActive == true) return`，否则 `pipelineJob = viewModelScope.launch { block() }`。所有会改导图/改状态的批量动作都必须经它，防止「状态变化触发的自动续跑」和「用户手动点的按钮」同时跑（字段注释 `DetailScreen.kt:448`）。 |
| `maybeRunPipeline()` | `DetailScreen.kt:473-493` | 自动续跑/纠偏。`noteId <= 0` 直接 return（474）；再起一个协程、开头再查一次 `pipelineJob?.isActive`（476），然后读一次权威的 `byId`（477），按四种情形分派：`TRANSCRIBING + content 空 + audioPath 非空` → `transcribe()`（479-480）；`DRAFT` → `generateInternal()`（481-482）；`GENERATING + mapJson 空`（生成中途被打断且没结果）→ 重跑 `generateInternal()`（483-485）；`GENERATING + mapJson 有值`（修改中途被打断但旧导图完好）→ **不重跑**，直接把行改成 `READY, errorMsg = null`（486-490）。 |
| `retry()` | `DetailScreen.kt:495-509` | 状态条上两个按钮的共用出口。三条分支：① `ERROR` 且 `errorMsg` 以「修改失败」开头 → 只把行清成 `READY`，**绝不重跑整篇生成**（499-503，判据来自 `Generator.revise` 失败时写的前缀，`Generator.kt:135-141`）；② `content` 空但有 `audioPath` → `transcribe()`（505）；③ 其余 → `generateInternal()`（506，重生成前 `Generator.generate` 会自动存快照，`Generator.kt:58-69`）。 |

| `generateInternal()`（private） | `DetailScreen.kt:544-551` | 把 `busyStage` 设成「正在生成导图…」、`Generator(db, settingsRepo).generate(noteId) { busyStage = it }`、`finally` 里清 `busyStage`。生成器每次调用现造（547，同一模式在 `sendSuggestion` 557、`restore` 579 重复三次），节流闸不受影响因为 `RateGate` 是进程级共享（`LlmClient.kt:22`）。阶段文案由 `LongTextPipeline` 回调上来（`LongTextPipeline.kt:120`、`123`、`235`、`261`）。 |
| `sendSuggestion(text)` | `DetailScreen.kt:553-562` | AI 改图。整体走 `startPipeline`（554）→ `busyStage = "正在按你的要求修改…"` → `Generator.revise(noteId, text)`（557；`Generator.kt:87-144`，改前存快照 `Generator.kt:96-104`）→ `finally` 清 `busyStage`。UI 侧按钮的可用条件是 `mapJson != null && busyStage == null`（`DetailScreen.kt:233`），点击后先清空输入框再调用（`DetailScreen.kt:227-231`）。 |

### 状态机（以 `NoteStatus`，`Entities.kt:9-15` 为准）

```
RECORD(有系统文字) / TEXT / IMPORT-粘贴导图 ─────────────→ DRAFT ──generate──→ GENERATING ──→ READY
        （TextInputScreen.kt:102、142；RecordSession.kt:131）    （DetailScreen.kt:481）  （Generator.kt:37）        （Generator.kt:71-80）
RECORD(无系统文字) / IMPORT ──→ TRANSCRIBING ──转写成功──→ DRAFT ──→ ……（同上）
        （RecordSession.kt:131；HomeScreen.kt:310）        （DetailScreen.kt:524）
GENERATING / TRANSCRIBING ──异常──→ ERROR（errorMsg = 友好文案）──retry──→ 三条分支
        （Generator.kt:83；Generator.kt:136-142；DetailScreen.kt:528-534）   （DetailScreen.kt:495-509）
GENERATING + 旧导图完好（进程被杀后回来）──→ READY（不重跑）
        （DetailScreen.kt:486-490）
READY + errorMsg 非空 ──「提示」而非错误（例如个别段未纳入）──→ 状态条按钮显示「补全」
        （DetailScreen.kt:160-178；errorMsg 由 notice 写入 Generator.kt:77）
```
关键点：`READY` 时 `errorMsg` 语义翻转成提示，所以 `retry()` 的第一分支必须靠字符串前缀「修改失败」区分（`DetailScreen.kt:500`），这是界面与 `Generator` 之间一个**靠文案维系**的隐式协议。

### 拖动防回环（实现不在本模块）

链路：JS 拖动 → `scheduleSave()` 500ms 防抖后 `AndroidBridge.onMapChanged(JSON.stringify(mind.getData()))`（`app/src/main/assets/mindmap/index.html:86-94`）→ `MapBridge.onMapChangedCb` 先记 `localJson = json` 再上抛（`MindMapPanel.kt:124-133`）→ `DetailScreen.kt:276` 的 `vm.saveMap(it)` → 写库（`DetailScreen.kt:569`）→ `observeById` 回推新 `mapJson` → `update` 块判定 `mapJson != localJson` 不成立，**不回推画布**（`MindMapPanel.kt:144-153`）。只有外部变化（AI 重生成、恢复版本）才会走到 `ctl.setData(mapJson)`。README 设计决策 4 说的就是这个（README 第 31 行）。

## 关键数据结构

无独立数据结构（本文件不定义 data class / enum），复用的都是别处的：

- 输入：`NoteEntity`（`Entities.kt:24-43`）——本文件实际消费的字段是 `title`（103）、`status`（129/141/160/276）、`errorMsg`（148/168）、`mapJson`（110/115/257）、`thinking`（353）、`content`（299）、`audioPath`（296/598）、`virtualRoot`（412）。

- 视图状态（VM 暴露给组合的流）：`note: Flow<NoteEntity?>`、`versions: Flow<List<VersionEntity>>`（442-445）、`busyStage: MutableStateFlow<String?>`（447，**一个字段两用**：状态条文案 + 「忙」标志，`DetailScreen.kt:137` 与 `233`）。
- 播放状态：`playing / playPosMs / playDurationMs`（453-455）+ 私有 `player: MediaPlayer?`（452）与 `playerJob`（456）。
- 朗读状态：`ttsSpeaking / ttsRate`（460-461）+ 私有 `tts`（459）。

## 已知坑与约束

1. **UI 与 ViewModel 同文件，且这个 ViewModel 还兼业务编排**：`DetailScreen.kt` 一个 678 行的文件里同时住着 6 个 Composable、1 个 Factory 和 1 个带转写/生成/重试/续跑职责的 `DetailViewModel`（`DetailScreen.kt:437-678`）。**后续要拆就拆 `DetailViewModel`**（把它移到 `ui/` 之外或单列 `DetailViewModel.kt`，`maybeRunPipeline`/`retry`/`transcribe` 这套状态机纠偏逻辑最该独立可测）。需要澄清的是「唯一」的口径：*ViewModel 与 UI 同文件*在本工程是通行做法，四处都有（`HomeScreen.kt:252`、`RecordScreen.kt:190`、`SettingsScreen.kt:294`、`DetailScreen.kt:437`）；DetailScreen 的特殊之处是 **同文件里 VM 承担了跨模块业务编排、且文件同时装了 8 个顶层声明**——`HomeViewModel` 也做文件与断点清理（`HomeScreen.kt:262-321`），`RecordViewModel` 只是转发（`RecordScreen.kt:192-211`），二者都算不上「编排」。所以严格讲「唯一一处两关注点同居」这句字面表述与代码不符，按上文的口径理解。
2. **索引 README 的模块归属与本文件不符**：README 把「生成流水线」整条归到 `llm/Generator.kt` 等文件（README 第 13 行），但流水线的**触发、状态兜底与转写调用**实际写在 `ui/DetailScreen.kt`（`DetailScreen.kt:473-537` 调 `Transcriber` 与 `Generator`）；README 第 23-24 行也只列了 `tts/TtsPlayer.kt`、`export/Exporter.kt`，没有任何一行提到详情页的 TTS/导出调用点在 `DetailViewModel`（`DetailScreen.kt:650-669`、`584-591`）。
3. **防回环不在本模块**：README 设计决策 4 说「MindMapPanel 记录 `localJson`」（README 第 31 行），实现确实在 `MindMapPanel.kt:91`、`124-133`、`144-153`；`DetailScreen.kt` 只负责把 `saveMap` 当回调传下去（`DetailScreen.kt:276`）。改防回环不要去动详情页。
4. **`retry()` 与状态文案强耦合**：分支判据是 `errorMsg.orEmpty().startsWith("修改失败")`（`DetailScreen.kt:500`），文案由 `Generator.revise` 写死（`Generator.kt:139`）。任何一侧改字面量，「只清提示、不重跑整篇生成」的省额度逻辑就会静默退化成整篇重跑。
5. **「补全」并不只补失败段**：`READY + errorMsg` 状态条上的按钮叫「补全」（`DetailScreen.kt:172-175`），走的仍是 `retry()` → `generateInternal()`（`DetailScreen.kt:506`）即重跑整条流水线；少花钱靠的是 `SegmentStore` 的断点复用（`SegmentStore.kt:23-42`、`LongTextPipeline.kt:120`），不是详情页的逻辑。
6. **`transcribe()` 用开跑前的旧对象回写**：`n` 在 `DetailScreen.kt:513` 读一次，之后 515/524/528 三次 `n.copy(...)` 全基于它（整行覆盖）。目前不炸是因为写库的另一方 `saveMap` 只在 `READY` 写（`DetailScreen.kt:568`）；若哪天放开 `saveMap` 的状态限制，转写期间的拖动结果会被无声吞掉。
7. **`retry()` / `shareMarkdown()` 缺 `noteId <= 0` 守卫**：`maybeRunPipeline`（474）和 `generate`（540）都守了，`retry`（495）没有——`noteId = 0` 时 `byId` 返回 null 而 `return@launch`（497），行为安全但与其他方法不一致。`noteId <= 0` 的来源是路由解析失败（`AppNav.kt:46`）。
8. **Snackbar 通道是死的**：`Scaffold` 挂了 `snackbarHost = { SnackbarHost(remember { SnackbarHostState() }) }`（`DetailScreen.kt:120`），但 `SnackbarHostState` 是就地 `remember` 的、没被存进变量，也没有任何 `showSnackbar` 调用点（本文件 grep 无）。所以恢复失败、导出异常、播放准备失败（`DetailScreen.kt:617-619` 只把 `playing` 置 false）全部**静默**。
9. **恢复结果不报告、不校验**：`Generator.restoreVersion` 返回 `Boolean`（`Generator.kt:146`、`172`），`DetailScreen.kt:579` 把返回值丢了，`busyStage` 在 `finally` 之外无条件清（580）；`versions` 行被别处删掉时用户只会看到「什么都没发生」。
10. **`busyStage` 既当文案又当互斥锁**：AI 建议按钮 `enabled = ... && busyStage == null`（`DetailScreen.kt:233`），但顶栏「分享」（`DetailScreen.kt:113-116`）与「重试/补全」（`DetailScreen.kt:153`、`172`）都不看 `busyStage`，只看 `pipelineJob`；于是「分享」可以在生成中途读到中间态并导出（588），「重试」在任务在飞时被 `startPipeline` 的守卫直接吞掉（468）而不给任何反馈。
11. **`toggleTts` 的等待循环可叠加**：`while (tts.isSpeaking) delay(300)`（`DetailScreen.kt:660`）没有保存 Job、也没取消上一次；快速连点两次时先后两个协程会交叉改 `ttsSpeaking`，按钮文案（`DetailScreen.kt:369-371`）可能和真实播报状态不一致。且 `TtsPlayer` 本身提供的 `onStateChange` 回调从未被赋值（`TtsPlayer.kt:13`、`25`、`45`、`50`），本页完全靠 300ms 轮询。
12. **语速有两条 UI 入口**：详情页 Slider（`DetailScreen.kt:375-380`）和设置页 Slider（`SettingsScreen.kt:269-275`）都是 `0.5f..2.0f` 并写同一个 DataStore key（`DetailScreen.kt:668`；`SettingsScreen.kt:396-398`；`SettingsRepository.kt:93-95`）。详情页的 `ttsRate` 只在 `init` 读一次（`DetailScreen.kt:463-465`），不 `collect`，所以在设置页改完语速再回到仍然活着的详情页，显示与生效值都是旧的。
13. **`TtsPlayer.speak(text, rate)` 在引擎就绪时忽略传入的 rate**：只有未就绪分支把 rate 存进字段（`TtsPlayer.kt:29-36` 对比 `TtsPlayer.kt:38-42`），实际发音语速取字段值，默认 `1.0f`。结果：README 第 23 行宣称的「语速 0.5~2.0x」在多数情况下不生效（0.5~2.0 这个区间本身也不在 `TtsPlayer` 里，是 UI 侧约束）。
14. **`shareMarkdown` 无异常保护**：`Exporter.buildMarkdown` 对 `mapJson` 走 `TreeText.fromMapData`（`Exporter.kt:29`），后者 `json.parseToJsonElement(mapJson)` 不做容错（`TreeText.kt:102`）。一条被写坏的 `mapJson` 会让顶栏「分享」直接抛，调用点没有 runCatching（`DetailScreen.kt:588`）。（对比：版本预览那里就规规矩矩包了 `runCatching`，`DetailScreen.kt:410-414`。）
15. **WebView 常驻 = 每条打开过的笔记都留一个 WebView**：`MapTab` 无条件组合（`DetailScreen.kt:190`），销毁点在 `AndroidView.onRelease`（`MindMapPanel.kt:137-139`）。切标签不丢缩放/平移是收益（`DetailScreen.kt:187-188` 注释），内存是代价。
16. **`onCleared` 只清播放与朗读**：`playerJob / player / tts` 都处理了（`DetailScreen.kt:671-677`），`pipelineJob` 交给 `viewModelScope`。因为 VM 按 `key = "note$noteId"` 存在回退栈条目上（`DetailScreen.kt:89`），**用户滑掉详情页等于取消在飞的 LLM 请求**，留下的中间态由下次进入时的 `maybeRunPipeline` 兜底（`DetailScreen.kt:483-490`）——这是一对配套设计，改一个必须看另一个。
17. **未接线的画布能力**：`MapController` 提供 `redo()` / `exportPng()`（`MindMapPanel.kt:60`、`62`），`MapBridge` 也留了 `onPngCb`（`MindMapPanel.kt:25`、`42-45`），JS 侧有 `appExportPng`（`app/src/main/assets/mindmap/index.html:194-203`）；详情页只用了 `toCenter()` 与 `undo()`（`DetailScreen.kt:282-287`），`MapBridge` 构造时没传 `onPngCb`（`MindMapPanel.kt:123-133`）→ 图片导出整条链路空转。
18. **播放完成后不能原地点重播**：完成回调把 `playPosMs` 钉在末尾（`DetailScreen.kt:608-611`），之后 `togglePlay()` 走的是 `p.start()` 分支（`DetailScreen.kt:624-627`），没有 `seekTo(0)`。是否能从头重播取决于 `MediaPlayer` 实现，未实测（见「疑点」）。
19. **原文标签把整篇当一个 Text 渲染**：`SelectionContainer { LazyColumn { item { Text(content …) } } }`（`DetailScreen.kt:306-316`），LazyColumn 里只有一个 item，长文本没有真正的懒加载收益；「复制全文」直接写剪贴板（`DetailScreen.kt:311-314`）。
20. **版本抽屉高度写死**：`LazyColumn(modifier = Modifier.height(360.dp))`（`DetailScreen.kt:399`），`ModalBottomSheet` 里再套固定高列表，快照很多时只在内部滚。
21. **`viewModel` 的 key 与路由参数不是同一套校验**：`key = "note$noteId"`（`DetailScreen.kt:89`）配合 `AppNav.kt:46` 的 `?: 0L`，`detail/abc` 这种坏 URL 会得到 `note$0` 的 VM 与一个永久转圈的进度圈（`DetailScreen.kt:126-128`），不会崩也不会提示。
