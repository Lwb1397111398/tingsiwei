# 转写模式选择模块总览

## 模块职责

一个全局二选一开关 `TranscribeMode`（`OFFLINE` / `SYSTEM`），决定录音的文字是靠"手机自带识别边录边转"还是"录完后用内置离线模型转写"。

## 运作流程

**从哪来（用户在哪切）**：设置页 →「语音转文字」卡片里的两个 `RadioButton`（`ui/SettingsScreen.kt:178-191`，"离线模型（推荐，免费、录音完转写）"在 `:183`，"手机自带识别（边录边转，各手机效果不一）"在 `:190`）→ `SettingsViewModel.setMode(mode)`（`ui/SettingsScreen.kt:545-548`）→ `SettingsRepository.setTranscribeMode`（`data/SettingsRepository.kt:151-153`）→ DataStore 键 `transcribe_mode`（`data/SettingsRepository.kt:63`）。除设置页外没有第二个写入口（首页/录音页只读不写）。

**怎么处理（读取与快照）**：`AppSettings.transcribeMode` 随 `settings` 流读出，缺省 `OFFLINE`——读侧两个函数各写一份兜底：`settings` 流（`data/SettingsRepository.kt:88`）与 `current()`（`:120`）。只有两个时点会读它：① `RecordSession.start()` 里读一次并缓存进 `RecordSession.transcribeMode`（`record/RecordSession.kt:67`）；② 录音页 `RecordViewModel.init` 读一次用于显示（`ui/RecordScreen.kt:201-205`，赋值在 `:203`）。

**分流在哪几行**（结论：**不在 `Transcriber.kt`**，那里没有模式分支）：
- `record/RecordSession.kt:77` —— 开录时 `if (transcribeMode.value == TranscribeMode.SYSTEM) startRecognition()`，SYSTEM 才边录边转。
- `record/RecordSession.kt:104` —— `resume()` 时同样按 SYSTEM 重启识别会话。
- `record/RecordSession.kt:126` —— 保存时 `val content = if (mode == TranscribeMode.SYSTEM && systemText.isNotBlank()) systemText else null`，紧接着 `:132` 据此决定 `status = DRAFT`（有文字，直接进生成）或 `TRANSCRIBING`（没文字）。
- OFFLINE 一侧是**隐式回落**，且 v1.5.0 起触发点前移：无论哪种模式，保存后 `RecordSession` 都调 `NoteProcessor.start(id, Kind.TRANSCRIBE)`（`record/RecordSession.kt:140`）；`TRANSCRIBING` 的笔记由宿主 `runTranscribe` 调 `Transcriber.transcribeOffline(...)` 转写（`pipeline/NoteProcessor.kt:106-137`，实调在 `:118`），全程不再看模式；`DRAFT`+正文的 SYSTEM 笔记进 `runTranscribe` 后因 `content` 非空直接跳去生成（`pipeline/NoteProcessor.kt:111-114`）。详情页 `maybeRun`（`ui/DetailScreen.kt:509`）与 App 启动 `resumeStuck`（`App.kt:22`）只是兜底续跑入口，`ui/DetailScreen.kt` 已无任何直接转写调用（grep 为零）。

**影响谁**：录音页文案与是否显示实时字幕（`ui/RecordScreen.kt:102`、`:165`）、是否创建 `SystemSpeechRecognizer`（`record/RecordSession.kt:156-161`）、笔记落库的 `content`/`status`（`record/RecordSession.kt:126-137`）、是否触发模型下载需求（`OFFLINE` 需模型就绪，`transcribe/Transcriber.kt:21-23`）、下游 LLM 生成入口（转写完成后宿主自动 `runGenerate`，`pipeline/NoteProcessor.kt:125`、`:139-141`）。

## 关键数据结构

- 定义形态：`object TranscribeMode { const val OFFLINE = "offline"; const val SYSTEM = "system" }`（`data/SettingsRepository.kt:19-22`）——**不是 `enum class`**，是字符串常量组；比较一律用 `==`。
- 持久化：DataStore preferences 键名 `"transcribe_mode"`（`data/SettingsRepository.kt:63`），值是原始字符串，写入不做白名单校验（`:151-153`）。
- 默认值：`TranscribeMode.OFFLINE`，四处独立写死——`settings` 流兜底（`data/SettingsRepository.kt:88`）、`current()` 兜底（`:120`）、`RecordSession.transcribeMode` 初值（`record/RecordSession.kt:35`）、`SettingsViewModel.transcribeMode` 初值（`ui/SettingsScreen.kt:457`）。
- 与笔记状态的耦合：`content != null → NoteStatus.DRAFT`，否则 `NoteStatus.TRANSCRIBING`（`record/RecordSession.kt:132`；状态常量见 `data/db/Entities.kt:9-15`）。
- 语义分工：`OFFLINE` = 录完再转、需要模型文件；`SYSTEM` = 边录边转、依赖厂商识别服务（注释 `data/SettingsRepository.kt:20-21`）。

## 已知坑与约束

- **索引 README 对照（已回收）**：旧登记称 README「转写模式选择」行还写着 `SettingsRepository.kt:58`——2026-10-04 README 第 30 行已改为准确落点（`:76`/`:105` 两处读盘默认、`RecordSession.kt:35` 内存初值、设置页选中态 `SettingsScreen.kt:179`），与代码一致，登记作废。其余表述（定义在 `data/` 不在 `transcribe/`、默认 OFFLINE、设置页可切）一直与代码一致；旧版「备用」错句已在 2026-09-20 README 重写时修掉。
- **同文件新增的 `llmStagedThinking` 键与本模块无逻辑交集，但共享写入通道**：`llm_staged_thinking`（键 `data/SettingsRepository.kt:69`，字段 `:44` 默认 `false`，setter `setLlmStagedThinking` `:159-161`）影响的是生成流水线的直路/三段式分叉（`llm/Generator.kt` 的 `stagedOrDirect`），不影响转写模式分流；它把 `SettingsRepository.kt` 从 102 行扩到 162 行，2026-10-05 又因应用自更新 4 键扩到 209 行——本总览全部行号已按 209 行版重校。转写慢和生成慢是两件事：转写耗时看 `Transcriber.transcribeOffline`（解码+逐块识别），生成耗时看思路精修开关（见笔记处理宿主总览「已知坑」第 1 条）。
- **分流点不在转写门面**：`transcribe/Transcriber.kt` 只有 `transcribeOffline` 一条路（`:16-52`），没有 `if (mode)`；真正的分叉在 `record/RecordSession.kt:77`、`:104`、`:126` 三行，加上 `pipeline/NoteProcessor.kt:111-114` 的隐式回落。想加第三种模式必须同时动这些行 + 2 处 UI（`ui/SettingsScreen.kt:177-190`、`ui/RecordScreen.kt:102`）。
- **录音途中改设置对本次无效**：模式在 `start()` 时快照（`record/RecordSession.kt:67`），正在录的这一段不会切换识别方式；但录音页文案读的是同一个快照（`ui/RecordScreen.kt:102`），而设置页的 `transcribeMode` 是另一份状态（`ui/SettingsScreen.kt:399`）——两份状态在用户切页后可能显示不一致。
- **字符串无校验，未知值退化成 OFFLINE**：`setTranscribeMode` 不校验入参（`data/SettingsRepository.kt:133-135`），任何脏值都会使 `== TranscribeMode.SYSTEM` 为 false（`record/RecordSession.kt:77`、`:126`）从而按离线走，且没有任何日志。
- **两条链路可能同时不可用**：`SYSTEM` 模式下一句话都没识别出来 → `content = null`、`status = TRANSCRIBING`（`record/RecordSession.kt:126-132`）→ 宿主仍会去跑离线转写（`pipeline/NoteProcessor.kt:115-120`），此时若模型没下载，`Transcriber` 直接抛「离线识别模型还没下载，请到设置页下载」（`transcribe/Transcriber.kt:21-23`），宿主把它写进 `ERROR.errorMsg`（`pipeline/NoteProcessor.kt:128-136`），用户会以为"我明明选了手机识别"。
- **模式不随笔记记录**：`NoteEntity` 没有存转写方式的字段（`data/db/Entities.kt:24-44`）→ 事后无法区分某条正文来自系统识别还是离线模型；详情页"重试"也是按 `content` 是否为空来决定重跑转写还是生成（`ui/DetailScreen.kt:522-524`），同样不看模式，所以**改了模式不会让已有笔记重新转写**。
- **`SYSTEM` 不额外省空间**：两种模式都会保留 m4a 并写 `audioPath`（`record/RecordSession.kt:134`），系统识别只是少了后处理，不减少磁盘占用。
