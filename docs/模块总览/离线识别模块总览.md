# 离线识别模块总览

## 模块职责

用 sherpa-onnx 的 `OfflineRecognizer` + SenseVoice int8 中文模型，把解码切块产出的 16k 单声道音频块逐块识别成文字并拼成整篇转写文本（全程不联网、不上传音频）。

## 运作流程

**从哪来**：详情页的转写任务。`DetailViewModel.maybeRunPipeline()` 命中"`status = TRANSCRIBING` 且 `content` 为空且有 `audioPath`"时自动续跑（`ui/DetailScreen.kt:479`），或"重试"按钮同样触发（`ui/DetailScreen.kt:505`），最终进 `transcribe()` → `Transcriber.transcribeOffline(App.get(), audio) { _, msg -> busyStage.value = msg }`（`ui/DetailScreen.kt:518-520`）。也就是说：**导入音频和录音走的是同一条离线链路**（导入见 `ui/HomeScreen.kt:305-315`）。

**怎么处理**（`transcribe/Transcriber.kt:16-52`）：
1. 门槛检查：`SherpaTranscriber.isModelReady(context)` 不通过就抛 `IllegalStateException("离线识别模型还没下载，请到设置页下载")`（`transcribe/Transcriber.kt:21-23`；判据见 `transcribe/SherpaTranscriber.kt:52-56`）。
2. 先报 `onProgress(0f, "正在加载识别模型…")`（`transcribe/Transcriber.kt:24`），再在 `Dispatchers.Default` 上 `SherpaTranscriber(dir)`（`:26`）——构造即加载模型：`init` 里组装 `OfflineRecognizerConfig`（`FeatureConfig` 默认 + `OfflineSenseVoiceModelConfig(model = <modelDir>/model.int8.onnx, language = "zh", useInverseTextNormalization = true)`、`tokens = <modelDir>/tokens.txt`、`numThreads = 2`、`modelType = "sense-voice"`），然后 `OfflineRecognizer(assetManager = null, config)`（`transcribe/SherpaTranscriber.kt:19-34`）。模型目录是 `filesDir/asr/sensevoice`（`:48-50`）。
3. 逐块识别：`withContext(Dispatchers.Default)` 里调 `AudioDecode.forEachChunk(audioPath, isCancelled = { !ctx.isActive }, onProgress = { frac -> … }) { chunk -> transcriber.recognizeChunk(chunk) }`（`transcribe/Transcriber.kt:30-46`）。每块走 `recognizeChunk`：`createStream()` → `acceptWaveform(samples, 16000)` → `decode(stream)` → `getResult(stream)` → `stream.release()` → `result.text.trim()`（`transcribe/SherpaTranscriber.kt:39-46`）。
4. 拼接：块文本非空才追加，且**若上一块末尾不是换行就先补 `'\n'`**（`transcribe/Transcriber.kt:41-44`）；`blocks++` 无条件计数（`:45`）。
5. 释放：`finally { transcriber.release() }`（`transcribe/Transcriber.kt:49-51` → `transcribe/SherpaTranscriber.kt:36`）。

**产出什么**：`suspend fun transcribeOffline(...): String` —— 一个 `trim()` 后的整篇转写文本。上层写进 `NoteEntity.content`、状态改 `DRAFT` 并紧接 `generateInternal()` 进 LLM 生成（`ui/DetailScreen.kt:521-525`）；抛异常则状态 `ERROR` + `errorMsg`（`ui/DetailScreen.kt:526-536`）。

**影响谁**：LLM 生成流水线（`llm/Generator.kt`）、详情页的"正在识别…已完成 N%，已识别 M 字（第 K 段）"文案（`ui/DetailScreen.kt:137`、`ui/DetailScreen.kt:519`）、设置页的模型状态卡片（因为共用 `isModelReady`/`modelDir`）。

**进度与"已识别 N 字"怎么统计**（重点，容易误解）：
- 百分比来自**解码位置**：`AudioDecode` 用 `presentationTimeUs / durationUs` 回调 0..1（`transcribe/AudioDecode.kt:87-89`），`Transcriber` 转成整数百分比（`transcribe/Transcriber.kt:35-38`）。它衡量的是"音频读到哪了"，由于解码与识别在同一协程里串行，也就约等于"识别到哪了"。
- **字数 `sb.length`**：`StringBuilder` 当前长度，即**已拼接字符数，包含块之间补的 `'\n'`，并且只统计非空块**（`transcribe/Transcriber.kt:28`、`:41-44`、`:37`）。纯静音块不加长字符串，所以"已识别 0 字"可以伴随"已完成 80%"。
- **段号 `blocks + 1`**：`blocks` 是"已处理的块数（含空块）"，进度回调发生在下一块识别之前，所以显示的是"正在处理的第几段"（`transcribe/Transcriber.kt:29`、`:45`、`:37`）。
- `onProgress` 的第二个参数是给人看的状态串，第一个参数被详情页丢弃（`ui/DetailScreen.kt:518` 用 `_`）。

## 依赖的上游模块

- **sherpa-onnx AAR**：`app/libs/sherpa-onnx-1.13.8.aar`（实测 50,129,134 字节 ≈ 47.8 MiB，已随 git 跟踪），通过 `implementation(fileTree(mapOf("dir" to "libs", "include" to listOf("*.aar"))))` 引入（`app/build.gradle.kts:48`）；Kotlin 侧只 import `com.k2fsa.sherpa.onnx.*` 的 5 个类型（`OfflineRecognizer` + 4 个配置类，`transcribe/SherpaTranscriber.kt:4-8`）。native 库按 `abiFilters = arm64-v8a / armeabi-v7a / x86_64` 打包（`app/build.gradle.kts:20`）。
- **模型文件**：由 `transcribe/ModelManager.kt` 下载到 `SherpaTranscriber.modelDir()`（见「模型下载模块总览」）；本模块只读文件、不下载。
- **音频解码与切块**：`AudioDecode.forEachChunk`（`transcribe/Transcriber.kt:32` → `transcribe/AudioDecode.kt:17`）。
- **协程调度**：`Dispatchers.Default` + `coroutineContext.isActive` 做取消（`transcribe/Transcriber.kt:5-7`、`:30-31`、`:35`）。
- **调用方所在模块**：`ui/DetailScreen.kt`（`DetailViewModel`）、`data/db`（`NoteEntity.status/content`）、`App`（Context）。
- 运行时前提：进程内存足够加载 int8 SenseVoice；无网络要求（与 SYSTEM 模式的关键差别）。

## 关键数据结构

- **配置树**（`transcribe/SherpaTranscriber.kt:20-32`）：`OfflineRecognizerConfig(featConfig = FeatureConfig(), modelConfig = OfflineModelConfig(senseVoice = OfflineSenseVoiceModelConfig(model, language, useInverseTextNormalization), tokens, numThreads, modelType))`。实际取值：`language = "zh"`（`:25`）、`useInverseTextNormalization = true`（`:26`，即数字/标点反文本化）、`numThreads = 2`（`:15` 默认参数，未从设置读取）、`modelType = "sense-voice"`（`:30`）、`assetManager = null`（`:33`，一律走文件系统）。`FeatureConfig` 用全默认，即 sherpa-onnx 侧的 16kHz/80 维 fbank 约定，与 `acceptWaveform(samples, 16000)`（`:41`）和上游 `PcmBuffer.TargetRate = 16000` 三者必须一致。
- **文件契约**：目录 `filesDir/asr/sensevoice`（`:50`，`apply { mkdirs() }`），两个必需文件 `model.int8.onnx`（`:24`）与 `tokens.txt`（`:28`）。
- **就绪判据 `isModelReady`**：`model.int8.onnx` 长度 `> 200_000_000` **且** `tokens.txt` 长度 `> 100_000`（`:52-56`）——只看字节数，不做哈希。
- **块文本 → 全文**：`StringBuilder sb` + `var blocks: Int`（`transcribe/Transcriber.kt:28-29`），块分隔符是 `'\n'`（`:42`），返回 `sb.toString().trim()`（`:48`）。
- **进度元组**：`(Float 0..1, String 文案)`（`transcribe/Transcriber.kt:19`、`:37`），文案模板 `"正在识别…已完成 $pct%，已识别 ${sb.length} 字（第 ${blocks + 1} 段）"`。
- **异常契约**（上层按 message 直接展示给用户）：`"离线识别模型还没下载，请到设置页下载"`（`transcribe/Transcriber.kt:22`）；`IllegalStateException("文件里没有音频轨道")` 来自解码层（`transcribe/AudioDecode.kt:40`）。

## 已知坑与约束

- **README 说"流式逐块识别"，实际不是流式识别器**：索引 README 第 19 行写"流式逐块识别拼接"。代码用的是 `OfflineRecognizer` / `OfflineSenseVoiceModelConfig`（`transcribe/SherpaTranscriber.kt:5-8`、`:17`、`:22-24`），每块都是"新建 stream → 整块 `decode` → 取结果 → 释放"的一次性整段解码（`:40-45`），不是 sherpa-onnx 的 `OnlineRecognizer` 流式接口。"流式"只成立在**外层按块推进**这个意义上。
- **模型体积口径三处不同**：README 第 20 行写"~226MB"，`SherpaTranscriber.kt:13` 注释同样写"约 226MB"，而 `ModelManager.MODEL_BYTES = 237_115_547`（`transcribe/ModelManager.kt:23`）——226 是 **MiB** 口径（237,115,547 / 1024² ≈ 226.1 MiB），设置页与下载提示文案则写"约 230MB"（`ui/SettingsScreen.kt:184`、`:429`）。
- **`isModelReady` 与就绪阈值不是同一套数**：就绪判据是 `> 200_000_000`（`transcribe/SherpaTranscriber.kt:54`），而真实文件是 237,115,547 字节（`transcribe/ModelManager.kt:23`）。被截断到 200MB 的坏文件会被判"已就绪"，然后在 `OfflineRecognizer` 构造处才炸。
- **`stream` 释放没有 `try/finally`**：`recognizeChunk` 里 `decode`/`getResult` 抛异常时 `stream.release()` 走不到（`transcribe/SherpaTranscriber.kt:42-45`），native 资源泄漏；`recognizer` 本身的释放有保障（`transcribe/Transcriber.kt:49-51`）。
- **解码与推理完全串行**：二者在同一个 `withContext(Dispatchers.Default)` 里顺序执行（`transcribe/Transcriber.kt:31-47`），没有"边解边识"的双缓冲流水线，CPU 解码期间推理线程空闲（反之亦然）。
- **每次转写都重新加载模型**：`SherpaTranscriber` 在 `transcribeOffline` 里 new、结束时 release（`transcribe/Transcriber.kt:26`、`:50`），不缓存 recognizer，也不做单例——连续"重试"每次都要付一次模型加载成本（表现为长时间停在"正在加载识别模型…"）。
- **取消响应粒度是一个块**：`isCancelled = { !ctx.isActive }`（`transcribe/Transcriber.kt:34`）只在解码循环里检查（`transcribe/AudioDecode.kt:61`、`:95`），块内 `recognizeChunk` 不可中断；`ctx` 取自 `withContext` 之前的 `coroutineContext`（`transcribe/Transcriber.kt:30`）。ViewModel 被清（离开详情页）时 `viewModelScope` 取消，任务随之中断。
- **块间无重叠，硬边界处会断句**：上游在找不到静音时会按 30s 硬切（`transcribe/SpeechCut.kt:65`），本模块不做前后块重叠，被切断的词可能两边都没有。
- **参数没出口**：`numThreads` 默认 2（`transcribe/SherpaTranscriber.kt:15`）、`language = "zh"`（`:25`）、块长按 `AudioDecode` 默认（`transcribe/Transcriber.kt:32` 未传 `targetSeconds/maxSeconds/silenceMs/silenceThresh`）——调这些只能改代码，设置页没有开关。
- **空结果被当作错误**：识别返回空串时上层抛"没有识别到内容，请检查录音质量；也可到设置里改用「手机自带识别」重新录一次"（`ui/DetailScreen.kt:521-523`），笔记进 `ERROR`。
- **无单测**：本模块依赖 native 库与真实模型文件，纯 JVM 测试跑不动；`testImplementation` 只有 junit（`app/build.gradle.kts:66`）。可测性被刻意下沉到 `SpeechScanner`/`PcmBuffer`（见「音频解码与切块模块总览」）。
- **依赖模型已落盘**：与 SYSTEM 模式的互备关系不在本模块里，而在录音侧的分流与详情页的回落（`record/RecordSession.kt:125`、`ui/DetailScreen.kt:479`）；`Transcriber.kt` 自身只有一条路。
