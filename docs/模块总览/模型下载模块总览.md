# 模型下载模块总览

## 模块职责

负责把 SenseVoice int8 离线识别模型（`model.int8.onnx` + `tokens.txt`）从国内镜像 `hf-mirror.com` 下载到应用私有目录，支持 `.part` 断点续传、5 次尝试、失败保留已下片段。

## 运作流程

**从哪来**：设置页「语音转文字」卡片里的「下载模型」按钮（`ui/SettingsScreen.kt:193-197`）→ `SettingsViewModel.downloadModel()`（`ui/SettingsScreen.kt:422-446`）：若已在下载就直接返回（`:423`），先把状态置 `DOWNLOADING`（`:424`），然后在 `viewModelScope` 里**先下 `tokens.txt` 再下 `model.int8.onnx`**（`:428`、`:430-438`），前者的进度回调被丢弃（`{ _, _ -> }`），后者逐次刷新 `modelState`。

**怎么处理**（`transcribe/ModelManager.kt:47-98`，`downloadFile` 全程在 `withContext(Dispatchers.IO)`）：
1. 若最终文件已 `>= minBytes` 直接返回"已完成"（`:54-58`）。
2. 进入 `while (true)` 尝试循环，`attempts++`（`:61-62`）。每轮：取 `.part` 当前长度作 `start`（`:64`），`start > 0` 就加请求头 `Range: bytes=$start-`（`:65-66`）。
3. 用 OkHttp **同步** `execute()`（`:67`）：HTTP 码不是 200/206 就抛 `"下载失败 (HTTP xxx)"`（`:68-70`），body 为空抛 `"下载失败：空响应"`（`:71`）。
4. 只有 `code == 206 && start > 0` 才 `append = true`；否则把 `start` 归零并**删掉 `.part` 从头再下**（`:72-76`）。总大小 `total = body.contentLength() + start`，取不到就用 `maxOf(start, MODEL_BYTES)`（`:77-79`）。
5. `copyWithProgress`：64KB 读缓冲，累计每 256KB 回调一次 `onProgress(已下载, 总大小)`，收尾再补一次（`:100-123`）。
6. 落地校验：`part.length() < minBytes` 就抛 `"下载的文件不完整"`（`:86`）；否则删同名旧文件、`renameTo` 转正，重命名失败退回 `copyTo(overwrite = true)` 再删 `.part`（`:87-91`）。
7. 异常处理：`attempts >= 5` 原样抛出，否则 `delay(1500L * attempts)` 再试（`:93-96`）——即 **1.5s、3s、4.5s、6s 的线性退避，共最多 5 次尝试（4 次重试）**。
8. 抛到 UI 后：`message = "下载失败：…（已下载部分保留，再点一次继续）"`，`finally` 里 `refreshModelState()` 会把 `.part` 长度显示成"下载中 N%"（`ui/SettingsScreen.kt:334-339`、`:440-444`）。

**产出什么**：`filesDir/asr/sensevoice/` 下的 `model.int8.onnx`（237,115,547 字节）与 `tokens.txt`，外加中断时的 `*.part`。目录由 `SherpaTranscriber.modelDir()` 决定（`transcribe/SherpaTranscriber.kt:49-50`），本模块只借用不定义。

**影响谁**：`SherpaTranscriber.isModelReady`（`transcribe/SherpaTranscriber.kt:52-56`）→ 离线转写能否启动（`transcribe/Transcriber.kt:21-23`）→ 详情页/生成流水线；设置页模型卡片（`ui/SettingsScreen.kt:181-186`）；「删除模型」按钮（`ui/SettingsScreen.kt:199` → `ModelManager.deleteModel`）。

## 关键数据结构

- 下载源（硬编码，无配置项、无回退）：`REPO = "https://hf-mirror.com/csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2025-09-09/resolve/main"`（`transcribe/ModelManager.kt:19-20`），文件由字符串拼接：`$REPO/model.int8.onnx`、`$REPO/tokens.txt`（`:21-22`）。模型仓库名与 `SherpaTranscriber.kt:13` 注释、`modelType = "sense-voice"` 一致。
- 两个文件的实际体积（以代码里可指到的数字为准，`transcribe/ModelManager.kt`）：

| 文件 | 代码里记录的体积/阈值 | 出处 |
| --- | --- | --- |
| `model.int8.onnx` | `MODEL_BYTES = 237_115_547L`（≈226.1 MiB / ≈237 MB，仅用于进度分母与文案） | `:23`、UI `ui/SettingsScreen.kt:290`、`:336`、`:424` |
| `model.int8.onnx` | 完成阈值 `minBytes = 200_000_000`（调用方传入） | `ui/SettingsScreen.kt:431`；就绪判据同量级 `transcribe/SherpaTranscriber.kt:54` |
| `tokens.txt` | **代码里没有任何体积常量**，只有完成阈值 `minBytes = 100_000` | `ui/SettingsScreen.kt:428`；就绪判据 `transcribe/SherpaTranscriber.kt:55` |

- 断点续传契约：最终文件 `<name>`，半成品 `<name>.part`，同目录（`transcribe/ModelManager.kt:30-34`）；续传头 `Range: bytes=$start-`（`:66`）；仅 `206` 视为可续（`:72`）。
- 重试状态：`attempts` 从 1 计，`if (attempts >= 5) throw e`，`delay(1500L * attempts)`（`:60-62`、`:93-96`）。
- 进度节流：64KB 缓冲 + 每 256KB 回调（`:107`、`:116-119`）。
- 状态映射在 UI 侧：`ModelState.{UNKNOWN, READY, DOWNLOADING, NOT_DOWNLOADED}` + `ModelStateUi(state, bytes, downloaded, total, progress)`（`ui/SettingsScreen.kt:284-292`、`:329-341`）。

## 已知坑与约束

- **README 说"5 次重试"，实际是 5 次尝试**：`attempts` 在第 5 次失败时直接 `throw`，不再等待也不发起第 6 次（`transcribe/ModelManager.kt:93-96`），所以真正的重试次数是 4 次；退避是 `1500 * attempts` 的**线性**递增（1.5/3/4.5/6s），不是指数退避（对比 LLM 层用的指数退避+抖动）。
- **README 的"~226MB"是 MiB 口径**：代码常量是 237,115_547 字节（`transcribe/ModelManager.kt:23`），UI 文案则写"约 230MB"（`ui/SettingsScreen.kt:184`、`:429`）、`SherpaTranscriber.kt:13` 写"约 226MB"。同一件事三处不同表述。
- **只有一个镜像、无回退**：`REPO` 硬编码 `hf-mirror.com`（`:19-20`），既没有 huggingface.co 直连也没有 ModelScope/gh-proxy 兜底，也没有把 URL 开放成设置项——README「坑」一节提到的 `gh-proxy.com` 只适用于当初取 sherpa-onnx release AAR，与模型下载无关。
- **没有真正的完整性校验**：只有长度阈值（`:86` 的 `minBytes`、`transcribe/SherpaTranscriber.kt:52-56`），无 sha256、无 ONNX 头部探测。200,000,000 的阈值明显低于真实 237,115,547 → 截断文件会被判"完成"，错误推迟到 `OfflineRecognizer` 构造时才暴露（`transcribe/SherpaTranscriber.kt:33`）。
- **`.part` 语义有副作用**：服务端忽略 `Range` 返回 200 时，代码删掉已下载的 `.part` 从零重下（`:73-76`）；返回 206 时不校验 `Content-Range` 的起点是否等于 `start`，一旦镜像返回错位区间，会拼出长度够但内容坏的文件。
- **失败不清理，成功才清理**：catch 分支只退避/抛出，`.part` 保留在内部存储（`:93-97`），中断一个月也占 200MB 左右；`deleteModel` 用 `dir.listFiles()?.forEach { it.delete() }` 会连 `.part` 一起删（`:125-128`），但**不递归子目录**、也不判断删除是否成功。
- **下载生命周期挂在设置页 VM 上**：`ui/SettingsScreen.kt:422-446` 用 `viewModelScope.launch`；VM 存活期间可继续，但**进程被杀即中断**（只有 `.part` 留下），也没有 WorkManager/前台服务，息态下载不保证；同时 `downloadFile` 内部用 OkHttp 同步 `execute()` 且无 `ensureActive()` 检查（`transcribe/ModelManager.kt:67`、`:100-123`），协程取消不会立刻打断正在读的那一次响应。
- **无并发/重复下载保护**：`ModelManager` 是 `object` 但没有任何"正在下载"标志（`ui/SettingsScreen.kt:423` 的守卫只挡同一个 VM 实例）；跨入口或重建 VM 后重复点击会开多条链路写同一个 `.part`（`FileOutputStream(part, append)`），结果不可预期。
- **无磁盘空间预检查、无流量提示**：约 237MB 落到 `filesDir`（内部存储），写满时表现为 `FileOutputStream.write` 抛异常并进入重试循环（`:80-84`、`:93-96`）。
- **`MODEL_BYTES` 只管 model 一个文件**：进度分母取自 `body.contentLength() + start`，取不到才回落到 `MODEL_BYTES`（`:77-79`）；`tokens.txt` 完全不计入进度（`ui/SettingsScreen.kt:428` 丢弃回调），所以按钮点下去会先出现一段"卡在 0%"的时间。
- **`totalBytes` 会把 `.part` 也算进"已下载"**（`:130-131`），与 `isModelReady` 的判断口径不同，可能出现"已下载（240MB）"这类包含半成品的数字。
- **`isFileComplete` 是死代码**：生产路径无人调用（见接口一节），改判据时容易只想到 `isModelReady` 而漏掉它。
- **本模块无单测**：`app/src/test` 下没有 `ModelManagerTest`，测试目录只有 6 个纯 JVM 用例文件；下载/续传逻辑依赖真实 HTTP 与文件系统，未抽出可注入的 `Transport` 接缝（对比 `llm/LlmClient.kt` 的做法）。
