# 模型下载模块总览

## 模块职责

`ModelManager` 管两组离线模型的下载、就绪判断与清理：ASR 识别模型（SenseVoice，2 个文件）和 v1.5.0 新增的 TTS 朗读模型（kokoro，373 个文件的清单），统一走国内镜像 hf-mirror.com、`.part` 断点续传、5 次尝试线性退避；应用启动时另起后台线程删掉已被 kokoro 替代的旧 vits-melo 朗读模型目录。

## 运作流程

**从哪来**：两个 UI 入口，都在设置页。

1. ASR：「语音转文字」卡「下载模型」按钮（`ui/SettingsScreen.kt:206`）→ `downloadModel()`（`SettingsScreen.kt:607-631`）：正在下载就直接 return（`:608`），先下 `tokens.txt`（完成阈值 `minBytes = 100_000`，`:613`）再下 `model.int8.onnx`（`minBytes = 200_000_000`，`:615-617`），tokens 的进度回调被丢弃、模型的逐次刷新 `modelState`。
2. TTS：「朗读」卡「下载模型」按钮（`SettingsScreen.kt:348-353`，只在引擎选了「离线朗读模型」时显示，`:329`）→ `downloadTtsModel()`（`SettingsScreen.kt:528-562`）→ `ModelManager.downloadTtsModel` 顺序下载 `TTS_FILES` 清单全部 373 个文件；每个文件开下时报「下载 i/count：相对路径」，espeak 语音数据那 350 多个小文件合并成「下载语音数据（i/count）…」免得刷屏（`SettingsScreen.kt:539-546`）。

**怎么处理**（`transcribe/ModelManager.kt`）：

1. 下载核心是通用函数 `downloadFileTo(dir, relPath, url, minBytes, onProgress)`（`ModelManager.kt:450-502`，全程 `withContext(Dispatchers.IO)`）：目标文件已存在且 `length() >= minBytes` 就跳过（`:459-462`）；否则按 `<relPath>.part` 续传——`.part` 当前长度作 `start`，`start > 0` 就加请求头 `Range: bytes=$start-`（`:468-470`）。
2. OkHttp **同步** `execute()`（`:471`）：HTTP 码不是 200/206 抛「下载失败 (HTTP xxx)」（`:472-474`），空响应抛错（`:475`）；只有 `206 && start > 0` 才追加写入，否则删 `.part` 从零下（`:476-480`）。总大小 `total = contentLength + start`，取不到回落 `maxOf(start, minBytes)`（`:481-483`；v1.5.0 前回落值是固定的 `MODEL_BYTES`，重构后改为按调用方传入的 `minBytes`）。
3. `copyWithProgress`（`ModelManager.kt:504-527`）：64KB 读缓冲（`:511`），每累计 256KB 回调一次 `onProgress(已下载, 总大小)`，收尾再补一次（`:520-526`）。
4. 落地校验：`part.length() < minBytes` 抛「下载的文件不完整」（`:490`）；通过则删同名旧文件、`renameTo` 转正，改名失败退回 `copyTo(overwrite = true)` 再删 `.part`（`:491-495`）。v1.5.0 起 `relPath` 可带子目录，父目录自动 `mkdirs()`（`:458`）——TTS 清单里的 `dict/`、`espeak-ng-data/` 都靠这个落位。
5. 重试：异常时 `attempts >= 5` 原样抛出，否则 `delay(1500L * attempts)` 再来（`:497-500`）——**共最多 5 次尝试（4 次重试），线性退避 1.5s/3s/4.5s/6s**。
6. ASR 适配层 `downloadFile(context, name, url, minBytes, onProgress)`（`ModelManager.kt:438-445`）：只是把目录钉在 `SherpaTranscriber.modelDir()`（`filesDir/asr/sensevoice`，`transcribe/SherpaTranscriber.kt:49-50`）再转调 `downloadFileTo`。
7. TTS 编排 `downloadTtsModel(context, onFileStart, onProgress)`（`ModelManager.kt:561-580`）：按清单顺序逐文件调 `downloadFileTo(dir, relPath, "$TTS_REPO/$relPath", f.bytes)`——**清单里每个文件声明的字节数直接当该文件的完整性下限**（类注释 `ModelManager.kt:28-29`：「字节数兼作完整性下限，下载完尺寸不符会报错」），比 ASR 的单一 200MB 阈值严得多；已完成的文件跳过并把基线累加进整体进度，整体进度 = 已下字节 / `TTS_TOTAL_BYTES`（`:566-578`）。
8. 启动清理：`App.onCreate` 起裸线程调 `cleanupLegacyTts(this)`（`App.kt:24` → `ModelManager.kt:534-536`，`File(filesDir, "tts/melo-zh-en").deleteRecursively()`）——旧版 vits-melo 朗读模型被 kokoro 替代后整个删掉。**体积口径注意**：`App.kt:23` 代码注释声明这一删「给用户腾出约 190MB 空间」——这是注释声明，melo 目录从未入库 git，无法对账实测；同一模块里可复核的真常量是 kokoro 侧的 `TTS_TOTAL_BYTES = 215,308,902` 字节（`ModelManager.kt:413`，= `TTS_FILES` 全部 `bytes` 求和，注释「约 215MB」在 `:412`）。两个数字口径不同（190≈被删的旧目录、215.3≈新下载的 kokoro 全量），不能互推。

**产出什么**：

- ASR：`filesDir/asr/sensevoice/` 下 `model.int8.onnx`（237,115,547 字节）与 `tokens.txt`，中断时留 `*.part`。
- TTS：`filesDir/tts/kokoro-v1.1-zh/` 下 373 个文件，合计 215,308,902 字节（≈215.3 MB 十进制 / 205.3 MiB）。大头：`model.int8.onnx` 114,299,010、`voices.bin` 53,790,720、`lexicon-{zh,us-en,gb-en}.txt` 3 项约 14.4MB、jieba 词典 `dict/` 9 项约 14.6MB、`espeak-ng-data/` 355 项注音数据约 18.0MB 垫底（`ModelManager.kt:36-410`，注释声明「清单即仓库实况（2026-09 核对），大文件在前、espeak 语音数据垫底」`:28-29`；项数与合计为本次脚本复核值）。
- 被删的旧目录：`filesDir/tts/melo-zh-en`（启动清理）。

**影响谁**：`SherpaTranscriber.isModelReady`（`SherpaTranscriber.kt:52-56`）→ 离线识别能否启动；`ModelManager.isTtsReady`（`ModelManager.kt:539-542`）→ `TtsPlayer` 离线分支用不用 kokoro（`tts/TtsPlayer.kt:69`）与设置页朗读卡状态（`SettingsScreen.kt:514`）；设置页两块卡片的状态文案与进度条（ASR `SettingsScreen.kt:192-212`、TTS `:330-357`）；`LocalTtsEngine` 构造时从 `ttsDir` 读模型（`TtsPlayer.kt:339`）。

## 已知坑与约束

1. **ASR「就绪阈值过松」仍在（TTS 侧已消除）**：`SherpaTranscriber.isModelReady` 只看文件长度 `> 200_000_000`（`SherpaTranscriber.kt:54`），真实体积 237,115,547 → 中断留下的 200~237MB 截断文件会被判「已就绪」。TTS 不存在此问题：`downloadTtsModel` 用每个文件声明的精确字节数当下限（`ModelManager.kt:575` + 注释 `:28-29`），`isTtsReady` 校验全部 373 个文件 `length() >= bytes`（`:539-542`），且 `ModelManagerTtsTest` 守门清单与总和一致。
2. **ASR「.part 残留卡假下载中」仍在（TTS 侧已修）**：`refreshModelState()` 把「存在 `.part`」判成 `DOWNLOADING`（`SettingsScreen.kt:435-437`），下载按钮禁用（`:206`）且 `downloadModel()` 首行 return（`:608`）——实际没有协程在跑，只能「删除模型」自救（`:210` → `:633-637`）。TTS 的 `refreshTtsModelState()` 把同样的场景判为 `NOT_DOWNLOADED` 并显示「已下载 X，点下载继续」（`SettingsScreen.kt:519-521`、`:333-334`），按钮可点。
3. **「5 次重试」实为 5 次尝试**：第 5 次失败直接 `throw`，真正重试 4 次，退避线性递增 1.5/3/4.5/6s（`ModelManager.kt:497-500`），不是指数退避。
4. **只有一个镜像、无回退**：`hf-mirror.com` 硬编码（`:21-22`、`:30-31`），无 huggingface.co 直连、无 ModelScope 兜底、URL 不开放成设置项；373 个文件逐个经镜像，镜像抖动会被放大。
5. **Range 续传不校验 `Content-Range` 起点**（`:476`）：镜像若返回错位区间会拼出长度够但内容坏的文件；服务端无视 Range 返回 200 时删 `.part` 从零重下（`:477-480`）——对 TTS 意味着已下的几十 MB 清零重来。
6. **下载生命周期挂在设置页 VM 上**：两处下载都在 `viewModelScope.launch`（`SettingsScreen.kt:530`、`:610`），进程被杀即中断（只留 `.part`），无 WorkManager/前台服务；`downloadFileTo` 无 `ensureActive()` 检查（`ModelManager.kt:450-502`），协程取消不会立刻打断进行中的读。
7. **并发保护仍只有同 VM 实例的状态守卫**（`SettingsScreen.kt:529`、`:608`）：`ModelManager` 是 `object` 无内部锁，重建 VM 或跨入口重复触发会开多条链路写同一个 `.part`。
8. **无磁盘空间预检查**：约 237MB（ASR）+ 约 215MB（TTS）都落内部存储 `filesDir`，写满表现为 `FileOutputStream.write` 抛异常进重试循环。
9. **两个删除函数行为不同**：`deleteModel` 只删 ASR 目录顶层文件、不递归（`:588-591`）；`deleteTtsModel` 是 `deleteRecursively` 整目录（`:582-584`）。两者都不判删除是否成功。
10. **体积口径至少六处不同**（同一件事的不同表述，见上表）：数字本身都对，只是 1024/1000 进制与取整不同；`Formatters.fileSize`（1024 进制）会把 ASR 显示成 `226.1 MB`、TTS 显示成 `205.3 MB`，与 UI 文案「约 230MB」「约 215MB」并存在同一界面。
11. **190MB 是注释声明、非实测**：`App.kt:23`「腾出约 190MB」——melo 目录从未入库，无法对账；本总览按计划案要求与 `TTS_TOTAL_BYTES = 215,308,902`（`ModelManager.kt:413`，kokoro 侧可复核常量）分开表述，二者口径不同。
12. **ASR 的 `tokens.txt` 不计进度**：下载时回调被丢弃（`SettingsScreen.kt:613`），「正在下载 tokens…」阶段进度为 0%；TTS 的 `tokens.txt`（1111 字节，`ModelManager.kt:54`）在清单里、计入 `TTS_TOTAL_BYTES`。
13. **索引 README 对照（已回收）**：旧登记称 README「模型下载」职责只写 ASR、未提 TTS 清单与 `cleanupLegacyTts`——2026-10-04 README 第 28 行已补「v1.5.0 起 TTS kokoro 清单 373 个文件（`TTS_TOTAL_BYTES`）+ 启动时 `cleanupLegacyTts` 删旧 melo 目录」，登记作废。README 行归 P-A2 组维护，此处仅对照。
14. **单测现状**：`ModelManagerTtsTest` 1 例只守 TTS 清单（路径不重复、关键文件在、字节数为正、总和等于 `TTS_TOTAL_BYTES`，`ModelManagerTtsTest.kt:12-27`）；HTTP 下载与断点续传本身仍无 JVM 单测，`downloadFileTo` 未抽出可注入的 Transport 接缝（对比 `llm/LlmClient.kt` 的做法）。
15. **`isFileComplete` 仍是死代码**（`:435-436` 生产零调用），改就绪判据时容易只想到 `isModelReady`/`isTtsReady` 而漏掉它。
