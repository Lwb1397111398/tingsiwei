# 笔记处理宿主模块总览

## 模块职责

App 级后台任务宿主（`object NoteProcessor` 单例）：转写、生成、改写三类任务跑在进程级协程作用域里，离开详情页、退到后台、锁屏都不会中断；同一笔记同时只跑一个任务（幂等启动）；各笔记的阶段进度集中在一条 `stages` 状态流，详情页进度条与首页徽章共用；进程被杀后，App 下次启动时按 Room 里的状态把半路任务全部续跑。转写完成后自动接着调生成，不需要用户再点一次。

## 运作流程

**从哪来（三处 `start` 入口 + 两处自动续跑）**：

1. **录音保存后**（状态机产出方）：`RecordSession.stopAndSave()` 先把笔记插进 Room——SYSTEM 模式识别出了文字就 `status = DRAFT` 且 `content` 直接带正文，否则 `status = TRANSCRIBING` 只带 `audioPath`（`record/RecordSession.kt:126`、`:132`）——随即在同一个 `Dispatchers.IO` 协程里调 `NoteProcessor.start(id, NoteProcessor.Kind.TRANSCRIBE)`（`record/RecordSession.kt:140`）。从通知栏点「完成」、保存时页面早已关掉，都会照常触发。
2. **导入音频**：`HomeViewModel.importAudio` 把文件拷进 `files/recordings/` 后插入 `status = TRANSCRIBING, source = IMPORT` 的笔记（`ui/HomeScreen.kt:319-329`，状态在 `:324`），再 `NoteProcessor.start(id, NoteProcessor.Kind.TRANSCRIBE)`（`ui/HomeScreen.kt:331`）。v1.5.0 起导入即开跑，不再要求用户点开一次笔记。
3. **详情页操作**：`DetailViewModel` 里三处显式启动——`generate()` → `start(noteId, Kind.GENERATE)`（`ui/DetailScreen.kt:530`）、`sendSuggestion(text)` → `start(noteId, Kind.REVISE, text)`（`ui/DetailScreen.kt:535`，返回 `true` 才把 `reviseAwaitingResult` 置 true）、`retry()` 按笔记状态分流：无原文且有录音走 `Kind.TRANSCRIBE`，其余走 `Kind.GENERATE`（`ui/DetailScreen.kt:522-524`）。
4. **打开笔记自动续跑**：`DetailScreen` 的 `LaunchedEffect(note?.id, note?.status)` 调 `vm.maybeRunPipeline()`（`ui/DetailScreen.kt:101`）→ `NoteProcessor.maybeRun(noteId)`（`ui/DetailScreen.kt:509`；实现 `pipeline/NoteProcessor.kt:70-86`）：`TRANSCRIBING` 且原文空且有录音 → 重新转写；`DRAFT` → 开始生成；`GENERATING` 且 `mapJson` 为空（生成中途被打断、没有结果）→ 重新生成；`GENERATING` 但旧导图完好 → 不重跑，直接把状态拨回 `READY` 并清 `errorMsg`（`pipeline/NoteProcessor.kt:83-84`）。
5. **App 启动拉起全部半路任务**：`App.onCreate` 调 `NoteProcessor.resumeStuck()`（`App.kt:22`；实现 `pipeline/NoteProcessor.kt:89-104`）：查 `NoteDao.byStatuses(listOf(TRANSCRIBING, GENERATING))`（`data/db/AppDatabase.kt:26-27`），逐条按与 `maybeRun` 相同的规则拉起或拨正。用户手机重启、进程被杀后不用挨个点开笔记。`DRAFT` 状态**不在**启动拉起范围——那表示「还没开始生成」，等用户打开笔记由 `maybeRun` 触发。

**怎么处理（`start` → `runTranscribe` → `runGenerate`）**：

1. **幂等启动**（`pipeline/NoteProcessor.kt:44-63`）：`start(noteId, kind, arg)` 首行拦 `noteId <= 0`（`:45`），然后在 `synchronized(jobs)` 块里查 `jobs[noteId]?.isActive == true`——同笔记已有任务在跑就直接返回 `false`，什么都不做（`:46-47`）；没在跑才 `scope.launch` 一个新任务并把 `Job` 记进 `ConcurrentHashMap<Long, Job>`（`:48-60`）。任务结束时 `finally` 把自己从 `jobs` 移除并清掉进度文案（`:55-58`）。任务收在 object 单例而不是 ViewModel，注释原话：「任务的生命周期必须长于页面」（`:42`）。scope 是 `CoroutineScope(SupervisorJob() + Dispatchers.Default)`（`:29`）——一个任务崩溃不连坐其他任务。
2. **`runTranscribe`**（`:106-137`）：先读笔记，`content` 已非空 → 直接 `runGenerate(noteId)` 返回（`:111-114`）——断点续跑时原文可能已转好只差生成；SYSTEM 模式保存的笔记（`status = DRAFT` + 有正文）也走 `Kind.TRANSCRIBE`、落进这个分支直接生成。否则置 `TRANSCRIBING`、清 `errorMsg`（`:115`），报「正在解码音频…」（`:116`），调 `Transcriber.transcribeOffline(App.get(), audio) { _, msg -> setStage(noteId, msg) }`（`:118-120`）——识别中的进度文案（「正在加载识别模型…」「正在识别…已完成 X%，已识别 N 字（第 M 段）」）由 `transcribe/Transcriber.kt:24`、`:37` 回调产生。识别结果为空 → 抛「没有识别到内容，请检查录音质量；也可到设置里改用「手机自带识别」重新录一次」（`:121-123`）；有结果 → 写回 `content`、状态置 `DRAFT`（`:124`），**紧接着调 `runGenerate(noteId)`（`:125`）——转写完成自动接生成，这就是本模块最关键的一行**。`CancellationException` 原样上抛保证取消立即生效（`:126-127`）；其余异常把笔记置 `ERROR` + `e.message ?: "转写失败"`（`:128-136`）。
3. **`runGenerate` / `runRevise`**（`:139-145`）：每次新建 `Generator(App.get().database, App.get().settings)`，调 `generate(noteId)` 或 `revise(noteId, suggestion)`，进度回调接到 `setStage`。状态从 `DRAFT` 流转 `GENERATING` → `READY`/`ERROR`、覆盖前存 `versions` 版本快照、改写走 `ReviseFlow`，全部发生在生成流水线模块内部，本宿主只负责启动与进度透传。
4. **进度流**：`_stages: MutableStateFlow<Map<Long, String>>`（`:31`）按 noteId 存当前阶段文案；对外 `stages` 整表暴露（`:34`）、`stageFlow(noteId)` 单条暴露（`:36`）。消费方两处：详情页 `busyStage = combine(NoteProcessor.stageFlow(noteId), localStage) { p, l -> l ?: p }`（`ui/DetailScreen.kt:462`，「正在恢复版本…」这类本地小任务优先显示）；首页 `stages[note.id]`（`ui/HomeScreen.kt:88`、`:168`），卡片在 `TRANSCRIBING/GENERATING` 状态下把文案渲染成一行主题色小字（`ui/HomeScreen.kt:232-240`）。

**产出什么**：本模块自己**不落任何文件**；全部持久化发生在下游——`runTranscribe` 写 `notes` 表的 `content`/`status`/`errorMsg`（`:115`、`:124`、`:128-136`），生成与改写的状态流转和 `versions` 快照在 `Generator`（见生成流水线模块总览）。进度文案只在内存 `stages` 里，进程被杀即丢。

## 已知坑与约束

1. **转写完成自动接生成 = 「提取后 LLM 处理慢」的入口**（`NoteProcessor.kt:125`）：转写一完不等用户操作直接进 LLM 生成，用户每次保存录音都必经这段等待。耗时长短由生成流水线模块决定，本宿主不控制调用次数：设置里 `llmStagedThinking`「思路精修」开关**默认关 = 直路一次成稿**（1 次 LLM 调用出 `<导图>+<思路>`），打开才走三段式（起草思路→自查优化→按思路出图，3+ 次串行调用，慢约 3 倍）——分叉点在 `llm/Generator.kt` 的 `stagedOrDirect`（开关读取 `data/SettingsRepository.kt:82`、`:111`，键 `llm_staged_thinking` 定义 `:63`）。嫌慢去设置页关「思路精修」，或在生成流水线模块排查。
2. **互斥只在单笔记粒度**：`jobs` 按 noteId 分桶，N 条笔记同时转写/生成互不等待、没有全局并发上限。LLM 侧的并发压力由 LLM 客户端模块的 `RateGate` 进程级节流闸兜住；转写侧（CPU 密集的本地识别）没有节流，同时导入多个大音频会并行解码。
3. **删除笔记的竞态窗口（静态推断，未实测）**：`HomeViewModel.delete` 先 `NoteProcessor.cancel(note.id)` 再删文件、清断点、删库（`ui/HomeScreen.kt:277-289`）。`cancel` 只是发起协程取消，若此刻恰有一次 `dao.update` 已经飞出，Room 挂起函数的取消检查点之后仍可能完成写入——在已删除笔记上多一次无效写。详情页 `restore()` 的注释记录了同一类风险（`ui/DetailScreen.kt:549`「在飞的那次写库会把恢复结果覆盖掉」）。
4. **恢复语义不对称**：转写没有断点，`resumeStuck`/`maybeRun` 拉起的 `TRANSCRIBING` 任务**从头重转**整段音频；生成有 `SegmentStore` 段断点（`filesDir/pipeline/segments-<noteId>.json`，只补失败段）。另外状态组合不在 `when` 覆盖内时三个入口都不会动它——例如 `TRANSCRIBING` 但 `audioPath` 为 null（`:75`、`:95` 的条件都不满足），或 `TRANSCRIBING` 但 `content` 已有值——永远卡在半路，只能靠详情页 `retry()`（`ui/DetailScreen.kt:522-524`）按内容有无手动分流。
5. **`Kind.TRANSCRIBE` 名不副实的分支**：SYSTEM 模式保存的笔记（`status = DRAFT` + 正文已在）传的是 `Kind.TRANSCRIBE`，实际因 `:111-114` 的 `content` 非空检查只跑生成、不跑转写。看任务类型日志时会误判。
6. **进度文案只在内存**：进程被杀即丢，`resumeStuck` 拉起后从「正在解码音频…」重新报起；转写完成的瞬间（`DRAFT` 写入后、生成开始前）`stages` 里短暂没有该笔记的条目，首页徽章可能闪一下空。
7. **后台跑没有任何通知**：任务在后台推进时用户能看到的只有首页卡片的一行进度小字和详情页进度条；没有通知栏进度、没有完成提醒（录音期间的通知是录音服务模块的，转写/生成不继承）。
8. **静默 return**：`runTranscribe` 开头笔记查不到或 `audioPath` 为 null 就直接 return（`:108-109`），不报错、不置状态——调用方无从感知任务没跑。
