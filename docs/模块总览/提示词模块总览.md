# 提示词模块总览

## 模块职责

`Prompts` 是全工程唯一存放发给 LLM 的中文文本的地方：它同时规定了「每个环节要什么、输出必须长成什么形状」，因此生成流水线、弹性层降级、输出解析器、`TreeText` 树引擎都靠这套约定对齐。

## 运作流程

**从哪来**：三个取词点。①`LlmClient.chat` 固定把 `Prompts.trimRule()` 当作 `degradeRule` 传下去（`LlmClient.kt:52`）；②`Generator` 取 `generateSystem` / `generateUser` / `reviseUser` / `formatReminder`（`Generator.kt:40`、`109-115`、`118`、`178-182`）；③`LongTextPipeline` 取 `outlineSystem` / `outlineUser` / `groupMergeSystem` / `groupMergeUser` / `finalUser` / `generateSystem` / `formatReminder`（`LongTextPipeline.kt:103`、`175-176`、`232`、`236`、`262`、`271`、`277`）。`Prompts` 自己不依赖任何东西，是纯字符串工厂（`Prompts.kt:4`）。

**怎么处理**：按环节分四类。

1. **短内容一次生成（直路）**：`generateSystem(allowExpand)` 作 system（`Generator.kt:178`），`generateUser(content)` 作 user（`Prompts.kt:33`，只是「请整理以下内容：」加原文），温度走 `LlmClient.chat` 的默认 0.4（`LlmClient.kt:41`、`Generator.kt:194-195`），输出上限 `FinalOutTokens = 2048`（`Generator.kt:207`）。
2. **长文流水线的三段**：逐段提炼用 `outlineSystem` + `outlineUser(chunk, seq, total)`，温度 0.2、输出上限 `MergeOutTokens = 1200`（`LongTextPipeline.kt:175-176`、`184`）；分层归并用 `groupMergeSystem` + `groupMergeUser(outlines, title)`，同样 0.2/1200（`LongTextPipeline.kt:232`、`236`、`240`）；最终生成换回 `generateSystem(allowExpand)` 作 system，user 换成 `finalUser(大纲, title)`（`LongTextPipeline.kt:262`、`271`），温度回到 0.4、输出上限是被窗口夹过的 `finalOutTokens`（`LongTextPipeline.kt:70-71`、`273`）。`finalUser` 只喂提炼过的大纲而不是原始长文，这是长文能一次装下的关键（`Prompts.kt:71` 注释）。
3. **AI 修改**：system 仍是 `generateSystem`（让模型知道输出格式），user 换成 `reviseUser(当前 TAB 树, 当前思路, 原文, 用户要求)`（`Generator.kt:109-115`）；当前导图由 `TreeText.fromMapData` 从库里 JSON 反解析回 TAB 缩进树（`Generator.kt:111`）。
4. **两种「加词」路径**：
   - 输出被长度上限截断（`LlmError.Truncated`）→ `chatWithDegrade` 把 `trimRule()` 拼成 `"$system\n$degradeRule"`，**只动 system、只重问一次**，user、温度、`desiredOutTokens` 全部不变（`LlmSession.kt:88-92`）。第二次仍截断才抛给用户（`LlmPolicy.kt:56`）。
   - 模型没按格式出图（`TreeText.parse` 结果为空）→ 把 `formatReminder()` 追加到 **user** 尾部再问一次，动 line 而非 system（`Generator.kt:117-119`、`181-183`；`LongTextPipeline.kt:273-279`）。两处都只重试一次，第二次仍空就报错（`Generator.kt:184-186`；`LongTextPipeline.kt:280-282`）。

**产出什么**：产出「一次 HTTP 请求的 system/user 两段文本」，并规定响应必须可被 `LlmOutputParser.parse` 切成 `mapText`（TAB 缩进树）+ `thinking`（`LlmOutputParser.kt:15`、`21-45`）。

**影响谁**：`LlmOutputParser` 的正则、`TreeText` 的层级解析、`LongTextPipeline` 的预算估算（`generateSystem` 长度直接进入 `useDirectRoute` 与「窗口太小」判定，`LongTextPipeline.kt:88-89`、`103-108`）、以及三个测试类对提示词字面量的字符串匹配（见下）。`outlineSystem`/`groupMergeSystem` 的输出**不带标签**，所以段大纲/中层大纲只作为纯文本被拼接，从不经过解析器（`LongTextPipeline.kt:148`、`248`、`265`）。

## 依赖的上游模块

无。`Prompts.kt` 全文只用 Kotlin 标准库的字符串模板与 `buildString`（`Prompts.kt:64`、`71`、`84`），不 import Android、不 import 序列化、不读设置——`allowExpand`/`title`/`chunk` 全部由调用方作为参数传进来。因此它可以被 JVM 单测直接调用，也是「改提示词不需要重新配置任何依赖」的原因。

反向依赖它的是同层的 `LlmClient`（`LlmClient.kt:52`）、`Generator`（`Generator.kt:40` 等）、`LongTextPipeline`（`LongTextPipeline.kt:103` 等），以及**隐式**依赖其格式约定的两个模块：`mindmap/LlmOutputParser.kt`（标签与围栏容错，`LlmOutputParser.kt:24-44`）与 `mindmap/TreeText.kt`（TAB 缩进树，被 `Generator.kt:56`、`LongTextPipeline.kt:274` 用来判空）。

## 关键数据结构

本模块没有自定义类型，「数据结构」就是**输出格式契约**：

| 契约 | 出处 | 消费方 |
| --- | --- | --- |
| `<导图>` / `</导图>` 与 `<思路>` / `</思路>` 两段，标签独占一行，不套代码块 | `Prompts.kt:21-29` | `LlmOutputParser` 的两条正则 `<\s*导图\s*>([\s\S]*?)<\s*/\s*导图\s*>`（`LlmOutputParser.kt:24-25`） |
| 导图 = 一行一个节点、TAB 缩进表层级、第一行总主题 | `Prompts.kt:14-17` | `TreeText.parse`；多顶层主题由树引擎包虚拟根（`Generator.kt:70` 的 `toMapData`） |
| 节点一般不超过 20 字、思路 200~500 字自然段 | `Prompts.kt:16`、`19` | 只影响 token 体量，无代码校验 |
| 降级时改为「节点 ≤12 字、思路 ≤250 字、节点宁少勿断、标签必须闭合」 | `Prompts.kt:37` | 与上一条**同时存在**于第二次请求（追加式，`LlmSession.kt:91`） |
| 段提炼/归并输出：第一行「小节：<≤12 字概括>」，其后 TAB 缩进，**禁止标签与解释** | `Prompts.kt:46-50`、`59-61` | 被当纯文本累积进 `outlines`/`level`，最终拼进 `finalUser`（`LongTextPipeline.kt:140`、`248`、`265`） |
| 归并输入的 `〔n〕` 分节标记 | `Prompts.kt:67` | 仅提示模型；解析不涉及 |

`allowExpand` 的两个分支文案（`Prompts.kt:8` 允许补充相关知识 vs `Prompts.kt:10` 只整理原文）来自设置里的 AI 拓展开关（`SettingsRepository.kt:29`、`89-91`），由 `cfg.allowExpand` 一路传到 `pipeline.run(..., allowExpand, ...)`（`Generator.kt:53`）。

## 已知坑与约束

1. **索引 README 的覆盖不全**：README「提示词」行写的是「生成/修改/分段提炼/分层归并/最终汇总 + 截断降级规则」，代码里还有第六类——格式纠正提示 `formatReminder()`（`Prompts.kt:40-41`），且它改的是 **user** 尾部而不是 system（`Generator.kt:118`、`LongTextPipeline.kt:277`）。排查「为什么第二次请求内容变了」时容易只盯着 `trimRule`。
2. **两套节点字数阈值会同时生效**：正常请求里是「不超过 20 个字」（`Prompts.kt:16`），降级请求里同时出现 20 字与 12 字两条要求，因为 `chatWithDegrade` 是把 `trimRule` 直接拼到原 system 后面而不是替换（`LlmSession.kt:91`）。这是刻意的（保留原始任务描述），但也意味着提示词内部存在互相冲突的指令。
3. **提示词字面量是测试的路由判据**，改措辞会静默改坏测试：`FakeLLM` 用正则 `第 (\d+)/(\d+) 小段` 判断是不是段提炼调用（`LongTextPipelineTest.kt:43`）、用 `system.contains("更高层的大纲")` 判断是不是归并调用（`LongTextPipelineTest.kt:52`）；`LlmPolicyTest.zz` 用 `user.contains("小段")` 与 `user.contains("份小节大纲")` 分支（`LlmPolicyTest.kt:394-396`）。对应源文案在 `Prompts.kt:54`、`Prompts.kt:58`、`Prompts.kt:66`。把「小段」改成「片段」，这些假实现会一律走到 `else` 分支返回完整导图，测试可能假绿。
4. **`reviseUser` 里的原文截断是字符级的**：`originalContent.take(6000)`（`Prompts.kt:93`）只看字数、不看窗口、不看语言（CJK 与英文按同样 6000 字符算），且提示词自己写了「可截断」（`Prompts.kt:92`）。真正的窗口约束由 `Tokens.fit` 兜底（`LlmSession.kt:50`），所以长原文做 AI 修改时模型看到的「参考原文」只有前 6000 字，界面上不会有任何提示。
5. **`generateSystem` 的长度参与预算判定**，改这句话等于改路由阈值：`useDirectRoute` 用 `estimate(content) + estimate(system) + 2048 <= effectiveWindow` 决定走直路（`LongTextPipeline.kt:88-89`，system 由 `Generator.kt:40,49` 传入真实文本），`run()` 再用它判断「窗口太小装不下提示词」并直接报错、一次都不调用（`LongTextPipeline.kt:103-108`）。`allowExpand` 两个分支长度不同，切换开关会轻微移动这条分界线。
6. **两处提示词体量估算是写死的、不随文案自动更新**：`fitsBudget` 用 `Prompts.generateSystem(true)` 实时估算（`LongTextPipeline.kt:292-295`），但 `finalReserveTokens` 用的是常量 `SystemPromptSlack = 700`（`LongTextPipeline.kt:66-67`、`310-312`，注释自称「粗略体量」）。大幅扩写 `generateSystem` 后必须人工复核 700 这个数，否则最终生成会低估占用、更容易触发 `finalTrimmed`（`LongTextPipeline.kt:266-270`）。
7. **段提炼/归并明确禁止标签**（`Prompts.kt:50`、`61`），因此段大纲文本绝不能喂给 `LlmOutputParser`——它有「最后兜底：整体当作导图」（`LlmOutputParser.kt:44`），一旦误喂会把大纲当成导图而静默通过。代码路径也确实没喂（`LongTextPipeline.kt:148`、`248` 只做拼接）。
8. **格式契约是「三层容错」，所以提示词写坏了不会立刻崩**：要求标签独占一行不用代码块（`Prompts.kt:21`），但解析器会剥围栏（`LlmOutputParser.kt:18-19`）、容忍标签两侧空白（`LlmOutputParser.kt:24-25`）、缺 `</思路>` 时把标签后的全部文本当思路（`LlmOutputParser.kt:30-31`）、还认 markdown 分节标题形式（`LlmOutputParser.kt:36-41`）。好处是宽容，坏处是提示词与解析器的偏离会退化成「看起来能用、结构质量下降」。
9. **没有任何一处要求「用中文输出」**：`generateSystem` 只靠中文提示词本身隐含语言预期，`finalUser` 传的标题/大纲可能中英混排（`Prompts.kt:72-75`）。模型出英文时的唯一出路是错误文案建议换模型（`LongTextPipeline.kt:281`），提示词层没有兜底。
10. **`trimRule` 与预算截断是两套机制**：`trimRule` 靠模型自觉压缩（`Prompts.kt:36-37`），`Tokens.fit` 靠硬截并加尾标（`LlmPolicy.kt:154-178`）。前者只出现在被 `Truncated` 触发的那一次重问里；`Tokens.fit` 的截断发生在每次请求前，二者不会互相通知。
11. **历史坑痕迹（与注释对应）**：`outlineUser` 特意说明「前后另有内容，只需提炼本段」（`Prompts.kt:54`）——针对的是段间上下文缺失导致的重复提炼，配合 `TextChunker` 的 1 句重叠（`TextChunker.kt:26`）与归并提示词的「保持原有先后顺序、不得丢掉术语、数字、法条名和结论」（`Prompts.kt:60-61`）；`groupMergeUser` 的空行拼接与 `〔n〕` 编号（`Prompts.kt:67`）是为了让模型数得清份数，与 `PipelineResult.notice` 里向用户报具体段号形成闭环（`LongTextPipeline.kt:40`）。归并失败时代码把原组 `joinToString("\n\n")` 原样上收（`LongTextPipeline.kt:248`），所以提示词里那句「不要输出解释、标签或代码块」如果失效，脏内容会一路带到最终生成的输入里——这是该兜底策略的已知代价。

**单测覆盖点**

- `LlmPolicyTest.c`：截断降级时第二次请求的 system 必须同时含「体量要求」且以原 system 开头（`LlmPolicyTest.kt:129-140`，断言 `:138-139`）——直接锁住 `trimRule()` 与「追加不替换」两条行为。
- `LlmPolicyTest.c2`：连续截断只重问一次（`LlmPolicyTest.kt:142-151`）。
- `LlmPolicyTest.g3`：`reviseUser` 造出的大输入（`LlmPolicyTest.kt:310`）必须被预算层压进窗口而不是被打断（`LlmPolicyTest.kt:307-317`）。
- `LlmPolicyTest.zz`：假传输层靠提示词字面量分流三种调用，验证三段式提示词在真实会话层上可区分（`LlmPolicyTest.kt:382-418`）。
- `LongTextPipelineTest` 的 `FakeLLM` 靠 `第 x/y 小段` 与 `更高层的大纲` 区分调用类型并统计次数（`LongTextPipelineTest.kt:43-56`），是提示词字面量最密集的用例，覆盖 17 例。
- `LongTextPipelineTest.短内容走直接生成不分段`：`generateSystem(true)` 长度直接进入路由判定（`LongTextPipelineTest.kt:259-266`）。
