# 提示词模块总览

## 模块职责

`Prompts.kt` 是全工程唯一一处存放发给大模型（LLM）的提示词（prompt，即"给 AI 的指令文本"）的地方：一个无状态的 `object`（单例对象），全是纯函数，输入参数 → 输出字符串。它规定了两件事：**让模型做什么**（整理导图/提炼大纲/归并/优化/按建议改图）与**必须回什么格式**（`<导图>` TAB 缩进树 + `<思路>` 记忆叙述，标签独占一行）。任何提示词措辞改动都会直接改变模型行为，且多处措辞是测试假实现的解析锚（见「已知坑」）。

## 运作流程

**从哪来**：提示词按笔记的四条处理路径取用——直路一次成稿、直路三段式（「思路精修」开关）、长文流水线、AI 改写。全部调用点在 `llm/` 包内（本模块不被 UI 直接引用）。

**四条路径各用哪几条**（按数据真实流动顺序）：

1. **直路一次成稿**（默认路径，`Generator.directGenerate`）：`generateSystem(allowExpand)`（`Generator.kt:208`；`Prompts.kt:6-31`，`allowExpand`=设置里"允许知识拓展"开关，决定第一段规则是"可自然补充相关知识"还是"只整理原文讲到的"）+ `generateUser(content)`（`Generator.kt:209`；`Prompts.kt:33`，就一句「请整理以下内容：」）→ 模型没按格式回时，把 `formatReminder()` 追加到 user 尾部重问一次（`Generator.kt:212`；`Prompts.kt:40-41`）。长路总生成也复用这一对 system 与 reminder（`LongTextPipeline.kt:113`、`343`、`368`）。
2. **直路三段式**（开关 `llmStagedThinking` 打开时，`Generator.stagedGenerate`）：① `draftThinkingSystem/User`（`Generator.kt:258`；`Prompts.kt:79-90`——通读原文、按讲解顺序写千字思路草稿、**只梳理不拓展**、输出 `<思路>` 标签）→ ② `refineThinkingSystem(allowExpand)/refineThinkingUser(草稿, 原文)`（`Generator.kt:270-271`；`Prompts.kt:93-120`——对照原文自查（遗漏/顺序/逻辑/概念）重写定稿；`allowExpand` 开时授权补写必要拓展并**在对应句子末尾标「（拓展）」、篇幅 ≤ 原文三分之一**；明确「不要输出自查过程」）→ ③ `mapFromThinkingSystem/User(定稿思路, 标题)`（`Generator.kt:292-293`；`Prompts.kt:146-167`——**只按思路出导图、不新增思路没有的内容、不重写思路**，图文天然一致；「（拓展）」标注的分支要原样带进导图节点 `:151`）；格式不对时 `mapOnlyReminder()` 重问（`Generator.kt:296`；`Prompts.kt:170-171`——**只提导图不提思路**，注释写明：提到思路反而会诱导模型把思路也写一遍）。
3. **长文流水线**（`LongTextPipeline`，`run` 内部）：逐段提炼用 `outlineSystem()` + `outlineUser(chunk, seq, total)`（`LongTextPipeline.kt:194-195`；`Prompts.kt:44-54`——第一行「小节：<≤12 字概括>」、TAB 列要点、保留术语/数字/法条名/例子/结论、**不要思路/标签/解释/代码块**；user 里「这是全文第 i/n 小段（前后另有内容，只需提炼本段）」给模型上下文位置感）→ 归并每层用 `groupMergeSystem()` + `groupMergeUser(组内大纲, 标题)`（`LongTextPipeline.kt:261`、`274`；`Prompts.kt:57-68`——"把相邻内容归并成一份**更高层的大纲**"，保持顺序、合并同类项但不丢硬信息）→ **定稿优化步**用 `refineOutlineSystem(allowExpand)/refineOutlineUser`（`LongTextPipeline.kt:312-313`；`Prompts.kt:123-143`——自查优化成**定稿大纲**，拓展行尾标「（拓展）」且新增行 ≤ 1/3）→ 总生成用 `generateSystem` + `finalUser(大纲, 标题)`（`LongTextPipeline.kt:343`、`362`；`Prompts.kt:71-76`——把录音标题当「主题提示」带进 user，正文是提炼过的大纲而非原文）。
4. **AI 改写**（`ReviseFlow` + `Generator.revise`）：主路径要最小编辑指令——`reviseDiffSystem()`（`ReviseFlow.kt:39`；`Prompts.kt:174-186`——给出带路径编号的树（`1`/`1.2`/`2.3.1` 是节点地址）与思路，要求只输出 `<修改>` 块里的「改/删/加 <路径>」行、**未点名节点逐字保留、绝不顺手润色**；重画子树=先逐条删再逐条加；思路确需同步才在 `</修改>` 后另给 `<思路>`；只有整体重构级改动才放弃指令输出完整 `<导图>+<思路>`）+ `reviseDiffUser(编号树, 思路, 建议)`（`ReviseFlow.kt:40`，编号来自 `MapDiffText.render`，只进提示词不落库）→ 无效输出 `diffReminder()` 重问（`ReviseFlow.kt:44`；`Prompts.kt:203-204`）→ diff 调用的截断降级规则用 `diffTrimRule()`（`Generator.kt:123`；`Prompts.kt:207-208`——指令行 ≤20 条，压不下去就升级全量）→ 两轮都不可用升级全量重发：`reviseUser(当前导图, 当前思路, 原文前 6000 字, 要求)`（`ReviseFlow.kt:94`；`Prompts.kt:215-236`——允许增删改层级重写思路，并要求保留原有「（拓展）」标注）+ system 用 `generateSystem + majorKeepRule`（`Generator.kt:117`；`Prompts.kt:211-212`——「只改涉及的部分，其余逐字保留」硬纪律）。

**截断降级的通用规则**：`LlmClient.chat` 的 `degradeRule` 参数默认值就是 `trimRule()`（`LlmClient.kt:42`；`Prompts.kt:36-37`——节点 ≤12 字、思路 ≤250 字、宁少勿断、标签必须闭合）。被长度上限砍断重问一次时，这条体量要求会被追加进系统提示词（`LlmSession.chatWithDegrade` 实现，用例 `LlmPolicyTest.kt:133-144` 断言第二次请求带「体量要求」四字且保留原系统提示）。

**影响谁**：模型是否按 `<导图>/<思路>` 标签返回（决定 `LlmOutputParser.parse` 走不走兜底路径）、导图节点文字密度、思路长度与拓展有无、改写是走 diff 还是全量。措辞还直接牵动测试假实现的解析（见坑 1/2）。

## 依赖的上游模块

- **无**——本模块零依赖（不 import 工程内其他类、不碰设置/网络/数据库），只输出字符串。
- 被依赖方全在 `llm/`：`Generator.kt`（直路/三段式/改写接线）、`LongTextPipeline.kt`（长路四步）、`ReviseFlow.kt`（改写决策）、`LlmClient.kt`（`trimRule` 作默认降级规则）。
- 参数语义来源：`allowExpand`/`llmStagedThinking` 等设置位由 `SettingsRepository` 读出后由调用方传入；本模块只消费布尔参数，不认识设置类。

## 已知坑与约束

1. **「第 $seq/$total 小段」是测试假实现的解析锚**：`outlineUser` 的这句（`Prompts.kt:54`）被 `LongTextPipelineTest.kt:50` 用正则 `第 (\d+)/(\d+) 小段` 反向解析，用来路由"哪些段要注入失败"。**改措辞 = 全部段级故障注入用例同时失明**（`seq` 解析不出来，假实现会把提炼请求误路由）。
2. **归并与优化步的 system 靠关键词区分**：`FakeLLM` 用 `system.contains("更高层的大纲")` 判归并、`contains("定稿大纲")` 判优化步（`LongTextPipelineTest.kt:57`、`:61`）——锚句分别在 `groupMergeSystem`（`Prompts.kt:58`）与 `refineOutlineSystem`（`Prompts.kt:129`）。同坑 1：改这两句措辞会打乱假实现路由。
3. **「小节：<...>」标题行是流水线的内容约定**：`outlineSystem:46` 要求提炼结果第一行以「小节：」开头，`groupMergeSystem:59`/`refineOutlineSystem:133` 同样保留——大纲拼接与归并装箱都按行处理，丢了这个约定不会崩，但组内条目会失去可读边界。
4. **`mapOnlyReminder` 特意不提「思路」**：三段式第三步只该回导图（`Prompts.kt:170`，注释原话「提到思路反而会诱导模型把思路也写一遍」）——别顺手把它换成通用的 `formatReminder()`。
5. **`fitsBudget` 估算固定用 `generateSystem(true)`**（`LongTextPipeline.kt:408`）：开拓展的 system 更长，属保守高估；估算时用的 `finalUser("", title)` 只取包装开销（`LongTextPipeline.kt:346`）。真实总生成传 `allowExpand` 实值（`:343`）。
6. **两个体量规则不能混**：`trimRule` 管生成/改写的**整次输出**压缩（节点 12 字、思路 250 字）；`diffTrimRule` 管改写 diff 的**指令行数**（≤20 条，超了就升级全量），且只挂在 diff 那条 `chat` 上（`Generator.kt:123`）；全量兜底那条 `chat` 不带 degradeRule（`Generator.kt:126-127`，截断直接 `Fail`）。
7. **提示词无温度/无采样参数**：`Complete` 与 `chat` 签名都不传 temperature（见「LLM客户端与弹性层模块总览.md」），提示词文本是控制模型输出的**唯一**手段——对格式的要求必须写在正文里（标签独占一行、不套代码块、不要解释），别指望参数。
8. **`reviseUser` 的原文只给前 6000 字**（`Prompts.kt:229` `take(6000)`）：全量兜底时模型看不到完整原文，超长录音的改写以当前导图+思路为准——这是体积权衡的既定约束，不是遗漏。
