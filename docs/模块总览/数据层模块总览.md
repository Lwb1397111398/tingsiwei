# 数据层模块总览

## 模块职责

全应用唯一的持久化出入口：`SettingsRepository` 用 DataStore Preferences 存应用设置（基础 9 项，含 LLM 接口配置，API KEY 只存在 `llm_key` 键；2026-10-05 起另有应用自更新 4 个键，见键位表），`AppDatabase` + `Entities` 用 Room 存两张表 `notes`（笔记）与 `versions`（导图版本快照）。

## 运作流程

**从哪来**：`App` 用 `by lazy` 各建一个实例——`database = AppDatabase.create(this)`（`app/src/main/java/com/tingsiwei/app/App.kt:8` → `data/db/AppDatabase.kt:60-63`）、`settings = SettingsRepository(this)`（`App.kt:9`），全局只有这一份，靠 `App.get()` 分发。

**怎么处理（写）**：
- 设置项：设置页每个动作对应一个 setter——`setLlm`（`app/src/main/java/com/tingsiwei/app/ui/SettingsScreen.kt:347`、`360`）、`setTranscribeMode`（`SettingsScreen.kt:388`）、`setAllowExpand`（`393`）、`setTtsRate`（`398`，详情页另有一处 `ui/DetailScreen.kt:668`）、`setLlmLimits`（`SettingsScreen.kt:418`）；写库前做 `trim()`（`data/SettingsRepository.kt:71-73`）与 `coerceIn` 夹取（`SettingsRepository.kt:79-80`）。
- 笔记插入：录音保存（`record/RecordSession.kt:126-136`）、首页导入音频（`ui/HomeScreen.kt:305-315`）、文字录入两条分支（`ui/TextInputScreen.kt:97-106` 生成路径 / `137-148` 粘贴导图路径）。
- 笔记更新：生成链路集中改状态（`llm/Generator.kt:34`、`37`、`76`、`83`、`105`、`128`、`138`、`167`），详情页改转写/导图/原文（`ui/DetailScreen.kt:488`、`501`、`515`、`524`、`529`、`569`）。
- 版本快照：只有 `Generator` 写——重新生成前存旧导图（`llm/Generator.kt:60-67`）、`revise` 前存（`96`）、恢复版本前再存当前（`152`）。
- 删除：`noteDao().delete(note)`（`ui/HomeScreen.kt:275`），删前先手动清音频文件（`HomeScreen.kt:264-266`）与分段落盘缓存（`HomeScreen.kt:272`）。

**产出什么**：`files/../databases/tingsiwei.db`（库名见 `AppDatabase.kt:61`）与 DataStore 文件 `settings`（store 名见 `SettingsRepository.kt:16`）。读侧全部是响应式：`settings: Flow<AppSettings>`（`SettingsRepository.kt:53-65`）+ 一次性 `current()`（`67`）、`noteDao().observeAll()`（`AppDatabase.kt:17-18`）、`observeById()`（`23-24`）、`versionDao().observeForNote()`（`41-42`），另有 `byId` 同步快照读（`20-21`、`44-45`）。

**影响谁**：首页列表与搜索（`ui/HomeScreen.kt:257-260`）、详情页三块内容（`ui/DetailScreen.kt:443-445`）、LLM 请求参数与限流策略（`llm/LlmClient.kt:60-74`、`llm/Generator.kt:39-47`）、转写方式选择（`record/RecordSession.kt:66`、`ui/RecordScreen.kt:203`）、TTS 语速（`ui/DetailScreen.kt:464`、`658`）。

### 状态机取值（`NoteStatus`，`Entities.kt:9-15`）

`DRAFT` 已录入未生成（`10`）、`TRANSCRIBING` 转写中（`11`）、`GENERATING` 生成中（`12`）、`READY` 完成（`13`）、`ERROR` 出错（`14`）。实际写入点不构成严格线性链：
- 进 `DRAFT`：录音且系统识别已有文字（`record/RecordSession.kt:131`）、文字生成路径（`ui/TextInputScreen.kt:102`）、离线转写完成（`ui/DetailScreen.kt:524`）。
- 进 `TRANSCRIBING`：录音无现成文字（`record/RecordSession.kt:131`）、导入音频（`ui/HomeScreen.kt:310`）、详情页补转写（`ui/DetailScreen.kt:515`）。
- 进 `GENERATING`：`llm/Generator.kt:37`（generate 开始）、`105`（revise 开始）。
- 进 `READY`：`llm/Generator.kt:76`、`128`、`167`（恢复版本）、粘贴导图直接入库（`ui/TextInputScreen.kt:142`）、`ui/DetailScreen.kt:489`、`501`（异常态兜底恢复）。
- 进 `ERROR`：`llm/Generator.kt:34`（无内容）、`83`（生成失败）、`92`（无导图可改）、`138`（改图失败）、`ui/DetailScreen.kt:530`（转写失败）。
- 界面映射：`ui/HomeScreen.kt:236-240` 把 5 个值翻成「已完成/生成中…/转写中…/待生成/出错」+ 不同底色；`ui/DetailScreen.kt:129`、`141`、`160` 分别处理进行中、出错、READY 带提示。

## 已知坑与约束

1. **Room 无任何迁移，且是破坏性策略**：`version = 1`（`AppDatabase.kt:54`）、`fallbackToDestructiveMigration()`（`62`），代码里没有 `addMigrations(...)`、没有 `Migration` 对象；`exportSchema = false`（`54`）导致仓库里没有 schema JSON 快照可比对（`app/schemas/` 不存在）。将来给 `notes`/`versions` 加字段而漏写迁移，用户全部笔记会被静默清空。索引 README 第 10 行只强调「version=1 未改动」，没提这条破坏性回退。
2. `NoteDao.insert` 用 `OnConflictStrategy.REPLACE`（`AppDatabase.kt:29-30`）：传入带非 0 `id` 的实体时是整行替换而不是报错，未列出的字段会丢；现有调用点都靠 `id` 默认 0 走自增（`record/RecordSession.kt:126`、`ui/HomeScreen.kt:305`、`ui/TextInputScreen.kt:97`、`137`），改成「就地编辑」时有踩雷风险。`VersionDao.insert` 则没有冲突策略（`47-48`）。
3. `NoteDao.search(q)`（`AppDatabase.kt:26-27`）是死代码：全项目零调用，首页搜索是把 `observeAll()` 全量拉进内存再 `filter`（`ui/HomeScreen.kt:257-260`）。笔记一多，内存过滤 + 每次表变更重查会先成为瓶颈，SQL 侧的 `LIKE` 索引能力完全没用上。
4. `notes` 表没有任何索引与外键（`Entities.kt:24-43` 只有 `@Entity(tableName = "notes")`），`ORDER BY updatedAt DESC`（`AppDatabase.kt:17`）是全表排序；`versions` 才有 `Index("noteId")`（`Entities.kt:55`）。
5. 版本快照只增不减：`VersionDao.delete`（`AppDatabase.kt:50-51`）无人调用，`Generator` 每次重新生成/改图/恢复都插一条（`llm/Generator.kt:60`、`96`、`152`），每条含完整 `mapJson`（`Entities.kt:61`）。唯一清理是删整条笔记时靠外键 `CASCADE`（`Entities.kt:52`）连带删除。
6. `versions` 的删除依赖数据库级联，但 `mapJson` 的父行删除走的是 `noteDao().delete(note)`（`ui/HomeScreen.kt:275`）；音频文件与分段缓存是**手工**删的（`HomeScreen.kt:264-272`），不走数据库——任何新增的删除入口若忘记这两步，就会留下孤儿文件（缓存清理包在 `try/catch (_: Exception)` 里，失败会静默）。
7. `audioPath` 存的是绝对路径（`record/RecordSession.kt:134` 的 `file.absolutePath`、`ui/HomeScreen.kt:312`），App 数据被系统清理后路径失效；转写时只按 `n.audioPath ?: return` 静默退出（`ui/DetailScreen.kt:514`），不会把状态从 `TRANSCRIBING` 改成 `ERROR`，界面会停在「正在转写…」（`ui/DetailScreen.kt:302`）。
8. 空串是合法设置值：`llmUrl`/`llmKey`/`llmModel` 缺省即 `""`（`SettingsRepository.kt:55-57`），数据层没有「是否已配置」的判定；地址合法性要到调用侧才校验，`LlmEndpoint.normalize` 会自动补 `https://` 与 `/v1`，空地址返回空串并由 `LlmClient.endpoint` 抛 `LlmError.BadUrl`（`llm/LlmPolicy.kt:95-102`、`llm/LlmClient.kt:56-57`）。
9. 边界值夹取有两道且不完全等价：写库时 `coerceIn(MinContextWindow, MaxContextWindow)`、`coerceIn(0L, MaxMinIntervalMs)`（`SettingsRepository.kt:79-80`，常量为 `2048`/`1_000_000`/`60_000L`，`98-100`），读取后又各夹一次（`llm/LlmClient.kt:67-71`）。绕开 setter 直接写 DataStore 的旧值不会报错，只会被静默夹取；保守模式不在数据层折算，存的是用户原值，减半/翻倍发生在 `llm/LlmPolicy.kt:134-138`。
10. `Context.dataStore` 是**顶层私有扩展属性**（`SettingsRepository.kt:16`），`preferencesDataStore` 委托要求每个进程名唯一且全局单例；当前只有这一个 store 名 `settings`，新增 store 时必须同样放在顶层，否则会在 `app/src/main/java/com/tingsiwei/app/data/SettingsRepository.kt:16` 之外再产生第二份委托实例。
11. 敏感信息的备份面：`llm_key` 是 DataStore 明文首选项（无加密层），而 `AndroidManifest.xml:12` 的 `allowBackup="true"` 且未提供 `fullBackupContent`/`dataExtractionRules` 资源，设置文件会进入系统自动备份。本文档只描述这一存在方式与读取路径，不涉及取值。
12. 状态字段是裸 `String` 常量而非枚举/`@TypeConverter`（`Entities.kt:9-22`、`30-31`），编译期无法阻止写入未知值；首页 `StatusChip`（`ui/HomeScreen.kt:234`）对 5 个已知值给了中文标签与底色（`HomeScreen.kt:236-240`），未匹配值走 `else -> status to surfaceVariant`（`HomeScreen.kt:241`）——脏数据会把原始英文状态串直接显示出来，而不是报错。
13. **索引 README 与本模块的差异**：README 第 10 行「数据层」条目说位置是 `data/db/`（Room：notes、versions 表，version=1 未改动）、`data/SettingsRepository.kt`（DataStore），与代码一致；其列举的设置项「LLM 地址/KEY/模型、转写方式、AI 拓展开关、语速、上下文窗口/请求间隔/保守模式」共 9 项，与 `AppSettings` 的 9 个字段严格一一对应（`SettingsRepository.kt:25-36`），但 README 未提到这三项的边界常量与默认值来源（`SettingsRepository.kt:97-101` ← `llm/LlmPolicy.kt:111-112`），也提到「笔记、版本快照」两张表 ✓。README 第 13 行说段成果「纯文件，不动 Room」，与代码一致：Room 只有 `notes` + `versions` 两实体（`AppDatabase.kt:54`），段缓存写在 `files/pipeline`（`llm/Generator.kt:45`）。README 第 13 行给的状态机是「DRAFT→TRANSCRIBING→GENERATING→READY/ERROR」的线性描述，代码里存在跳过中间态的写入：粘贴导图直接 `READY`（`ui/TextInputScreen.kt:142`）、导入直接 `TRANSCRIBING`（`ui/HomeScreen.kt:310`）、恢复版本直接 `READY`（`llm/Generator.kt:167`）、详情页兜底 `GENERATING→READY`（`ui/DetailScreen.kt:489`），且 `READY + errorMsg` 被复用为提示位（`ui/DetailScreen.kt:160`）——这是文档需要留意的「非单向」状态机。
