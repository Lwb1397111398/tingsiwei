# 生成流水线模块总览

## 模块职责

把一条笔记的转写/粘贴原文变成 `<导图>+<思路>`：短内容默认一次调用直出（设置里开「思路精修」才走三段式），长内容按 token 预算语义分段 → 逐段提炼 → 最多两层归并 → 一次总生成，全程不超上下文窗口、成果落盘可断点续跑、失败段可解释，最后写 Room 并维护版本快照与笔记状态机。

## 运作流程

**从哪来**：`DetailScreen` 的 `DetailViewModel` 三处入口——`generate()` → `generateInternal()`（`ui/DetailScreen.kt:539-551`）、`sendSuggestion()` → `revise()`（`ui/DetailScreen.kt:553-562`）、`restore()` → `restoreVersion()`（`ui/DetailScreen.kt:574-582`）；另有 `maybeRunPipeline()` 在打开笔记时自动续跑未完成流程（`ui/DetailScreen.kt:472-493`）。三者都 `new Generator(db, settingsRepo)`，进度回调把文案写进 `busyStage`，由顶部的进度条区渲染（`ui/DetailScreen.kt:129-140`）。

**怎么处理**：`Generator.generate(noteId, onStage)`（`Generator.kt:29-85`）按顺序做这些事。

1. 取笔记，原文空 → 直接 `ERROR` +「没有可用的内容」并返回（`Generator.kt:31-36`）；否则置 `GENERATING` 且清 `errorMsg`（`Generator.kt:37`）。
2. 读设置，构造 `LongTextPipeline`：`complete` 是把 `client.chat(cfg.llmUrl, cfg.llmKey, cfg.llmModel, ...)` 包起来的闭包（`Generator.kt:42-44`），`store` 落在 `filesDir/pipeline`（`Generator.kt:45`），并把 `contextWindow`/`conservative` 传进去（`Generator.kt:46-47`）。这就是 `Complete` 接缝（`LongTextPipeline.kt:8-10`）——它让流水线可以被假实现直接单测，而不需要 Android 环境。
3. **路由阈值**：`useDirectRoute(content, system, FinalOutTokens)` 判据是 `estimate(content) + estimate(system) + 2048 <= effectiveWindow`（`LongTextPipeline.kt:88-89`），`effectiveWindow = max(windowFor(contextWindow, conservative), 1024)`（`LongTextPipeline.kt:63`）。装得下就走直路；默认上下文窗口 131072 下几乎所有真实录音都走直路，长文流水线只在内容超约 12.8 万 token（或用户手动调小窗口）时才触发。
   - **直路默认一次成稿**：`stagedOrDirect` 开头 `if (!cfg.llmStagedThinking) return directGenerate(cfg, content)`——1 次 chat 出 `<导图>+<思路>`，`TreeText.parse` 为空则带 `formatReminder()` 再问一次，仍空则报「AI 没有按格式返回导图」（`Generator.kt` 直路段）。
   - **「思路精修」开关打开时走三段式**（`StagedFlow.kt`，2026-09-30 引入）：① 起草思路（输出上限 `DraftOutTokens=6144`，提示词要求约千字）→ ② 对照原文自查优化出定稿思路（`RefineOutTokens=8192`，会把原文+草稿再发一遍）→ ③ 只按定稿思路出导图（`FinalOutTokens=2048`）。至少 3 次串行调用，慢约 3 倍；任一步失败逐级兜底（优化失败拿草稿继续、出图失败退回一次成稿），窗口装不下三段（`StagedFlow.fits`）也直接退一次成稿。设置项 `llmStagedThinking` 默认 `false`（2026-10-03 加开关：三段式让每次生成从 1 次调用变 3+ 次，是「提取后 LLM 处理很慢」的主因）。
4. **长路 `pipeline.run`**（`LongTextPipeline.kt:91-170`）：
   - 先体检：`effectiveWindow < estimate(system) + 512 + InputSlack` 就抛「上下文窗口太小……装不下提示词和输出」，**一次都不调用**（`LongTextPipeline.kt:103-108`，用例 `LongTextPipelineTest.kt:209-221`）。
   - 分段：`TextChunker.plan(content, chunkTargetTokens, maxChunks, maxChunkTokens)`（`LongTextPipeline.kt:109`）。预算三元的公式在 `LongTextPipeline.kt:66-76`：`finalReserveTokens = min(2048+700, window/2)` 且不低于 `MergeOutTokens/2=600`；`maxChunkTokens = max(window - finalReserveTokens, 256)`；`chunkTargetTokens = min(maxChunkTokens, max(window*0.28, 256))`；`maxChunks = conservative ? 6 : 12`。按此公式推得默认 16384 非保守窗口下三个数分别约为 `finalReserveTokens=2748`、`maxChunkTokens=13636`、`chunkTargetTokens=4587`。
   - 逐段提炼：命中缓存就复用并回报「已复用第 i/n 段的断点成果」，否则回报「正在提炼第 i/n 段…」并调 `askOutline`（`LongTextPipeline.kt:115-124`）。温度 0.2、输出上限 `MergeOutTokens=1200`（`LongTextPipeline.kt:184`）。
   - 归并：`while (!fitsBudget(level) && levels < MaxReduceLevels)` 最多两层 `mergeLevel`（`LongTextPipeline.kt:148-153`），每层按 `maxChunkTokens` 装箱分组，逐组一次调用并回报「正在汇总第 i/N 组（第 L 层）…」（`LongTextPipeline.kt:210-251`）。`MaxReduceLevels = 2`（`LongTextPipeline.kt:306-307`，注释写明「写成常量而非无限递归，避免层数失控」）。
   - 总生成：`finalGenerate` 回报「正在汇总生成导图…」，把大纲拼成 `finalUser`，必要时截断并如实记 `trimmed`，温度 0.4、输出上限 `finalOutTokens`（`LongTextPipeline.kt:70-71`、`255-284`）。
5. **产出与写库**：`PipelineResult`（`LongTextPipeline.kt:12-49`）→ 回 `Generator` 后先 `TreeText.parse` 校验非空（`Generator.kt:56-57`）→ **覆盖前存一份版本快照**（`Generator.kt:58-69`）→ `toMapData` 写 `mapJson`/`thinking`/`virtualRoot`，状态 `READY`，并把 `notice()` 当 `errorMsg` 一起写（`Generator.kt:70-80`）。任何异常 → `ERROR` + `friendly(e)`（`Generator.kt:81-84`）。

**影响谁**：Room 的 `notes`

**改写链路（最小化编辑，2026-09-30 重做）**：`Generator.revise`（`Generator.kt:87`）先照旧存快照、置 `GENERATING`，决策交给 `ReviseFlow.run`（`ReviseFlow.kt:38`）。流程：原树经 `MapDiffText.render` 渲染成带路径编号的行（编号只进提示词不落库）→ `Prompts.reviseDiffSystem/User` 向模型要**一份 `<修改>` 指令块**（`chat` 的 `degradeRule` 换成 `diffTrimRule`，见 `LlmClient.kt:42`）→ `ReviseOutput.classify` 三态判定（`MapEdit.kt`）：见到 `<修改>` 走 diff；见到 `<导图>` 或 markdown 分节即模型自判整体重构、直接按全量采纳；都没有算无效，附 `diffReminder()` 重问一次。diff 指令由 `MapEdit.parseAll` 解析（`改/删/加` 单行三种，非法行计入忽略），`MapEditApplier` **先把所有路径对原树解析、再统一执行**删→摘链→改→加，未被点名的节点逐字不变，应用后空图整批拒收转兜底。diff 截断按行抢救：`dropIncompleteLastLine` 丢掉未闭合尾行、完整行照常应用——半截整图永远不覆盖完好旧图（`ReviseFlow.kt:47`）；应用/忽略数量经 `errorMsg` 在 READY 态显示为提示。两轮 diff 都不可用才自动兜底：按现行全量形态 `reviseUser` + `generateSystem` 拼 `majorKeepRule`（只改涉及部分、其余逐字保留）重发一次；全量仍截断则 `ReviseResult.Fail` 报「输出太长被截断…拆小一点再试」（`Generator.kt:144-161`）。

**影响谁**：Room 的 `notes`（状态、导图、思路、errorMsg）与 `versions`（快照，`Entities.kt` 的 `VersionEntity`）两张表；`filesDir/pipeline/segments-<noteId>.json` 断点文件（删笔记时由首页一并清理，`ui/HomeScreen.kt:269-274`）；详情页顶部条（进度 / 出错重试 / READY 带提示时的「补全」按钮，`ui/DetailScreen.kt:141-179`）；首页状态标签（`ui/HomeScreen.kt:236-240`）；`saveMap` 只在 READY 写库以避免与生成流程互相覆盖（`ui/DetailScreen.kt:565-572`）。

| --- | --- | --- |

| `ChunkPlan(chunks, noBoundary, targetTokens, chunkCapExceeded)` | `TextChunker.kt:12-22` | `targetTokens` 回传收敛后实际采用的块预算；`size` 即段数 |

| `PipelineResult.Stats` | `LongTextPipeline.kt:25-33` | `segmentCalls/reduceCalls/finalCalls` 与派生 `totalCalls`，外加 `reusedSegments`、`maxInputTokens`（后者被断言必须 ≤ 窗口，`LongTextPipelineTest.kt`/`LlmPolicyTest.kt:413-416`） |
| `Complete` | `LongTextPipeline.kt:8-10` | `fun interface`，签名带 `temperature` 与 `desiredOutTokens`，让流水线能自己定温度（0.2 提炼/归并、0.4 总生成） |

| 指纹算式 | `SegmentStore.kt:77-81` | `sha1(content + "\u0000" + params)` 的十六进制；`params` 实参是 `"$chunkTargetTokens\|$maxChunks\|$maxChunkTokens"`（`LongTextPipeline.kt:110`） |
| 计数器（实例字段） | `LongTextPipeline.kt:78-85` | `segmentCalls/reduceCalls/finalCalls/reusedSegments/maxInputTokens/failureHint/consecutiveFatal/consecutiveFailed`，`run()` 开头全部重置（`LongTextPipeline.kt:98-101`） |
| 收手与层数常量 | `LongTextPipeline.kt:305-322` | `MaxReduceLevels=2`、`MergeOutTokens=1200`、`FinalOutTokens=2048`、`SystemPromptSlack=700`、`InputSlack=512`、`MaxConsecutiveFatal=2`、`MaxConsecutiveFailedSegments=3` |
| `NoteStatus` 常量 | `data/db/Entities.kt:9-15` | `DRAFT`/`TRANSCRIBING`/`GENERATING`/`READY`/`ERROR`，字符串常量而非 enum |

**「连续 N 段失败即收手」的两个不同数值**（易混，都在 `LongTextPipeline.kt:316-321` 有注释）：

- `MaxConsecutiveFatal = 2`：**不可重试**错误（401/404/坏格式/空内容/截断等）连续 2 段 → 抛 `LlmException` 停手（`LongTextPipeline.kt:200-205`、`125-126`）。段内 `repeat(2)` 的第二次尝试遇到不可重试错误会直接跳过（`LongTextPipeline.kt:181`、`189`），所以「连续两段被拒」恰好只有 2 次 HTTP 调用（用例 `LongTextPipelineTest.kt:140-153` 断言 `fake.calls == 2`；穿真实客户端的等价用例在 `LlmPolicyTest.kt:420-450`）。
- `MaxConsecutiveFailedSegments = 3`：**可重试**错误打满重试后仍失败的段连续 3 段 → 抛「连续 3 段都没能提炼成功……已停止以免继续浪费接口额度。稍后可点「补全」从断点继续」（`LongTextPipeline.kt:128-136`）。单段最多 2 次调用，因此最坏 6 次（用例断言 `fake.calls <= 3 * 2`，`LongTextPipelineTest.kt:268-281`）。成功一段即清零（`LongTextPipeline.kt:138`）。
- 偶发一段不可重试错误只跳过那一段，不中止整篇（`LongTextPipelineTest.kt:170-180`）。

**调用次数**：段数 N（每段 1 次，可重试错误/空返回则 2 次）+ 归并每层组数（层 ≤ 2）+ 总生成 1 次（格式不对再 1 次）。四万字长文在「每 4 次调用里第 2 次抛 429」的注入下，断言总调用 ≤ 60 且必须大于 `maxChunks`（`LongTextPipelineTest.kt:73-90`，断言在 `:83`、`:88`；故障注入在 `:46`）。进度回报共 4 类文案 + 直路 1 类：`LongTextPipeline.kt:120`、`123`、`235`、`261`；`Generator.kt:50`。

**状态机流转位置**：`DRAFT` 由录入侧产出（`ui/TextInputScreen.kt:102`；录音侧转写完成时 `if (content != null) NoteStatus.DRAFT else TRANSCRIBING`，`record/RecordSession.kt:131`）；`TRANSCRIBING` 由导入/转写前置（`ui/HomeScreen.kt:310`、`ui/DetailScreen.kt:515`）；`GENERATING` 只出现在 `Generator.kt:37`（生成）与 `Generator.kt:105`（修改）；`READY` 在 `Generator.kt:76`、`128`、`167`；`ERROR` 在 `Generator.kt:34`、`83`、`92`、`138`。旁路：`ui/TextInputScreen.kt:142` 用户直接粘贴 TAB 树时本地转导图、跳过 LLM 直接 `READY`；`ui/DetailScreen.kt:487-491`（修改被打断但旧导图完好）与 `:500-505`（「修改失败」提示的清除）会把状态拨回 `READY`。`READY` 时 `errorMsg` 语义是「提示」而非错误（`Generator.kt:77` 写入 `notice()`，`ui/DetailScreen.kt:160-179` 渲染成「补全」按钮）。

**语义分段规则细节**：三级退级——强边界 `。！？；!?;\n` → 弱边界 `，,、：: 空格` → 按 token 折算的字符硬切（`TextChunker.kt:31-32`、`116-135`、`152-162`）；每块严格不超 `target`（`TextChunker.kt:79-105`）；只带 1 句重叠（`OVERLAP_SENTENCES = 1`，`TextChunker.kt:26`），且重叠 token 必须 ≤ `target/4` 才带（`OverlapShareOfTarget = 4`，`TextChunker.kt:28-29`、`85`）；块数超过 `maxChunks` 时按比例放大 `target` 重试，最多 5 轮、绝不越过 `maxTargetTokens` 上限（`TextChunker.kt:51-66`），仍超就置 `chunkCapExceeded = true`；`stripped()` 去掉各块开头的重叠句后拼接应等于 `trim()` 后的原文（`TextChunker.kt:21`）。

## 已知坑与约束

1. **索引 README 说指纹是「`sha1(内容)+参数`」，代码实际把参数一起喂进哈希**：`sha1(content + "\u0000" + params)`（`SegmentStore.kt:77-81`），不是「sha1(内容) 再拼参数」。含义一致（两者都变即失效），但按 README 去手算/复现指纹会算不出来。
2. **README 未给出「连续 N 段失败」的数值**，代码里其实是**两个不同的计数**（2 与 3，`LongTextPipeline.kt:316-321`），且一个是「不可重试段数」、一个是「失败段数」，语义不同；把两者当同一个数会误判停手时机。
3. **`noBoundary` 在两条路径下含义不同**：单块路径它是「全文没有强边界标点」（`TextChunker.kt:49`、`36`），多块路径它其实是「发生过字符硬切」（`TextChunker.kt:54`、`59` 取的是 `atomize` 的 `hardCut`）。而 `PipelineResult.notice()` 一律渲染成「转写文字缺少标点，分段质量受影响」（`LongTextPipeline.kt:44`）。用例 `TextChunkerTest.kt:140-147` 锁住了后者（有逗号时不该报无边界）。
4. **首尾空白也会让断点整体作废**：指纹喂的是**未 trim 的** `note.content`（`LongTextPipeline.kt:110`），而分块喂的是 `text.trim()`（`TextChunker.kt:44`）。只加一个换行也会重算全部段。
5. **段缓存以「段号」为 key，靠参数指纹保证不错位**：`params` 含 `chunkTargetTokens|maxChunks|maxChunkTokens`（`LongTextPipeline.kt:110`），三者随 `contextWindow` 与 `conservative` 变化（`LongTextPipeline.kt:63`、`74-76`），所以中途改窗口/开关会让旧断点整体失效而不是错配——这是正确性设计，代价是白打若干段。`allowExpand` 与标题**不**进指纹，但因为段提炼提示词与它们无关（`Prompts.kt:44-51`），复用仍安全。
6. **`consecutiveFatal`/`consecutiveFailed` 是实例可变状态**（`LongTextPipeline.kt:84-85`），只在 `run()` 开头重置（`LongTextPipeline.kt:98-101`）。同一个 `LongTextPipeline` 实例并发跑两次会互踩计数；现状安全仅因为 `Generator.generate` 每次新建实例（`Generator.kt:41`）。
7. **归并是否继续的判据用的是 `maxChunkTokens` 而不是 `effectiveWindow`**（`LongTextPipeline.kt:292-295`），且估算 system 固定用 `generateSystem(true)`——`allowExpand=false` 时是保守高估。
8. **归并失败的兜底是「原样上收」**（`LongTextPipeline.kt:247-248`），内容不丢但预算可能仍超；真装不下时由 `finalGenerate` 截断并置 `finalTrimmed`，明确告诉用户「汇总时截掉了后半部分，建议在设置里调大上下文窗口或关掉保守模式」（`LongTextPipeline.kt:46`、`263-270`）——注释原话是「不留给下游静默截」。
9. **只有零失败段才清断点文件**（`LongTextPipeline.kt:156`）：有失败段时故意留着，「补全」才能只补那几段（用例 `LongTextPipelineTest.kt:107-124`：续跑仅 1 次段调用、复用 total-1 段、全部成功后文件消失）。
10. **`SegmentStore` 全线吞异常**：`load` 任何异常 → 空 map（`SegmentStore.kt:23-28`），`save` 失败静默（`SegmentStore.kt:64-66`，注释「断点存储失败不影响本次生成，只是下次要从头提炼」），`clear` 也吞（`SegmentStore.kt:69-74`）。落盘走 `tmp` + `renameTo`，改名失败再直写（`SegmentStore.kt:54-63`）。单个坏条目跳过而不整份作废（`SegmentStore.kt:35-41`，注释即此意），但指纹不符是整份作废（`SegmentStore.kt:33`）。
11. **`directGenerate` 不产生任何提示**（`Generator.kt:187` 返回 `notice = null`）。而 `useDirectRoute` 只算 `content + system + 2048`（`LongTextPipeline.kt:88-89`），没算 `generateUser` 的「请整理以下内容：」前缀（`Prompts.kt:33`）——临界长度上仍可能被 `Tokens.fit` 截掉输入尾巴而不告知。长路的同类风险才有 `finalTrimmed` 兜底。
12. **历史坑痕迹（注释里的「为什么这么写」）**：
    - `SegmentStore` 类注释「写文件而不是动 Room schema（数据库版本保持 1，避免无法验证的迁移）」（`SegmentStore.kt:12-15`）。
    - `TextChunker.build` 第 94-102 行的「放弃重叠」块，注释「光靠重叠就已经装不下下一句：放弃重叠，保证每块严格不超 target」；对应测试注释直接写着「**老实现会照拼，块就超预算并被下游静默截断**」（`TextChunkerTest.kt:96-97`），用例 `TextChunkerTest.kt:94-109`。
    - 死循环防线两处：装填时 `curPieces.size > carry.size`（`TextChunker.kt:80`、`107`）与单句超长时强制向前推进（`TextChunkerTest.kt:171-177`）。
    - `askOutline` 的分诊注释「KEY/地址/坏格式类错误重试没有意义，再打一次也只是浪费」（`LongTextPipeline.kt:188`）与「连续多段都是不可重试错误 = 配置/额度问题，停手；偶发一段坏就只跳过那一段」（`LongTextPipeline.kt:200-201`）。
    - `Generator` 的三条快照注释：「覆盖前存一份快照：重新生成绝不能把用户手动整理过的导图弄丢」（`Generator.kt:58`）、「修改前存版本快照，可回退」（`Generator.kt:95`）、「回退前把当前状态也存一份快照，方便再切回来」（`Generator.kt:150`）。
    - `revise` 失败必须带「修改失败」前缀，因为界面上的「重试」只清提示、不重跑整篇生成（字面量在 `Generator.revise` 的 `ReviseResult.Fail` 分支 `Generator.kt:147` 与两个异常分支 `:159`/`:166`，与 `ui/DetailScreen.kt` 的 `startsWith("修改失败")` 判据成对；改动任一处字面量都会破坏这个约定）。改写走新链路后（见「改写链路」），前缀语义原样保留。
    - `PipelineResult.notice()` 注释把四类提示逐条列明（`LongTextPipeline.kt:35`），`Stats.maxInputTokens` 存在的唯一目的就是让「每次请求都在窗口内」可被断言（`LongTextPipeline.kt:297-299`；`LongTextPipelineTest.kt` 多处、`LlmPolicyTest.kt:413-416`）。
