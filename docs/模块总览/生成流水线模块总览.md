# 生成流水线模块总览

## 模块职责

把一条笔记的转写/粘贴原文变成 `<导图>+<思路>`：短内容默认一次调用直出（设置里开「思路精修」才走三段式），长内容按 token 预算语义分段 → 逐段提炼 → 最多两层归并 → 定稿前优化步 → 一次总生成，全程不超上下文窗口、成果落盘可断点续跑（段级与归并组级）、截断能抢救、失败段可解释，最后写 Room 并维护版本快照与笔记状态机。任务的**执行宿主**是 App 级 `pipeline/NoteProcessor`（见「笔记处理宿主模块总览.md」），本模块是它调用的生成器本体。

## 运作流程

**从哪来**：`pipeline/NoteProcessor.runGenerate/runRevise` 各自 `new Generator(db, settingsRepo)`（`NoteProcessor.kt:139-145`），进度回调经 `setStage` 写进 `stages` 流（`NoteProcessor.kt:147-149`）；触发链：`DetailScreen.generate/retry/sendSuggestion`（`ui/DetailScreen.kt:529`/`:512`/`:533`）、打开笔记自动续跑 `NoteProcessor.maybeRun`（`:70-86`）、App 启动批量恢复 `resumeStuck`（`:89-104`）、转写完成同栈自动接生成（`:112`/`125`）。唯一例外：`restoreVersion` 仍由详情页本地直调（`ui/DetailScreen.kt:554`）。

**怎么处理**：`Generator.generate(noteId, onStage)`（`Generator.kt:29-85`）按顺序做这些事。

1. 取笔记，原文空 → 直接 `ERROR` +「没有可用的内容」并返回（`Generator.kt:31-36`）；否则置 `GENERATING` 且清 `errorMsg`（`Generator.kt:37`）。
2. 读设置，构造 `LongTextPipeline`：`complete` 是把 `client.chat(cfg.llmUrl, cfg.llmKey, cfg.llmModel, ...)` 包起来的闭包（`Generator.kt:42-44`），`store` 落在 `filesDir/pipeline`（`Generator.kt:45`），并把 `contextWindow`/`conservative` 传进去（`Generator.kt:46-47`）。这就是 `Complete` 接缝（`LongTextPipeline.kt:8-10`，签名只有 `system/user/desiredOutTokens`——**请求体已不含 temperature**，由用例 `LlmPolicyTest.kt:593`「m6 请求体不得携带temperature」守门）——它让流水线可以被假实现直接单测，而不需要 Android 环境。
3. **路由阈值**：`useDirectRoute(content, system, FinalOutTokens)` 判据是 `estimate(content) + estimate(system) + desiredOutTokens <= effectiveWindow`（`LongTextPipeline.kt:96-97`，`FinalOutTokens = 16384` 在 `LongTextPipeline.kt:429`），`effectiveWindow = max(windowFor(contextWindow, conservative), 1024)`（`LongTextPipeline.kt:68`）。装得下就走直路；默认上下文窗口 131072 下内容不超过约 11.4 万 token 都走直路，长文流水线只在超长内容（或用户手动调小窗口）时才触发。
   - **直路默认一次成稿**：`stagedOrDirect` 开头 `if (!cfg.llmStagedThinking) return directGenerate(cfg, content)`（`Generator.kt:237`）——`directGenerate`（`Generator.kt:207-222`）1 次 chat 出 `<导图>+<思路>`，`TreeText.parse` 为空则带 `formatReminder()` 再问一次（`Generator.kt:211-213`），仍空则报「AI 没有按格式返回导图」（`Generator.kt:214-216`）。调用被 `parseOrSalvage` 包着（`Generator.kt:308-320`）：截断异常带回的部分内容能解析出导图结构就接着用并附提示「输出超出长度上限，已尽量保留……」（`Generator.kt:217-221`），抢救不出才上抛。
   - **「思路精修」开关打开时走三段式**（`stagedGenerate`，`Generator.kt:249-284`；纯逻辑在 `StagedFlow.kt`）：① 起草思路（输出上限 `DraftOutTokens=6144`，提示词要求约一千字，`StagedFlow.kt:10`）→ ② 对照原文自查优化出定稿思路（`RefineOutTokens=8192`，`StagedFlow.kt:13`，会把原文+草稿再发一遍）→ ③ 只按定稿思路出导图（`mapFromThinking`，`Generator.kt:287-300`，出不来结构返回 null）。至少 3 次串行调用，慢约 3 倍；任一步失败逐级兜底：优化失败拿草稿继续（`Generator.kt:275-280`）、出图失败退回一次成稿（`Generator.kt:283`）、起草截断用带回的部分正文（`Generator.kt:260-261`，`StagedFlow.thinkingText` 容错截断标签）；窗口装不下三段（`StagedFlow.fits`，`StagedFlow.kt:23-27`）也直接退一次成稿（`Generator.kt:238-239`）。设置项 `llmStagedThinking` 默认 `false`（2026-10-03 加开关：三段式让每次生成从 1 次调用变 3+ 次，是「提取后 LLM 处理很慢」的主因）。
4. **长路 `pipeline.run`**（`LongTextPipeline.kt:99-189`）：
   - 先体检：`effectiveWindow < estimate(system) + LlmPolicy.MIN_OUTPUT_TOKENS(512) + InputSlack` 就抛「上下文窗口太小……装不下提示词和输出」，**一次都不调用**（`LongTextPipeline.kt:113-118`，用例 `LongTextPipelineTest.kt:219-232`）。
   - 分段：`TextChunker.plan(content, chunkTargetTokens, maxChunks, maxChunkTokens)`（`LongTextPipeline.kt:119`）。预算推导在 `LongTextPipeline.kt:71-80`：`finalReserveTokens = min(FinalOutTokens+700, window/2)` 且不低于 `MergeOutTokens/2=2048`；`maxChunkTokens = max(window - finalReserveTokens, 256)`；`chunkTargetTokens = min(maxChunkTokens, max(window*0.28, 256))`；`maxChunks = conservative ? 6 : 12`。另有一个**最终生成输出上限** `finalOutTokens = (finalReserveTokens - 700).coerceIn(512, FinalOutTokens)`（`LongTextPipeline.kt:75-76`）。按此公式推得默认 131072 非保守窗口下：`finalReserveTokens=17084`、`maxChunkTokens=113988`、`chunkTargetTokens=36700`、`finalOutTokens=16384`。
   - 逐段提炼：命中缓存就复用并回报「已复用第 i/n 段的断点成果」，否则回报「正在提炼第 i/n 段…」并调 `askOutline`（`LongTextPipeline.kt:127-155`）；输出上限 `MergeOutTokens=4096`（`LongTextPipeline.kt:428`——注释写明旧值 1200 让推理模型在「想」的环节就撞顶，是截断报错的最主要来源，`:424-427`）。提炼截断时带回的部分大纲照样能用（`LongTextPipeline.kt:206-213`）。
   - 归并：`while (!fitsBudget(level) && levels < MaxReduceLevels)` 最多两层 `mergeLevel`（`LongTextPipeline.kt:162-168`），每层按 `maxChunkTokens` 装箱分组（`:245-259`），逐组一次调用并回报「正在汇总第 i/N 组（第 L 层）…」（`:263-296`）。**归并组成果按成员内容寻址进断点缓存**（`fingerprintForGroup`，`:264-272`；续跑命中回报「已复用归并断点：第 i/N 组」`:270`），归并结果被截断也直接用（`:281-283`）。`MaxReduceLevels = 2`（`LongTextPipeline.kt:421-422`，注释「写成常量而非无限递归，避免层数失控」）。
   - **定稿优化步**：`refineOutline`（`LongTextPipeline.kt:305-332`，2026-09-30 后新增）把归并后的大纲整体自查优化一遍（遗漏/归组/层级，`allowExpand` 开时按需拓展并标「（拓展）」）。窗口装不下 `system+user+RefineOutTokens` 直接原样跳过（`:314-316`）；调用失败返回原大纲（`:327-331`）——绝不让优化步把已到手的大纲弄丢。回报文案按拓展开关二选一（`:317`）。
   - 总生成：`finalGenerate` 回报「正在汇总生成导图…」，拼 `finalUser`（`LongTextPipeline.kt:336-375`）。**输出预算随大纲体量抬升**：大纲装得下窗口时 `out = (大纲token × FinalOutRatio 0.6).coerceIn(finalOutTokens, min(window/2, 剩余空间))`（`:350-355`）；装不下时维持 `finalOutTokens` 并截断输入、如实记 `trimmed`（`:356-361`，注释「不留给下游静默截」）。`formatReminder()` 重问一次仍无结构才报「AI 没有按格式返回导图」（`:364-373`）。最终调用包在 `callOrSalvage` 里（`:382-399`）：截断能抢救出结构就置 `outputTruncated`（`:388-393`）；可重试错误在这里多试一次——「前面几十趟都熬过来了，定稿最不能白跑」（`:394-395`）。
5. **产出与写库**：`PipelineResult`（`LongTextPipeline.kt:12-54`）→ 回 `Generator` 后先 `TreeText.parse` 校验非空（`Generator.kt:55-56`）→ **覆盖前存一份版本快照**（`Generator.kt:57-68`）→ `toMapData` 写 `mapJson`/`thinking`/`virtualRoot`、状态 `READY`、`notice()` 当 `errorMsg` 一起写（`Generator.kt:69-80`），并 `setLastGoodModel(cfg.llmModel)` 记下本次成功的模型名（`Generator.kt:70`，供失败时 `withLastGoodHint` 提示「上次成功用的是 X」，`Generator.kt:337-342`）。任何异常 → `ERROR` + `withLastGoodHint(friendly(e))`（`Generator.kt:81-84`）。

**改写链路（最小化编辑，2026-09-30 重做）**：`Generator.revise`（`Generator.kt:87-174`）先照旧存快照、置 `GENERATING`，决策交给 `ReviseFlow.run`（`ReviseFlow.kt:38`）。流程：原树经 `MapDiffText.render` 渲染成带路径编号的行（编号只进提示词不落库）→ `Prompts.reviseDiffSystem/User` 向模型要**一份 `<修改>` 指令块**（`chat` 的 `degradeRule` 换成 `diffTrimRule`，`Generator.kt:119-124`）→ `ReviseOutput.classify` 三态判定（`MapEdit.kt`）：见到 `<修改>` 走 diff；见到 `<导图>` 或 markdown 分节即模型自判整体重构、直接按全量采纳；都没有算无效，附 `diffReminder()` 重问一次。diff 指令由 `MapEdit.parseAll` 解析（`改/删/加` 单行三种，非法行计入忽略），`MapEditApplier` **先把所有路径对原树解析、再统一执行**删→摘链→改→加，未被点名的节点逐字不变，应用后空图整批拒收转兜底。diff 截断按行抢救：`dropIncompleteLastLine` 丢掉未闭合尾行、完整行照常应用——半截整图永远不覆盖完好旧图（`ReviseFlow.kt:47`）；应用/忽略数量经 `errorMsg` 在 READY 态显示为提示。两轮 diff 都不可用才自动兜底：按现行全量形态 `reviseUser` + `generateSystem` 拼 `majorKeepRule`（只改涉及部分、其余逐字保留）重发一次；全量仍截断则 `ReviseResult.Fail` 报「输出太长被截断……拆小一点再试」（`Generator.kt:144-162`）。

**影响谁**：Room 的 `notes`（状态、导图、思路、errorMsg）与 `versions`（快照，`Entities.kt` 的 `VersionEntity`）两张表；`filesDir/pipeline/segments-<noteId>.json` 断点文件（删笔记时由首页一并清理，`ui/HomeScreen.kt:277` 停任务、`:286` 清断点）；详情页顶部状态条（进度 / 出错重试 / READY 带提示时的「补全」按钮，`ui/DetailScreen.kt:133-188`）；首页角标与阶段文案（`ui/HomeScreen.kt:232-236`、`:250`）；`saveMap` 只在 READY 写库以避免与生成流程互相覆盖（`ui/DetailScreen.kt:538-546`）。

**「连续 N 段失败即收手」的两个不同数值**（易混，都在 `LongTextPipeline.kt:440-444` 有注释）：

- `MaxConsecutiveFatal = 2`：**不可重试**错误（401/404/坏格式/空内容等）连续 2 段 → 抛 `LlmException` 停手（`LongTextPipeline.kt:227-231`、`137`）。段内 `repeat(2)` 的第二次尝试遇到不可重试错误会直接跳过（`LongTextPipeline.kt:199-200`、`216`），所以「连续两段被拒」恰好只有 2 次 HTTP 调用（用例 `LongTextPipelineTest.kt:150-164` 断言 `fake.calls == 2`；穿真实客户端的等价用例在 `LlmPolicyTest.kt:486-519`）。
- `MaxConsecutiveFailedSegments = 3`：**可重试**错误打满重试后仍失败的段连续 3 段 → 抛「连续 3 段都没能提炼成功……已停止以免继续浪费接口额度。稍后可点「补全」从断点继续」（`LongTextPipeline.kt:141-148`）。单段最多 2 次调用，因此最坏 6 次（用例断言 `fake.calls <= 3 * 2`，`LongTextPipelineTest.kt:278-292`）。成功一段即清零（`LongTextPipeline.kt:150`）。
- 偶发一段不可重试错误只跳过那一段，不中止整篇（`LongTextPipelineTest.kt:180-191`）。

**调用次数**：段数 N（每段 1 次，可重试错误/空返回则 2 次）+ 归并每层组数（层 ≤ 2，续跑命中缓存 0 次）+ 优化步 1 次（装不下/失败则 0）+ 总生成 1 次（格式不对再 1 次）。四万字长文在「每 4 次调用里第 2 次抛 429」的注入下，断言总调用 ≤ 60 且必须大于 `maxChunks`（`LongTextPipelineTest.kt:83-101`；该注入是 `FakeLLM.failEvery`，判定行 `:51`）。进度回报共 6 类：`LongTextPipeline.kt:132`（复用段）、`135`（提炼）、`270`（复用归并组）、`273`（汇总）、`317`（优化，按拓展开关两文案）、`342`（总生成）；直路三段式另 3 类：`Generator.kt:255`、`265`、`282`。

**状态机流转位置**：`DRAFT` 由录入侧产出（`ui/TextInputScreen.kt:102`；录音侧转写完成时 `if (content != null) NoteStatus.DRAFT else TRANSCRIBING`，`record/RecordSession.kt:132`；宿主转写成功也写 `DRAFT`，`pipeline/NoteProcessor.kt:124`）；`TRANSCRIBING` 由导入/转写前置（`ui/HomeScreen.kt:324`、`pipeline/NoteProcessor.kt:115`）；`GENERATING` 只出现在 `Generator.kt:37`（生成）与 `Generator.kt:105`（修改）；`READY` 在 `Generator.kt:76`、`138`、`197`；`ERROR` 在 `Generator.kt:34`、`83`、`92`、`146`、`159`、`168`。旁路：`ui/TextInputScreen.kt:142` 用户直接粘贴 TAB 树时本地转导图、跳过 LLM 直接 `READY`；`pipeline/NoteProcessor.kt:83-84`（打开笔记时发现修改被打断但旧导图完好，拨回 `READY`；App 启动批量为 `:97-100`）与 `ui/DetailScreen.kt:517-520`（「修改失败」提示的清除）也会把状态拨回 `READY`。`READY` 时 `errorMsg` 语义是「提示」而非错误（`Generator.kt:77` 写入 `notice()`，`ui/DetailScreen.kt:169-187` 渲染成「补全」按钮）。

**语义分段规则细节**：三级退级——强边界 `。！？；!?;\n` → 弱边界 `，,、：: 空格` → 按 token 折算的字符硬切（`TextChunker.kt:31-32`、`116-135`、`152-162`）；每块严格不超 `target`（`TextChunker.kt:79-105`）；只带 1 句重叠（`OVERLAP_SENTENCES = 1`，`TextChunker.kt:26`），且重叠 token 必须 ≤ `target/4` 才带（`OverlapShareOfTarget = 4`，`TextChunker.kt:28-29`、`85`）；块数超过 `maxChunks` 时按比例放大 `target` 重试，最多 5 轮、绝不越过 `maxTargetTokens` 上限（`TextChunker.kt:51-66`），仍超就置 `chunkCapExceeded = true`；`stripped()` 去掉各块开头的重叠句后拼接应等于 `trim()` 后的原文（`TextChunker.kt:21`）。

## 已知坑与约束

1. **指纹公式已对账**（旧版此坑记录「README 写 `sha1(内容)+参数` 易被读成先哈希再拼参数」——README 2026-09-20 已改成带分隔符的准确写法，本坑销案）：代码实际是 `sha1(content + "\u0000" + params)`（`SegmentStore.kt:99-102`），内容与参数一起进哈希、两者任一变化断点即失效。
2. **「连续 N 段失败」是两个不同的计数**（README:21 数值已对上：2 与 3）：一个是「不可重试错误连续段数」（`MaxConsecutiveFatal = 2`），一个是「提炼失败连续段数」（`MaxConsecutiveFailedSegments = 3`，`LongTextPipeline.kt:440-444`）；语义不同，把两者当同一个数会误判停手时机。
3. **`noBoundary` 在两条路径下含义不同**：单块路径它是「全文没有强边界标点」（`TextChunker.kt:49`、`36`），多块路径它其实是「发生过字符硬切」（`TextChunker.kt:54`、`59` 取的是 `atomize` 的 `hardCut`）。而 `PipelineResult.notice()` 一律渲染成「转写文字缺少标点，分段质量受影响」（`LongTextPipeline.kt:48`）。用例 `TextChunkerTest.kt:140-147` 锁住了后者（有逗号时不该报无边界）。
4. **首尾空白也会让断点整体作废**：指纹喂的是**未 trim 的** `note.content`（`LongTextPipeline.kt:120`），而分块喂的是 `text.trim()`（`TextChunker.kt:44`）。只加一个换行也会重算全部段。
5. **段缓存以「段号」为 key，靠参数指纹保证不错位**：`params` 含 `chunkTargetTokens|maxChunks|maxChunkTokens`（`LongTextPipeline.kt:120`），三者随 `contextWindow` 与 `conservative` 变化（`LongTextPipeline.kt:68`、`71-80`），所以中途改窗口/开关会让旧断点整体失效而不是错配——这是正确性设计，代价是白打若干段。`allowExpand` 与标题**不**进指纹，但因为段提炼提示词与它们无关（`Prompts.kt:44-54`），复用仍安全。归并组缓存键则按**成员内容**寻址（`SegmentStore.kt:105-107`），段数漂移不会串组。
6. **`consecutiveFatal`/`consecutiveFailed` 等计数器是实例可变状态**（`LongTextPipeline.kt:83-93`），只在 `run()` 开头重置（`LongTextPipeline.kt:106-111`）。同一个 `LongTextPipeline` 实例并发跑两次会互踩计数；现状安全仅因为 `Generator.generate` 每次新建实例（`Generator.kt:41`）。
7. **归并是否继续的判据用的是 `maxChunkTokens` 而不是 `effectiveWindow`**（`fitsBudget`，`LongTextPipeline.kt:407-410`），且估算 system 固定用 `generateSystem(true)`——`allowExpand=false` 时是保守高估。
8. **归并失败的兜底是「原样上收」**（`LongTextPipeline.kt:288-295`），内容不丢但预算可能仍超，且原样上收的结果**不进断点**（下次还给它归并的机会，`:288` 注释）；真装不下时由 `finalGenerate` 截断并置 `finalTrimmed`，明确告诉用户「汇总时截掉了后半部分，建议在设置里调大上下文窗口或关掉保守模式」（`LongTextPipeline.kt:50`、`356-361`）——注释原话是「不留给下游静默截」。
9. **只有零失败段才清断点文件**（`LongTextPipeline.kt:172`）：有失败段时故意留着，「补全」才能只补那几段（用例 `LongTextPipelineTest.kt:117-135`：续跑仅 1 次段调用、复用 total-1 段、全部成功后文件消失）。
10. **`SegmentStore` 全线吞异常**：`load` 任何异常 → 空快照（`SegmentStore.kt:26-31`），`save` 失败静默（`SegmentStore.kt:86-88`，注释「断点存储失败不影响本次生成，只是下次要从头提炼」），`clear` 也吞（`SegmentStore.kt:91-96`）。落盘走 `tmp` + `renameTo`，改名失败再直写（`SegmentStore.kt:79-85`）。单个坏条目跳过而不整份作废（`SegmentStore.kt:37-50`，注释即此意），但指纹不符是整份作废（`SegmentStore.kt:36`）。**旧格式文件没有 `merge` 字段按空处理**（`SegmentStore.kt:37`、`45`），v1.5.0 前的老断点文件不会崩、只是没有组级续跑。
11. **直路的截断抢救也会产生提示**：`directGenerate` 在 `parseOrSalvage` 抢救成功时返回「输出超出长度上限，已尽量保留生成的导图……」（`Generator.kt:217-221`）——旧说法「直路不产生任何提示」已作废。但 `useDirectRoute` 只算 `content + system + 16384`（`LongTextPipeline.kt:96-97`），没算 `generateUser` 的「请整理以下内容：」前缀（`Prompts.kt:33`）——临界长度上仍可能被 `Tokens.fit` 截掉输入尾巴而不告知。长路的同类风险才有 `finalTrimmed`/`outputTruncated` 兜底。
12. **历史坑痕迹（注释里的「为什么这么写」）**：
