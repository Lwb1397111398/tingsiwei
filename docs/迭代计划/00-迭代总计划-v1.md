# 「听的思维」迭代总计划 v1

> 目标：修掉"长录音就报错 HTTP 429"及其背后的根因（机械拆分、无弹性、假进度、失败不可续跑），
> 迭代到稳定后产出 APK 并推送 GitHub。私人自用，不考虑商业化。

---

## 一、现状诊断（证据到代码行）

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| P1 | 429 不重试也不退避 | `llm/Generator.kt:215-229` `callWithRetry` 只在 message 含 `"HTTP 5"` 时重试 1 次；`llm/LlmClient.kt:110` 任意非 2xx 直接 `throw LlmException` | 长录音 → 分段多 → 串行请求撞渠道 RPM/TPM → 整篇笔记 ERROR |
| P2 | 只重试一次、无节流闸 | 同上，无任何"最小请求间隔 / 并发上限 / 全局闸门" | 分段数越多越容易自触发限流（自己打自己） |
| P3 | 文本机械拆分 | `Generator.kt:177-213` `splitChunks` 固定 `chunkSize=3500` 字符硬切，**零重叠**、不看句/语义边界、把段落内换行 `trim` 抹平 | 一句话被劈成两半，段间上下文丢失，逐段提炼质量差 |
| P4 | 汇总阶段二次超长 | `Generator.kt:156-164` 把 N 段大纲用 `"——第 i 段——"` 机械拼接后**一次性**喂给 merge | 1 小时课 → 十几个 chunk → merge 输入本身又超长 → 再撞 429 / 截断，越修越炸 |
| P5 | 无 token 预算 | `Generator.kt:26-27` 用字符数拍脑袋；`LlmClient.chat` 的 `maxTokens` 参数存在但**调用方从不传**（`Generator.kt:222`） | 输出无上限 → 渠道按 max 截断（`finish_reason=length`）→ 标签残缺 → 解析失败 → 又整篇重跑 |
| P6 | 不识别截断/空返回 | `LlmClient.kt:116-131` 只取 `choices[0].message.content`，从不读 `finish_reason` | 截断结果被当成完整结果入库，导图缺枝 |
| P7 | 失败不分级、不可续跑 | `Generator.kt:54-57` 统一 catch → `NoteStatus.ERROR`，逐段提炼结果不落盘 | 第 7 段 429 → 前 6 段白跑，重试从零开始 |
| P8 | 音频机械切块 | `transcribe/AudioDecode.kt:17-22` `chunkSeconds=15` 固定时长切块 → `Transcriber.kt:31-38` 逐块识别后简单换行拼接 | SenseVoice 是整句离线模型，15s 硬切会切断词与句、边界丢字、句间无衔接 |
| P9 | 进度是假的 | `Transcriber.kt:38` `onProgress(0f, ...)` 直接丢弃 `AudioDecode` 已算出的真实进度（`AudioDecode.kt:127`） | 长录音时用户看到 0% 与"已识别 N 字"，体感像卡死 |
| P10 | 错误文案不可读 | `Generator.kt:231-236` `friendly` 把 HTTP body 前 400 字（一坨 JSON）直接甩到界面 | 用户无法判断该做什么 |
| P11 | 工程无版本控制 | `E:\engine\tingsiwei` 不是 git 仓库；根目录残留 `hs_err_pid16812.log`/`replay_pid16812.log`（JVM 崩溃日志） | 无法回滚；无法推送 GitHub |

**根因一句话**：整条链路按"固定尺寸切块 + 一次性串行调用 + 失败即终态"设计，
而真实渠道有限流、模型有上下文窗口 → 长录音必然触发 P1→P4 的连锁失败。

## 二、迭代总目标（成功判据）

1. 1 小时录音（约 8000–15000 字转写）在**有限流渠道**上稳定产出导图+思路；429 时自动退避恢复，不整篇重来。
2. 长文分段带重叠与语义边界；汇总走**递归分组**，任何一次 LLM 调用输入都不超预算。
3. 任一环节失败 → 保留已完成成果 + 从断点继续；错误提示是可执行的自然语言。
4. 全程真实进度（转写按已解码时长、生成按已完成段数）。
5. 单元测试全绿；`assembleDebug` 出包；回归确认既有功能（录音服务/导图拖拽/版本回退/TTS/导出）未被破坏。
6. 交付 APK + 更新 `docs/模块总览` 与 `使用说明.md` + git 仓库推送 GitHub。

## 三、拆解为小计划（每项独立评分 ≥90 才开工）

### M1 LLM 弹性层（`llm/LlmClient.kt`、新增 `llm/LlmPolicy.kt`）
- 错误分级：`RateLimited(429)` / `ServerError(5xx)` / `Network` / `Timeout` / `BadFormat` / `EmptyContent` / `Truncated`，取代裸 `LlmException`。
- 重试策略：`maxRetries`（默认 5）+ 指数退避（1s→2→4→8→16，封顶 60s）+ **抖动**；优先读 `Retry-After` 头，其次解析 body 里的 `reset`/`wait` 秒数。
- 全局节流闸：进程内 `Semaphore(1)` + 上次请求时间戳，保证相邻请求 ≥`minIntervalMs`（默认 1200ms，设置页可调）；并发请求排队而非齐发。
- 上下文预算：`estimateTokens()`（CJK≈1 字/token，拉丁≈4 字符/token）；请求前算 `input + max_tokens ≤ contextWindow`，超预算拒绝并交给上层拆分；`max_tokens` 按剩余预算自动填。
- 读 `finish_reason`：`length` → 视为 `Truncated`，可带"请精简/只输出导图"降级重问一次。
- 可测性：抽 `transport` 接口（注入假实现 + 假时钟），JVM 单测覆盖退避序列、Retry-After、预算计算、截断。
- 验收：新增 ≥8 个单测；旧 `chat()` 调用点全部通过编译且行为兼容（`revise` 也走新策略）。

### M2 语义分段（新增 `llm/TextChunker.kt`，替换 `Generator.splitChunks`）
- 先按句末标点（。！？；!?;\n）断句，再贪心装填到 `targetTokens`，**相邻块重叠 1 句**（携带上文），绝不切断句子。
- 保留原始换行结构（转写文本的分行是有意义的，当前实现 `trim` 抹平）。
- 无标点长流（ASR 未落标点）→ 按逗号退级 → 再按字符硬切，并打 `noBoundary` 标记供上层提示。
- 块数上限：`maxChunks`；超限时自动升 `targetTokens` 合并，避免请求数失控（这直接治 P2 的"自己打自己"）。
- 验收：单测 ≥10 例（中文多句、中英混排、超长无标点、纯短文本、恰好等于预算、重叠不重复计字、块序稳定可还原）。

### M3 递归汇总（`Generator.produceMapAndThinking`、`llm/Prompts.kt`）
- 分段提炼输出**结构化中间结果**（每段：小标题 + 要点 + 关键原句），而非自由大纲。
- reduce 改为**分组递归**：每 `K` 段（默认按 token 预算推）合并为一份中层摘要，逐层上收，直到落入一次最终生成调用的预算内 → 彻底消除 P4。
- 段间传递"上一段结论尾句"，保住跨段连贯。
- 单段失败：记录并跳过（末尾提示"第 X 段未纳入"），不再整篇失败 → 与 M5 的续跑配合。
- 进度真实：`已完成段/总段数` 上抛给 UI。
- 验收：40000 字合成转写 + 注入假 429 的端到端 JVM 测试，产出非空合法导图，且失败段可在续跑时补齐。

### M4 静音对齐切块（`transcribe/AudioDecode.kt`、`Transcriber.kt`）
- 自研能量 VAD：在解码流上找短静音（默认 ≥220ms 低能量）作为切点，块长目标 12–20s 区间内取静音点，**块间 0.3s 重叠**；无静音点才回退固定时长。
- 拼接去重：重叠区文字若与上块尾部相同则去重，避免重复字。
- 释放：复用同一个 `OfflineRecognizer`（当前每笔记新建/释放，长音频没问题但多笔记频繁重载模型 → 加轻量缓存 + 显式释放）。
- 真实进度：把 `AudioDecode` 的 `onProgress` 接通到 UI（治 P9）。
- 验收：解码纯函数部分（VAD 边界选择、重叠计算、去重）抽成可 JVM 测试的逻辑并覆盖；APK 装上后录音功能回归。

### M5 断点续跑与状态机（`data/db/`、`Generator`、`DetailScreen`）
- 新增 `pipeline` 进度记录（笔记表加列或伴生表，Room 版本 +1 + 迁移）：已完成的段索引、段结果、上次失败原因。
- ERROR 态区分"可续跑"与"需重来"；详情页提供「从断点继续」按钮；`TRANSCRIBING/GENERATING` 中允许取消且不脏写。
- 错误文案：自然语言 + 建议动作（如"渠道限流中，已保留前 5 段成果，60 秒后自动继续"）。
- 验收：迁移测试（老库升级不丢数据）；UI 文案回归。

### M6 整体质量检测
- `testDebugUnitTest` 全绿 + `assembleDebug` 出包 + 回归清单逐项勾（录音前台/后台 1h、暂停继续、导入音频、文字直输、粘贴导图、拖拽改结构、AI 修改、版本回退、TTS、导出 MD、深色模式、模型断点下载）。
- 交叉影响审查：M1 改了 client → 检查 `revise()`/设置页"测试连接"/"获取模型列表"三条调用路径；M2/M3 改了 pipeline → 检查 `TreeText`/`LlmOutputParser` 契约；M4 改了音频 → 检查导入文件与系统识别两条支路。
- AI 代码质量评审 ≥90 分（正确性/可读性/无重复/错误处理/性能/测试覆盖）。

### M7 交付
- 清掉 `hs_err_*.log`/`replay_*.log`，加 `.gitignore`（build/.gradle/.kotlin/local.properties/密钥）。
- `git init` + 首次提交 + 建 GitHub 私有仓库 + 推送（推送前向你确认）。
- 产出 release/debug APK，复制到工作目录并命名 `听的思维-安装包-v<版本号>.apk`；更新 `使用说明.md`（新增限流自动重试、断点续跑说明）与 `docs/模块总览/README.md`。

## 四、执行顺序与门禁

```
M1 → 单测 → M2 → 单测 → M3 → 端到端测试 →（M1+M2+M3 = 大功能"长录音不再炸"整体回归）
   → M4 → 单测 + 录音回归 → M5 → 迁移测试 →（M4+M5 = 大功能"转写与续跑"整体回归）
   → M6 总质检 ≥90 → M7 打包推送
```
每个 M：先出小计划 → AI 评分 ≥90（不足则按建议改到 ≥90）→ 实现 → 代码/策略 AI 质量评分 ≥90 → 单测/回归 → 下一个 M。

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| 渠道 RPM 极低，退避仍不够 | 节流闸间隔 + `maxChunks` 上限 + 设置页"保守模式"（段数少、间隔大） |
| 无 gradle 网络（依赖已在本地缓存） | 构建用 `--offline`；新增依赖一律避免（VAD/token 估算全部自研纯 Kotlin） |
| Room 迁移出错毁数据 | 迁移前 `fallbackToDestructiveMigration` 禁用，写迁移并在单测里验证 schema；开发期先手动备份 db |
| 我无法真人录音 | 用合成 PCM + 合成超长转写文本做可重复的自动化验证；真人长录音最终由你实测（文档中标注） |
| 20 轮额度 | 每轮并行多文件改动 + 后台构建，评审用子代理并行 |
