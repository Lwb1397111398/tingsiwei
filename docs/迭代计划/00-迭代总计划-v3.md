## 已修的 BLOCKERS

**B1 — T4 的 `planSpeechCuts(pcm: FloatArray, …)` 必然 OOM（v2 第 77 行）**
`AudioDecode` 的存在理由就是不能整体载入（1h ≈ 830MB，`AudioDecode.kt:8-9`；现在只累积 `srcRate*chunkSeconds` 个 short，`:49-51`，边解边排空 `:54-77`）。整体传 FloatArray 等于把它删了。
→ **改为流式有界设计**：决策函数只接收"当前已累积的缓冲区"，不接收整条音频：
```
fun pickCut(buffer: FloatArray, len: Int, sampleRate: Int,
            targetSamples: Int, maxSamples: Int, minSilenceSamples: Int, thresh: Float): Int
```
返回本次出块的结束位置（找不到静音就返回 `maxSamples`，保证硬上限），调用方切完后 `System.arraycopy` 保留尾部（沿用现有 `:72-77` 的保留逻辑）。
缓冲区峰值 = `maxSamples`（30s@16k float ≈ 1.9MB），与音频总时长无关 → 内存有界。
`SpeechCutTest` 直接测这个纯函数（合成静音/无静音/全静音/极短/单句/尾部不足），
另加断言：任何输入下返回值 ∈ [target 的下界, maxSamples]，且返回值 > 0（防死循环）。
`AudioDecode.kt:72-77` 的尾部保留改写是 T4 的**必做子项**，不能只测纯函数就收工——用"短于一个块的音频必须出且只出一块、切完后可还原样本数"的集成断言覆盖（纯 JVM 可测，不需要设备）。

**B2 — `SegmentStore` 从不失效（v2 第 65 行）**
`DetailScreen.kt:505` 会覆盖 `note.content` 后立即重生成；`:453-466` 进程重启后还会自动续跑。旧 `segments-<noteId>.json` 会把上一版文本的大纲复用到新文本上 → 静默产出错导图并持久化。
→ 文件名不变，**内容带指纹**：`{fingerprint, chunkParams, segments}`，
`fingerprint = sha1(content) + targetTokens + maxChunks + overlapSentences`。
`doneIndices()` 只在指纹完全一致时返回，否则返回空集并重写文件。
→ T3 验收新增可证伪用例：**(d) 写入 3 段 → 用不同 content 的指纹重载 → `doneIndices()` 为空**。

**B3 — 预算不变式会打断现成的 revise 流程（v2 第 46 行 T1(g)）**
`Prompts.kt:70` 的 revise 已经带 `originalContent.take(6000)` + 全量当前导图 + 思路；默认 `contextWindow=8192 - maxOut 2048` 只剩 6144，**每次 revise 都会踩线**。`Generator.kt:26` 的 `maxDirectChars=5000` 同理。
→ 预算从"硬失败"改为**四级降级，永不阻断请求**：
1. 先压输出：`maxOut = min(desiredOut, cw - estIn)`，下限 `512`；
2. 再截输入：`truncateToTokens(user, cw - estSys - maxOut)`，在句末边界截断并追加"…（内容过长，已截断）"，**保留头部优先**；
3. 仍超（连 system 都放不下）→ 换用精简版 system（去掉示例块）；
4. 兜底：照发，只记一条提示。
`contextWindow` 默认从 8192 提到 **16384**（主流兼容接口普遍 ≥16k；保守模式再减半）。
→ T1(g) 断言改写为：**(g) 任何输入（含 30k 字 revise）`chat` 都会发出请求且不抛预算类异常；请求体 `max_tokens ≥ 512`；`estimate(system+user)+max_tokens ≤ contextWindow`（降级后成立）；截断只发生在句末。**
